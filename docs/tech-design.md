## 1. Conclusion

V1 implements the expanded list as a live monitor of current Turns rather than a history list. The authoritative membership set is: root threads, across every Project and `Chats` under the current Desktop account, that have an active Turn or an unread terminal Turn and can still be navigated to exactly in Desktop under the same `threadId`.

The integration is "supported Desktop observation channel + event reducer + set correction". Project, unread state and exact navigation are all release gates and may never be inferred from cwd, timing or window focus. Desktop Project identity and unread membership are explicitly product-approved, schema-gated private read-only exceptions; every dependency on undocumented or uncommitted implementation details must be registered in [`non-public-codex-integration-features.md`](non-public-codex-integration-features.md). Official Hooks, the App Server and deep links are publicly supported interfaces and are not registered merely for being a different channel.

This document records the implementation, the verified protocol capabilities and the current beta boundaries.

### 1.1 The first implementation slice

Implemented:

- A JSON-RPC connection over `codex app-server --listen stdio://` shipped with Codex Desktop, strictly following the `initialize → initialized` handshake.
- Only seven read-only methods are called — `thread/list`, `thread/read`, `thread/loaded/list`, `thread/items/list`, `account/read`, `account/rateLimits/read`, `account/usage/read` — and the app never answers or handles approval/input requests on the user's behalf. `thread/read` **must always carry `includeTurns: false`**: it fetches one Thread's metadata by id (title, preview, the root-thread test, `status`) and is never used to read Turn history; `thread/turns/list` is never called. **`thread/items/list` is the one later exception to that constraint**, existing only for the "latest public progress" on a Codex `Running` row (PRD §7): no Codex hook carries assistant text before a Turn ends — `last_assistant_message` appears only on `stop.command.input` and `subagent-stop.command.input`, checked schema by schema against CLI `0.149.0-alpha.4.3` — so that row previously showed the user's own prompt for the whole Turn, the one thing in it that cannot change. The call shape is minimised and pinned by tests: **`turnId` is mandatory** (scoping to the reducer's own Turn), plus `sortDirection: desc` and `limit: 6`, taking only the newest `agentMessage`'s `text` on that page and skipping every other item type — never reading commands, paths or `aggregatedOutput`. See §11 and the [registry](non-public-codex-integration-features.md).
- The current account's primary rate-limit window's real `usedPercent` is read and converted to a remaining percentage; unavailable shows a grey ring.
- Today's token bucket comes from `account/usage/read.dailyUsageBuckets` for the local calendar day; the expanded footer shows the standard compact number, the quota reset date and the Settings entry. A missing today bucket inside a valid array is `0`, and an unavailable interface shows today's usage as `--`.
- A user-triggered hooks installer merges into `~/.codex/hooks.json` incrementally, preserving other definitions and requiring the user to review and trust them under Codex `/hooks`. Settings uses one `Codex integration` master switch that starts and stops the required lifecycle event definitions as one product capability; switching off stays in Settings rather than resetting onboarding.
- The Turn lifecycle bridge uses `UserPromptSubmit`, `PermissionRequest`, `PreToolUse` (catch-all, filtered by tool name inside the reducer), `PostToolUse` and `Stop`, plus `SubagentStart`/`SubagentStop` to record subagents still running on the same Thread. Every status event must carry an exact `session_id + turn_id`, and input requests and both approval shapes must be closed in pairs by the same `tool_use_id`.
- **A hook Turn becomes a row only once the App Server hands over its Thread and that Thread passes the root-thread test.** The test fails closed: no Thread received and a Thread judged a subagent have the same answer, no row. Codex side chats are what this rule exists to stop — an ephemeral thread with its own thread id firing Turn hooks as usual, yet never persisted, never listed by `thread/list`, answered `-32600 "thread not loaded"` by `thread/read`, with no deep link, and with the parentage living only in Desktop's process memory. The cost is one local `thread/read` per row rather than a full `thread/list`; measured, the thread is already persisted and readable when the first hook fires (2026-08-25, CLI `0.149.0-alpha.4.3`). Subagents are unaffected: Codex stamps their hooks with the **parent** session's identity, so they already land on the parent's row. See [ADR 0017](adr/0017-a-row-requires-a-thread-the-app-server-vouches-for.md).
- Titles come from Thread metadata in two cost tiers: threads the hook reducer currently tracks are read by id with `thread/read` (`includeTurns: false`, measured about 1.2 KB per thread), while the fully paginated `thread/list` handles only low-frequency membership reconciliation (measured about 45 KB for 33 threads, growing linearly with history). `thread/list` contractually **always returns empty `turns`** (per schema, `turns` is populated only on `thread/resume`, `thread/rollback`, `thread/fork` and `thread/read` with `includeTurns: true`), so any Turn-level fact can only come from the hook reducer. Project/`Chats` uses the exact thread assignment in Desktop's private global state and never treats `thread.section` as a Project. Unread-terminal membership read-only consumes the local unread set in that same state; active threads are always shown, and hiding happens only once the authoritative main file confirms a terminal Turn is read. Thread status holds only Running, Input needed, Approval needed and Completed, and a live `Stop` plus the App Server's `completed`, `failed` and `interrupted` all converge on Completed with no Thread-detail read to distinguish why.
- Previews are always shown, with no switch; a missing Desktop title falls back to this Turn's prompt, and failing that to `Untitled`. Codex-side prompt and answer fragments reach the running process's memory over a Unix socket from the helper, §11.
- `MonitorStore` replaces the production mock. Refresh is deadline-driven rather than polled — the store sleeps until the next moment the service says output could change, with a 60-second heartbeat as a backstop for silently failing mechanisms and a 1-second floor so a bad deadline cannot busy-loop (`system-architecture.md` §2). After the first legitimate hook, only a boolean configuration-health marker is persisted, carrying no session identity or content. On restart the reducer starts from an empty set, and every hook from before launch — `Stop` and `SessionEnd` included — restores and modifies no Turn; only hooks after this process started are live evidence, and they are the sole source of the four statuses. Running shows its status name directly — `Working...`, [`PRD.md`](PRD.md) §6.1 — the quota region always shows a real remaining share, and empty lists and global states use the thin expanded UI.
- A session row opens the same Codex Desktop thread through the official `codex://threads/<thread-id>` deep link, re-asking `thread/read` for **that one Thread** first and refusing navigation when the App Server will not hand it over or it is not a navigable root thread (no longer paginating the whole history, [ADR 0018](adr/0018-the-click-asks-about-one-thread.md)). The URL is handed only to bundle id `com.openai.codex`, and the panel collapses only once Launch Services accepts it.

Verified against this machine's current Codex version: the App Server handshake, real quota responses, the Thread/Turn schema, Desktop Project and unread private state parsing, hooks configuration merging, the event reducer and the exact navigation adapter. The unread adapter's main/backup/last-known-good paths, private schema failures, atomic-replacement directory events, the settling window and end-to-end read removal all have unit tests. The app builds and the unit tests pass.

Still unmet and therefore still blocking V1:

- A standalone App Server shares no in-process event stream with Codex Desktop and measurably cannot answer Turn-level questions (below), so launch does no cold-start sync: once the App Server completes its handshake and returns one successful `thread/list`, it publishes Ready with an empty set. Presence is already knowable then (whether Codex Desktop is running), so the collapsed state can honestly show `Connected` while knowing nothing about Turns — a deliberate asymmetry: presence is knowable the instant this app launches and Turns are not. Only an unresponsive App Server or a failed connection shows `Disconnected`, with Connecting held while the validating request is outstanding. A hook marker persisted across restarts is used only for configuration health and may never restore any session state.
- **Measured boundary (Codex CLI `0.148.0-alpha.9`, sampled on a genuinely in-flight Turn)**: a standalone App Server's `thread/loaded/list` returns empty; every Thread's `status.type` is permanently `notLoaded`; `thread/list` contractually never returns `turns`; and `thread/read` never shows `inProgress` even with `includeTurns: true` — a running Turn is recorded as `interrupted` with a null `completedAt`. The direct consequence is that `activeFlags` correction, which depends on `status.type == "active"`, **can never hold** in this topology. That mechanism (`activeEvidence`, `terminalStatus`, `reconcileActiveStatus`, `markCompleted` and `hasLiveBoundary`) was deleted outright, because leaving dead code would make a later design believe the capability exists. Should a shared-runtime topology appear, it should be redesigned on the fields verified then rather than by reviving this code.
- The current public protocol still has no read field corresponding to Desktop's blue dot; the production implementation depends on the private read-only schema registered in §1.3. The real read/unread version matrix after a Desktop upgrade is still a release verification item, and any incompatibility must conservatively keep terminal rows.
- Hooks reliably cover the start, both approval shapes, `request_user_input` and terminal boundaries; Approval needed is always proven by a tool call's open/close interval (a dedicated approval tool forms its own, an ordinary tool is named by `PermissionRequest` borrowing its still-open call id), and a lone `PermissionRequest` does not prove a person is still needed. **What hooks cannot answer is whether an approval will reach a person**: `PermissionRequest` fires even when an automatic reviewer passes it, and the official schema has no field distinguishing the two (measured 2026-08-22), so that half's evidence comes from §9.2's Desktop approval-routing gate. The App Server's `completed`, `failed` and `interrupted` all map to Completed, and end-to-end coverage still needs verifying against a real Desktop sample matrix.
- `threadSource`/`sourceKinds` still cannot by themselves prove the Desktop versus standalone-IDE origin boundary and must keep being verified against real samples.

### 1.2 Read-removal and exact-navigation capability boundaries

- The official [Codex Desktop deep links](https://learn.chatgpt.com/docs/reference/commands#deep-links) define `codex://threads/<thread-id>`. The navigation adapter is implemented under this section's constraints; Codex still offers no public receipt that the page finished rendering.
- The official [Codex App Server](https://learn.chatgpt.com/docs/app-server) currently has no unread/read/open/current-view field or notification. `thread/read` reads a Thread record rather than marking it read, and neither `thread/loaded/list` nor `thread/closed` expresses blue-dot semantics.
- The current Desktop package persists the blue-dot set in `$CODEX_HOME/.codex-global-state.json` under `electron-persisted-atom-state.unread-thread-ids-by-host-v1.local`. With product approval, this field is in production as a standalone, registered private read-only adapter, and it does not extend to other Electron state or IPC.
- The implementation must handle atomic replacement and brief main/backup generation differences. An active Turn is shown regardless of the blue dot, and only a terminal Turn is removed once it disappears from the unread set in an authoritative main-file snapshot — **and that snapshot must have been written after that Turn ended**, because the blue-dot set is an on-disk projection of Desktop's in-memory state, and when the projection lags, its silence describes a different moment (measured 2026-08-26, §1.3). It must never inject IPC, modify `app.asar`, use Accessibility/AppleScript, or treat Stop/SessionEnd as a read.
- Direct Developer ID distribution with the App Sandbox off can technically read that path; the Mac App Store sandbox would need the user to choose the directory and a security-scoped bookmark. Under either, a readable file is still not a supported interface.
- The long-term direction is migrating to a future public `hasUnreadTurn` snapshot and change notification from Codex; when an equivalent public capability appears, the private adapter and its registry row must be removed in the same change.
- **Claude Code has no equivalent deep link.** `claude-cli://open` and `claude://code/new` both only create sessions, and `claude://code/sessions/local_…` is measurably rejected by Desktop. That side is therefore implemented as raising the host (§14.2), degraded per product per [ADR 0004](adr/0004-make-exact-desktop-navigation-a-release-gate.md). After every Claude Desktop update, re-check whether the `/code/sessions/` route begins accepting local session IDs; once official support appears, migrate to the deep link and remove the Apple Events path.

### 1.3 The Desktop unread private read-only adapter (implemented)

Read-only verification against Desktop `26.810.50856` build `6644` and CLI `0.148.0-alpha.9` shows:

- The state root is `process.env.CODEX_HOME ?? ~/.codex`, and the default file is `.codex-global-state.json`.
- The unread set is at `electron-persisted-atom-state.unread-thread-ids-by-host-v1.<hostID>`; local V1 may consume only `local` and may not merge other hosts.
- Desktop waits about `500 ms` after a state change before persisting; writes atomically replace the main file by `rename` from a temporary file in the same directory, then replace `.bak` separately. So the target inode changes, and the main file and backup may briefly belong to different generations.
- **"About 500 ms" is that delay's floor, not its ceiling** (re-measured on Desktop `26.820.60940`, 2026-08-26). The main process persists the **entire** `electron-persisted-atom-state` through a 500 ms trailing debounce **with no max-wait, shared by every persisted atom** — any atom written more often than every 500 ms pushes persistence back indefinitely. The composer draft `composer-prompt-drafts-v2` is exactly such an atom, written by the editor's `dispatchTransaction` on **every keystroke**. Measured: typing 165 characters continuously into the composer produced **one** write in a 45.4-second window, about half a second after typing stopped and none during it. So the blue dot lights in Desktop's sidebar within milliseconds while that id stays out of the file for the whole stretch. Non-atom top-level keys (window position, current Project) persist immediately and flush the whole atom map as a side effect, which makes the starvation intermittent and is how 583 ms came to be measured.
- This is a real Thread-level blue-dot set with no Turn ids. It composes only with the domain model "each Thread shows its latest active or unread terminal Turn".

The production implementation:

1. `CodexDesktopUnreadStateRepository` reads `$CODEX_HOME/.codex-global-state.json` only, with `NOTCHLINE_CODEX_HOME` overriding the Codex home for tests and isolated environments.
2. A directory-level `DispatchSourceFileSystemObject` with `O_EVTONLY` watches the Codex home rather than holding the target file's inode; directory events refresh after a **50 ms** trailing debounce, sized to the 3–14 ms burst an atomic replace produces. When the watcher cannot attach, the backstop is `nextRefreshDeadline()` and the 60-second heartbeat, never a poll.
   **Attaching is not a one-off.** A missing target (`~/.codex/hooks.json` does not exist on first run) or one deleted/replaced (reinstalling after an uninstall, Codex swapping its whole state directory) must be recoverable: the watcher reopens its descriptor on `rename`/`delete`, and both the unread repository's `snapshot` and `CodexHookRegistrar.registration()` call `attachIfNeeded()` on the read they were making anyway; after this app's own install/uninstall, `invalidateRegistration()` drops the cache and the following read re-attaches in passing. **There is deliberately no retry timer of its own** — the cost of failing to attach is one failed `open` per refresh rather than an extra wake-up source.
3. Only the `local` host's string set is parsed, validating all host names, empty ids and duplicate ids. The reader rejects symlinks, files not owned by the current user, files over 4 MiB, malformed JSON and incompatible schema, and records neither raw JSON nor thread ids.
4. `.bak` is read when the main file fails, and an in-process last-known-good is kept when both do. But backup and last-known-good serve only retention and diagnostics: only a main-file snapshot with `source == current` may make a new hiding decision, and a parse failure must never be interpreted as an empty set.
5. Active, Input and Approval are always shown and clear that Turn's terminal gate. **For an authoritative snapshot to speak for a Turn, its `modificationDate` must not precede that Turn's own end** — `HookTurnState.turnEndedAt`, compared against `DesktopUnreadStateSnapshot.currentAsOf`, and never `terminalBoundaryAt`, which a subagent outliving the Turn pushes past the answer (see §1.5.3); an earlier write happened before this Turn ended and cannot have recorded it, so "the id is absent from the set" says nothing about it — the row stays and waits for the next write on the 1-second re-check (waiting on a file rather than a user, so a locked screen keeps waiting). On top of that, a 2-second settling window still applies when a terminal Turn first appears and the main file does not yet contain the unread id — but that window now covers only the milliseconds between Desktop receiving `turn/completed` and the renderer pushing the atom to main, and is no longer a persistence delay (that delay is unbounded, above; widening the window was rejected, because any window wide enough to cover typing keeps read rows on the notch just as long). Once unread has been observed and then disappears from an authoritative main snapshot, hiding is immediate. The hiding gate holds through a transient parse failure so the UI does not flash back, while new terminal rows keep showing during it.
6. `MonitorStore` consumes the directory change stream, and one shared in-flight gate merges concurrent refreshes. Stopping monitoring or switching the integration off clears terminal gates (~~clear the list~~ — that action is deleted, §16.2).

The adapter has fixtures for success, absence, corruption, backup, last-known-good, schema incompatibility, atomic replacement and terminal races; after a Desktop update the real read/unread and finish/read race matrix must still be run. The target is p95 sync under 1.5 seconds and p99 under 2, with no error ever removing a terminal row early. The current Developer ID non-sandboxed build can read that path; the Mac App Store sandbox would still need a user-chosen directory and a security-scoped bookmark, and support must not be claimed before it is implemented.

Independent research into other routes found no public, accurate alternative:

- The App Server, hooks, notifications, JSONL, SQLite, window focus and deep-link callbacks none of them express "the user has read this".
- The current Desktop private Unix socket `~/.codex/ipc/ipc.sock` does broadcast `thread-read-state-changed` deltas, but with no initial full snapshot; a connector would have to register as an internal IPC client and take part in discovery, possibly affecting routing and timeouts. Its risk and version coupling both exceed a pure read-only file, so it is not adopted.
- Accessibility, AppleScript, title matching, timed removal and "Desktop got focus means read" are all inaccurate and violate the safety constraints. (This is written for Codex. The Claude Code exception is product-approved, [ADR 0012](adr/0012-read-state-is-answered-per-product-or-not-at-all.md): there is no other source there, and which session is on screen is a matter of record, so focus speaks about **that one** session rather than "every thread is read". Accessibility, AppleScript, title matching and window geometry remain banned on both sides.)
- The only public, honest product compromise is defining a Notch click as this app's own "acknowledged", but it cannot cover reading directly in Desktop and must not be called Desktop read sync; the current product semantics do not adopt it.

The minimum public capability that could replace this private implementation is still a `hasUnreadTurn` snapshot obtainable at launch and reconnect, plus a `thread/readState/changed` notification carrying `threadId`, `hostId` and the new boolean, with capability/version negotiation.

### 1.4 The Desktop Project private read-only adapter (implemented)

The current public Thread schema has no Desktop `projectId`/`projectName`, and `thread.section` is an independent Thread Section that cannot serve as a Project. With product approval, Project identity uses a strictly limited private read-only adapter:

- It reads `$CODEX_HOME/.codex-global-state.json` by default, with `NOTCHLINE_CODEX_HOME` naming the Codex home explicitly.
- A `local` assignment in `thread-project-assignments[threadId]` joins to `local-projects[projectId].name`, and a `remote` one to `remote-projects[id].label`.
- `Chats` shows only when `projectless-thread-ids` explicitly contains the thread ID. When the file has no mapping for that thread at all, `Project unavailable` shows, and it must never fall back to `cwd`, the Git root, the Section or `Chats`.
- The current schema's minimum key set: at least one of `thread-project-assignments` and `projectless-thread-ids` must exist, and `thread-project-assignments` must exist whenever any Project is defined. All four top-level keys are deliberately not required — measured, a healthy state file has `remote-projects` missing entirely (Desktop writes it only with a cloud Project), and requiring it would fail closed on the most common local-only installation.
- **An assignment that is written but unreadable is schema drift, not "this thread has no Project"**: an empty thread id, a `projectKind` that is not `local`/`remote`, or a `projectId` naming an undefined Project each void the whole current snapshot and degrade to `.bak` / last-known-good with a diagnostic saying why. Skipping such an entry would publish a quietly incomplete mapping still marked `.current`, exactly what the fail-closed contract excludes. Renaming `local-projects` or `remote-projects` is caught by the same rule, since every assignment it resolved would dangle.
- On a failed main-file read or parse it tries `.bak`, and with both failing it keeps an in-process last-known-good and emits a diagnostic. Parse results are reused by size, mtime and inode revision while the file is unchanged.
- The reader rejects symlinks, files not owned by the current user, files over 4 MiB, empty Project names, duplicate remote ids and conflicting Project/Chats membership; it records no raw JSON, root path or thread id, and diagnostics say only which rule was violated.

Verified on Desktop `26.810.50856` build `6644` and CLI `0.148.0-alpha.9`. It remains a high-version-risk private schema, and updates and failure triage must follow [`non-public-codex-integration-features.md`](non-public-codex-integration-features.md).

### 1.5 The Claude Code read-state adapter (implemented)

The Claude Code side previously had no read-state source at all, and a terminal row could only leave on the next submission, the session disappearing, or the user removing that row by hand (CC-013). It now splits in two with **entirely different evidence**: desktop-hosted sessions read Claude Desktop's private records (1–7 below), and terminal sessions read the kernel's record of controlling-terminal access time (§1.5.1, involving no private schema). Product semantics and the division are in [ADR 0012](adr/0012-read-state-is-answered-per-product-or-not-at-all.md); this section records only the implementation.

Read-only verification against Claude Desktop `1.32885.1` and CLI `2.1.235` (2026-08-19) shows:

- Each desktop-hosted session has a record at `~/Library/Application Support/Claude/claude-code-sessions/<org>/<account>/local_<uuid>.json`, whose `cliSessionId` is the `session_id` the hook carries, so identity needs no inference.
- `lastFocusedAt` is written as `Date.now()` by `setSessionVisibility(id, isVisible, reason)` when `isVisible` is true, followed immediately by `saveSession`. It means "last displayed on screen", not "last active".
- Writes atomically replace by `rename` from a temporary file in the same directory (measured: the inode changes), so a **directory-level** watcher can see them — the opposite of `~/.claude/sessions/<pid>.json`, which is rewritten in place and where only a file-level watcher helps (§15.1).
- A pure terminal session has no file in this tree at all, and Claude Code's own session record writes no focus field (searching the 2.1.235 and 2.1.236 binaries: no focus/read/seen key is persisted; the in-process `userPresence` object holds `lastInteractionTime` and `terminalFocus` but is never persisted and never sent as a hook). **That half therefore asks its terminal instead of Claude Code — §1.5.1.**

The production implementation:

1. `ClaudeCodeDesktopReadStateRepository` reads `~/Library/Application Support/Claude/claude-code-sessions` by default, with `NOTCHLINE_CLAUDE_DESKTOP_HOME` overriding Claude Desktop's application-support root. The tree is enumerated at exactly two levels of `<org>/<account>`, never recursively searched.
2. Each record decodes exactly four fields: `cliSessionId`, `sessionId` (Desktop's own `local_<uuid>`, the id its log names on screen, used to join the log back to hook identity), `lastFocusedAt` and `isArchived`. The title, `cwd` and MCP configuration in the same file are never decoded. The reader rejects symlinks, files not owned by the current user and files over 4 MiB.
3. **Parse results are cached on `(size, mtime, inode)`**, so each read opens only records that genuinely changed. Measured on this machine's 31 records (about 2 MB): 5 ms cold, 1 ms fully cached. Past 512 records the 512 newest by mtime are taken — a live session must be among those recently displayed or resumed — and the tail answers unknown and keeps its rows. **The whole pass is wrapped in `autoreleasepool`** (CR-Fable-041): a fully cached pass produces almost no bridged objects, since the directory and three numbers come back in one `getattrlistbulk` rather than a per-file `attributesOfItem` — but **a pass that opened records** does a `resourceValues`, an `attributesOfItem`, a `Data` and a decode per file, all autoreleased, in a synchronous actor method with no pool of its own. Release measurements in `system-architecture.md` §6.
4. **The left half of every one of these comparisons is `HookTurnState.turnEndedAt`, the Turn's own terminal.** Not `terminalBoundaryAt`: that is the later of the Turn's end and its last subagent boundary, and handing it to the read tests is what made a read row immortal (§1.5.3). The test has two layers. The file layer is in the provider: `readState(forSession:terminalBoundaryAt:)` compares against the Turn's own end (`HookTurnState.lastEventAt`), where `lastFocusedAt >= boundary` means read, `isArchived` likewise means read, and **an absent record is unknown rather than unread**. The cross-source layer is in the orchestrator (`AGENTS.md` §6.1, "a decision spanning data sources belongs to the orchestration centre"); when the file says unread, three more tests each supply a fact the file lacks:
   - **`comingBackShowedIt`**: `isOnScreen(that session)` and `DesktopActivationReporting.lastActivation()` later than `boundary`.
   - **`isInFrontOfThem`**: `isOnScreen(that session)` and `DesktopReadingReporting.isInFrontOfTheUser()`. **The only test in the whole app that compares no moment and asks nothing of the user**, and therefore the only one that can retire an unread row; the trade-off is ADR 0012's rule 3.
   - **`movedOnFrom`**: this app saw, at some refresh, that session carrying a `.completed` row on Claude Desktop's screen, and Desktop has since put **another session** there (`hasReplacedItOnScreen`). That membership is recorded on the Turn rather than the session — cleared as soon as the row is no longer `.completed` — and cleared with the session leaving the list.

   **All three ask one question — is that what is on screen — and it has two sources, §1.5.2.** The records answer only half: `setSessionVisibility` stamps only when a session is **put** on screen and writes nothing when one is taken off, so after the user switches to a **new session's composer** the last-stamped session goes on impersonating "on screen". `isOnScreen` is therefore the **intersection** of the records and Desktop's log, and `hasReplacedItOnScreen` additionally requires the thing displacing it to be a **session** — a composer is not one, and making room for it is not somebody finishing and moving on.

   **Both later tests were forced by measurement rather than added for safety.** On a real machine 2026-08-19: the user switched away, waited for the Turn to finish, switched back to the same session and read it — and **0 files** in the whole `~/Library/Application Support/Claude` tree were modified in 6 minutes; the same review confirmed the package has no read field at all (`lastReadAt`/`hasUnread`/`seenAt`/`viewedAt`, zero hits). (That review also once recorded that "`main.log`'s `setFocusedSession` is a subset of the `lastFocusedAt` stamps" — **that was wrong, and a lost-row measurement overturned it that evening**: in the decisive direction it is a *superset*, because it also writes `sessionId=null`, which is exactly the half the records cannot express. See §1.5.2.) Product semantics, the two written rules this overturns and the costs are in [ADR 0012](adr/0012-read-state-is-answered-per-product-or-not-at-all.md).
   The activation signal comes from the public `NSWorkspace.didActivateApplicationNotification` (`DesktopActivationWatcher`), filtered by bundle identifier, recording only the **moment of a transition** and never "is it in front right now", and knowing only activations after this app started.
   "Is it in front of a person" comes from `DesktopReadingWatcher`: the same public notification maintains "does that application hold the foreground now" (seeded once at construction from `NSWorkspace.frontmostApplication` and driven only by notifications afterwards), minus three states that hold the foreground and mean nothing — `CGDisplayIsAsleep` for a sleeping display, `CGSessionCopyCurrentDictionary` reporting a lock or not being on console, and the public `com.apple.screensaver.didstart` / `didstop` reporting a running saver. All three are public, need no entitlement and measurably prompt for no authorisation; an unreadable session dictionary answers `false`, failing towards keeping. Hiding an app is not listed separately (hiding surrenders the foreground); **minimised, another display and another Space cannot be told apart**, and rows in those three states are retired unseen, an accepted cost rather than a gap.
   A version using "a keystroke or scroll" as evidence once shipped (`c1052bb`, `CGEventSource.secondsSinceLastEventType` for `.keyDown` and `.scrollWheel`); it is safer but cannot answer "sat, read, did nothing", and is superseded by this. Its details and one flaw are in ADR 0012's rejected list.
5. It reuses the Codex side's `TerminalUnreadMembershipGate`: each refresh the service folds the test results into one unread set for it, with identical settling-window, "hide immediately once unread has been observed" and `retain` rules. **A row that cannot be asked about never enters the gate** (no Desktop record and no controlling terminal), so it never re-checks once a second for a question with no answer; its exits remain the next submission, the session disappearing, or manual removal (right-click on the row; ~~or clearing the whole list~~ — clear-all is deleted, §16.2). **Manual removal is also an exit for a row already in the gate**: the dismissal travels down with the snapshot request (§17), a dismissed row is no longer evaluated, `retain` drops its entry, and it books no further re-check (CR-Fable-003). **The unread snapshot the gate receives is split in two by row**: rows judged by Desktop carry the Desktop reading's source (which may hide nothing while `unavailable`), and rows judged by a terminal carry `.current`. That split is not decoration — a user who has never opened Claude Desktop has no tree at all and that reading is permanently `unavailable`, so letting terminal conclusions borrow it would switch the path off entirely on exactly the machines that need it most. It is also honest: the Desktop source exists because that reading can lag a generation (a snapshot kept after a parse failure carries an old focus moment), whereas a device access time cannot lag — it is read live in the refresh that uses it, and a failed read answers `nil` and moves that row **out** of the gate rather than entering with a stale conclusion.
6. There are two edges: Claude Desktop writing a record, and it returning to the foreground. The latter comes straight from the activation notification, so "switch back and read" is the same event as the row leaving the notch, with no need to wait for the gate's 1-second re-check. **`isInFrontOfThem` has no edge**: it needs three states at once (foreground, display, lock), so it is sampled on the 1-second re-check the gate has already booked for waiting rows, and that second is also its upper bound; with no row waiting, no sample happens. **But when the display and lock states are false, that second stops sampling entirely**: one of the three is then permanently false and the answer is known before any work starts (CR-Fable-018). A row disappearing after the user wakes the screen or unlocks is instead driven by `ScreenAvailabilityWatcher`'s edge — the one moment those two states go from false to true, arriving before the user can do anything — and only then does it return to that second. The former edge comes from `PathSetChangeWatcher`, a watcher whose watched path set can be replaced at any time, shared with `ClaudeCodeSessionRecordWatcher`. The adapter watches the state root plus every account directory discovered; account directories are discovered on the first read, and new ones by a root-directory edge or the heartbeat.
7. Failures fail closed throughout: an absent tree (normal for a pure terminal user) is `unavailable` **with no diagnostic**; one unreadable record makes only that session answer unknown; and **only when every record is unreadable** is the schema judged incompatible, emitting a diagnostic and keeping last-known-good with no new hiding.
8. **With no `.completed` row in the list, none of the above is asked at all** (CR-Fable-041). The gate passes non-terminal rows straight through and drops their entries, so this reading — the whole account tree, Desktop's focus log, activation moments and one terminal `stat` per row — can only change whether a terminal row stays; the original fetched it before looking at `rows`, so a list entirely of Running rows read it pointlessly on every refresh, and once any terminal row anywhere pins refresh at 1 Hz that pass was once a second. The skipped pass still does both pieces of bookkeeping: screen membership and gate entries are cleared, exactly as the original pass cleared them row by row for such a list. **The diagnostic is skipped with the reading**: it says "terminal rows have been kept for you", and there are none. The test uses `TerminalUnreadMembershipGate.isTerminal` rather than a second in-place `== .completed`, so a future widening of the gate's definition cannot silently miss a new case here.

#### 1.5.2 Which session is on screen: beyond the records, ask Desktop's log (implemented)

All three tests above rest on one sentence: **this session is the one Claude Desktop has on screen**. The records answer only half, and the missing half loses rows.

Measured (the evening of 2026-08-19, Claude Desktop `1.32885.1`, with the user never having read that row):

| Time | What the user did | What the records held |
| --- | --- | --- |
| 21:02:30 | switched to session A | `lastFocusedAt` ← now |
| 21:03:30 | opened a **new session's composer** | **nothing** |
| 21:03:58 | A's Turn ended | the row went Completed; this app still believed A was on screen and recorded "on screen when it ended" against it |
| 21:04:18 | sent the new session's first message | the new session was displayed → `movedOnFrom(A)` held → **the row was removed as read** |

The same stale judgement also loses rows earlier through `isInFrontOfThem` (Claude Desktop holds the foreground while the user types in the composer) and through `comingBackShowedIt` (the user returning to the window to send).

**Claude Desktop states this itself**, in its own log, and in both directions:

```js
setFocusedSession(e){ log.info(`[CCD] LocalSessions.setFocusedSession: sessionId=${e ?? `null`}`), … }
```

Called on every navigation, with `info` written unconditionally, and `null` being exactly the half the records cannot express (a composer, Home, the settings page). Measured, each navigation writes `null` and then its destination (another session writes a second line with an id; still `null` means what is on screen is not a session).

`ClaudeDesktopFocusLogReader` therefore reads `~/Library/Logs/Claude/main.log` (overridable with `NOTCHLINE_CLAUDE_DESKTOP_LOG`) and answers one of `.session(desktopSessionID:)` / `.nothing` / `.unknown`:

1. **Only lines this app watched being appended count.** `AGENTS.md` §6.2: business state comes only from a current snapshot or events observed after this process started. At launch (and after the log is rotated or truncated) that history is read once and **allowed to say exactly one thing: `.nothing`** — the direction that only keeps a row a little longer, a cost the product already accepts; a session named in the history answers `.unknown`.
2. Each read `stat`s once and decides by (inode, size) whether to continue or restart, reading at most 256 KiB per read (this machine's log is about 800 KiB/day) and **parsing only to the last newline** — a half-written line carries half an id, and half an id would read as "a different session is on screen".
3. Only that one line shape is matched and only what follows `sessionId=` is taken; every other line is unparsed. Everything but a regular file owned by the current user is rejected; nothing is written.
4. If the file disappears or cannot be read, **the last statement is kept** (Desktop going quiet is not Desktop retracting what it said) and only the read offset is forgotten.

**In the orchestrator it is a veto rather than a fifth source** (`ClaudeCodeMonitorService.isOnScreen` / `hasReplacedItOnScreen`): it can block the session the records claim but cannot nominate one they do not, and `.unknown` is the behaviour from before this log. So a missing, rotated or reshaped log at worst reverts to the old behaviour and never retires a row early. The `local_<uuid>` → hook identity join comes from the records' `sessionId` (§1.5 item 2), and an unjoinable id always reads as "not this session".

**That "a veto, not a source" has one exception, forced by measurement (CC-024).** `hasReplacedItOnScreen` once followed the same rule: require the **records** to have named another session, then let the log veto. The problem is that the two sources say the same thing at different times. Measured (2026-08-20, this machine):

| Time | What happened |
| --- | --- |
| 11:14:41.910 | Desktop stamps `lastFocusedAt` and writes the navigation to the log in the same instant |
| 11:14:42.257 | the CLI it started for the opened session writes `~/.claude/sessions/<pid>.json`, whose directory edge wakes a refresh |
| 11:14:42.938 | Desktop's own record finally persists (1.03 s after the stamp) |

In that second the log has already named the new session while the newest `lastFocusedAt` still belongs to **the session just left**. So it is neither on screen (the log vetoes) nor displaced (`hasReplacedItOnScreen` asks the records, and the records have not moved) — all four read paths fail at once and the row is reported unread again. What the user sees is: **switching between two finished sessions makes the Claude Code matrix flash like a completion signal and go dark again.**

The fix lets the log answer this one question itself, with the records stepping in only when the log answers `.unknown`. This is not a new judgement but the same judgement the records would give a second later; and it is still only a statement about who is on screen — what turns it into "read" is `movedOnFrom`, which holds only for a session that has actually appeared on screen carrying a finished Turn.

**An unjoinable id must be split in two here, or §1.5.2's last sentence is forfeited.** When a `local_<uuid>` the log names cannot be joined to any hook identity, it may be either **a record not yet written** (the very second this rule handles) or **a record no longer carrying its own `sessionId`** (§1.5 item 2's degraded form). Reading the latter as "not this session" is right; reading it as "another session displaced it" would retire a row on a name nobody verified. Separating them needs no waiting: compare against **this session's own record's** Desktop id — if it records a different id, what is on screen is not it, whatever that pending record eventually says; and if its own record has no id at all, fall back to the records answering alone, which is the behaviour from before the log.

**A second change is in the gate and is source-independent: once hiding is done, it is final for that finished Turn** (`TerminalUnreadMembershipGate`, shared by both products). It previously put a row back the moment it read "unread again", making the row a live reading of what each source currently says — and those sources are files another app writes on its own schedule, so a brief disagreement is normal rather than exceptional and every one of them would flash an already-retired row back onto the notch. Nothing can genuinely become unread again within one finished Turn, so refusing costs nothing; the only thing that brings a row back is **a later Turn ending** (`terminalBoundaryAt` advancing), and a new Turn normally passes through a running state where the gate drops the entry entirely.

**It has no edge of its own.** The one transition only it can see (a session giving way to a composer) only keeps rows, and a terminal row listed on the notch already re-checks once a second; every transition that can retire a row comes with Desktop writing a record or a hook arriving, and those edges already exist. Watching this file for it would buy a wake-up for every oauth line and git-diff timing Claude Desktop logs.

#### 1.5.1 Terminal sessions: controlling-terminal access time, plus whether that terminal is in front of a person (implemented)

Desktop's tree says nothing about a terminal session, and Claude Code has no concept of read. This half therefore asks a different party: **that session's controlling terminal**.

`ControllingTerminalGestureReader` reads **two facts** at once, all public BSD interfaces plus one public workspace notification, opening no file contents:

1. `sysctl(CTL_KERN, KERN_PROC, KERN_PROC_PID, pid)` → `kp_eproc.e_tdev`, the process's controlling terminal device number (`-1` meaning none). The pid comes from the public `claude agents --json`, the same one `~/.claude/sessions/<pid>.json` is named by.
2. `devname_r(dev, S_IFCHR, …)` → `ttysNNN`, composed into `/dev/ttysNNN`. **Cross-checked once**: the `stat` must still be a character device whose `st_rdev` equals step 1's device number — `devname_r` answers from a name table cached by device number, and a reused name would attribute another terminal's actions to this session.
3. `stat`'s `st_atimespec` — the **gesture** half.
4. The same `sysctl`'s `kp_eproc.e_ppid`, walked upwards to see whether **the foreground application's pid is an ancestor of this session** — the **in front of a person** half. The chain measured here is `claude` → `-/bin/zsh` → `/usr/bin/login` → `Ghostty`, walked at most 16 levels. The foreground pid is maintained by `NSWorkspace.didActivateApplicationNotification` (the same notification as `DesktopReadingWatcher`, for the same reason: this question is asked on the refresh's executor, and AppKit does not guarantee answering there), and it reuses `DesktopReadingWatcher.systemScreenIsAvailable` — a sleeping display, a lock screen or a switched-away user all mean holding the foreground is not being in front of anyone, and **locking is itself one of the ways a surface receives `ESC [ O`**.

Step 4 needs no terminal allowlist, no bundle id and no judgement about which level counts as the application: **the chain that reaches the foreground process is the chain hosting it**, whoever that is. It shares `systemParentProcessIdentifier` with the navigation path (`ProcessAncestryHostResolver.systemParent` is now just a forwarder).

The test is in the orchestrator (`ClaudeCodeMonitorService.rowsStillWorthShowing`), as the fifth path beside Desktop's four: **access time ≥ that Turn's end, and that terminal's application holds the foreground now**. The left side has the same source as the other four (the Turn's own end). A session answering `nil` (no controlling terminal, or unreadable) never enters the gate; **a session answering "nobody is in front of it" does enter** — that is "unread" rather than "cannot be asked", so it keeps re-checking once a second and clears the moment someone returns to that terminal.

**It is a peer of the four rather than their fallback**, even though a fallback would read more naturally (desktop-hosted sessions have records, terminal-started ones do not, and between them everything is covered). **Remote control** is why it cannot be written that way: one session sits in front of both a terminal and Claude Desktop, read by different gestures, and only one side writes anywhere this app can see — reading it in the terminal does not move a byte of Desktop's record. As a fallback, such a row would wait indefinitely on a `lastFocusedAt` that will never advance.

The reverse direction is safe structurally rather than by luck: this can only hold for a session that genuinely has a controlling terminal, and Claude Desktop-hosted sessions do not — Desktop runs the CLI as `--output-format stream-json` over pipes with no terminal interface, which is also why those sessions have no `status` ([#41](https://github.com/soondubu137/notchline/issues/41)).

(Measured 2026-08-19: a CLI session with remote control on has **no record at all** in the `claude-code-sessions` tree — no file anywhere in the Claude Application Support tree mentions its `sessionId` or its `bridgeSessionId` — so today it answers `unknown` and never reaches the "present on both sides" branch. That is a fact about one Desktop version, not a property the product should rely on.)

Measured (from 2026-08-19, re-measured and extended on Ghostty + CLI `2.1.238` 2026-08-20):

| Event | Access time | Modify time |
| --- | --- | --- |
| A keystroke | advances | — |
| That surface gains the foreground (`ESC [ I`) | advances | — |
| That surface loses the foreground (`ESC [ O`) | advances | — |
| **The pointer crossing that surface** (`ESC [ ? 1003 h` all-motion mouse reporting) | **advances, with no foreground needed** | — |
| **A hidden surface** through two complete foreground switches | **0 changes** | — |
| The CLI rendering output | unchanged | about twice a second |
| **A whole Turn** (submit → answer → Stop hook → notification and bell) | **advances only at the submission**, then unchanged for 110 s | moving throughout |
| An idle session (nobody touching the terminal) | 0 changes in 150 s | — |
| **A `read` returning `EAGAIN` having read zero bytes** | **advances** | — |
| `write` / `open` / `close` / `tcgetattr` / `ioctl` / `select` on the same device | unchanged | `write` advances |

**The second-to-last row overturns this path's original premise.** Access time records not "the terminal handed the session something" but "the session issued a read on this device" — an empty read is as good as a keystroke. That difference is invisible while only the terminal handing something over makes the CLI read, and the next row makes it visible.

**The fourth row is this bug.** Claude Code enables all-motion mouse reporting itself — `ESC [ ? 1000 h`, `1002 h`, **`1003 h`**, `1006 h`, written once at startup and again mid-session (captured on `2.1.238`) — so the terminal writes bytes into the pty for **every movement of the pointer over the window**, needing no keypress, no button and **no foreground**. macOS delivers pointer motion to whatever is under the pointer, regardless of which app is active (exactly what [ADR 0012](adr/0012-read-state-is-answered-per-product-or-not-at-all.md) says when rejecting `CGEventSource` mouse movement). On two displays the pointer **merely passing** over an unfocused terminal window on the other screen advances the access time, and an unread terminal row disappears within a second. Nothing can be told apart afterwards: access time is a scalar, and by the time it is read, why it moved is gone.

So the test now requires the gesture **and** the foreground together. This folds a state into a transition, the same direction as `DesktopReadingReporting`'s reversal, but here it is only an `AND` and can **only narrow** the path: the pointer crossing an unfocused window no longer counts; an `ESC [ O` caused by another app grabbing the foreground no longer counts (at sampling time the foreground is that app's, not this terminal's); and keystrokes and `ESC [ I` still count, since both already require that terminal to be in front. **It is still a transition first** — a terminal in front of an empty chair produces no gesture, and a state alone is never enough.

Row five is the whole reason this path holds per session rather than per application, and row six is the whole reason access time must be read rather than modify time. Focus reporting is likewise Claude Code's own (`ESC [ ? 1004 h`, in the shipped binary, written on every exit from the alternate screen).

**No edges, only sampling.** Device access time is advanced by the kernel and produces no filesystem event, so it is sampled on the `terminalUnreadRecheckInterval` (1 second) the gate has already booked for waiting rows, and that second is also the upper bound on a row leaving. The cost must be accounted **per whole refresh** rather than per reading: that deadline wakes `MonitorStore.performRefresh`, which runs a complete `fetchSnapshot` for every registered product, so this reading's direct cost (one `sysctl` and one `stat` per listed terminal row, plus a walk of at most 16 hops — now always run to completion, since "could the host ever be in front" must be answered regardless of foreground and screen state, with one more `proc_pidpath` per hop) is a small part of the bill. Pricing it as a single `sysctl` once hid two real 1 Hz costs (CR-Fable-018, CR-Fable-036). What actually holds the total down is **who does not enter the gate** and **when nothing is booked**: nothing is asked with no row waiting, a row whose host can never be in front never enters the gate, and a row waiting on a user books nothing while there is no screen.

**Degradation directions.** A terminal without focus reporting (or a multiplexer with `focus-events` off) is left with keystrokes, so the row waits for the next keypress rather than a return to the tab; a session inside `tmux`, `screen` or `ssh` walks its chain only to `launchd` and its host can never hold the foreground, so such a row waits for the next submission — **a degradation this change adds**, in the keeping rather than the retiring direction; and a session with no controlling terminal keeps its existing behaviour. **This must be reported by the reading itself** rather than left for the caller to infer from "not in front right now" (CR-Fable-036): the two look identical in a single reading, but "not in front for the moment" is worth asking again a second later while "can never be in front" gives the same answer however often it is asked — and `terminalCanSpeak` originally tested only "is there a device", reading the latter as the former, so one `tmux` session booked a 1 Hz two-product full refresh for its entire lifetime. `ControllingTerminalReading` therefore reports `hostCanEverBeInFrontOfTheUser` alongside `hostIsInFrontOfTheUser`: the same walk also answers **whether the chain passes through any `.app` bundle** — every chain ends at `launchd`, so the *destination* distinguishes nothing and what distinguishes them is what they pass through (measured `claude` → `zsh` → `login` → `Ghostty.app`, against `claude` → `zsh` → a daemonised `tmux` server reparented to `launchd`). The test looks only at the path, reusing the rule `ProcessAncestryHostResolver` already writes, and opens no `Info.plist`: the question is whether there is *an* application on the chain, not which one. Unreadable ancestry (the process has gone) also counts as "can never be in front", again in the keeping direction. A session with a device whose host can never be in front is treated exactly like one with no device: **it never enters the unread gate**, so it books no re-check for a question with no answer. **Two paths still fall towards early removal**: pointer movement over a terminal window that **does** hold the foreground counts as read (the same trade `DesktopReadingReporting` makes for a window in front of an empty chair, and narrower — it also requires someone to have moved the pointer); and the foreground is sampled about a second after the gesture, so a user leaving in the milliseconds between `ESC [ O` and the workspace notification reads as not having left.

Unit tests come in two layers: `aTerminalsAccessTimeRecordsBeingReadFromRatherThanBeingTypedInto` opens a real pty against the real kernel to verify rows one, six, nine and ten of the table above — **the empty-read row is the one added here, and it is what this reading actually means** — and `aTerminalIsInFrontOnlyWhenItsOwnApplicationIs` verifies step 4's four answers with an injected process chain (reaching the foreground process, reaching another application, reaching `launchd`, screen unavailable). The five behavioural cases use injected doubles and therefore do not depend on which terminal the developer runs the tests in; among them `aGestureAtATerminalNobodyIsInFrontOfRetiresNothing` pins this bug.

## 2. Design constraints

#### 1.5.3 One instant per question: `turnEndedAt` dates the reading, `terminalBoundaryAt` bounds the window (implemented)

**Both products' read tests take `HookTurnState.turnEndedAt`, the Turn's own terminal, as the moment they must be later than.** Reading is something a person does to a Turn's *answer*, and the answer landed when the Turn ended: Codex's blue dot, Claude Desktop's `lastFocusedAt`, its return to the foreground and a controlling terminal's access time are all evidence only if they came after that.

`HookTurnState.terminalBoundaryAt` is a different fact — the later of the Turn's end and the last subagent boundary — and it exists for one job: the settling window, so a row is not snatched off the notch in the instant its subagent badge clears. A subagent's `SubagentStop` was measured **91 seconds** past its parent's `Stop` (2026-08-22).

From `dff7d66` (2026-08-23) until this was split out, both products handed `terminalBoundaryAt` to the read tests as well, and the failure is the same sentence on either side: *the user's read was dated earlier than the bar and thrown away*. On Codex the gate demanded an unread file written later than the subagent's stop, which Desktop has no reason to produce — the write recording the user opening the thread happened while the subagent was still going, because that is exactly when the row is on the notch. On Claude Code `readState(forSession:terminalBoundaryAt:)` reported `unread` for a session whose `lastFocusedAt` sat after the `Stop` but before the subagent's finish, and `comingBackShowedIt` and `wereAtItsTerminal` failed the same way. In both cases the row the user had already read came back reported unread and stayed until that product happened to display the session a second time.

`ClaudeCodeDesktopReadStateRepository`'s own documentation had said the right thing throughout — the left half is "the instant the Turn actually ended, from the event that ended it" — and only the call site disagreed with it.

**The window is untouched.** `terminalBoundaryAt` still starts the settling window, so the case `dff7d66` was fixing ("the row vanishes the instant it stops saying anything is running") does not come back; and `TerminalUnreadMembershipGate`'s `endedAgain` now asks the Turn's terminal too, so a late `SubagentStop` no longer un-hides a row already retired.


### 2.1 Product constraints

- A row is a root Thread; a Turn is one processing cycle inside it.
- Monitor every Project and `Chats` under the current Desktop account, without following the sidebar selection.
- An active Turn is always shown; a terminal Turn is shown only while Desktop marks it unread.
- Read, archived, deleted or no longer navigable leaves the list immediately.
- Subagents, exec runs and standalone CLI/IDE sessions are never top-level rows.
- A click must reach exactly the same Desktop Thread; opening the home page is not success.
- Launch shows no cached rows and rebuilds no pre-launch session; the list starts empty and accumulates only Turns producing lifecycle events after launch.
- Previews are always shown (the former global switch is deleted, PRD §7).

### 2.2 Safety constraints

- Use only official, public, supported interfaces whose version capability can be judged; a production exception must be explicitly product-approved, read-only, fail-closed and registered in [`non-public-codex-integration-features.md`](non-public-codex-integration-features.md).
- Never connect to an unsupported private Desktop socket, write a private database, or use Accessibility or GUI automation.
- Never read authentication files or copy Desktop credentials.
- Never start a Turn, resume a Turn, approve, input, cancel, archive or delete.
- Integration configuration is modified only after user confirmation and can be removed from Settings.

### 2.3 UI constraints

- The shared expanded baseline width is `520`; with a `46` menu bar and three session rows the reference total height is `316`.
- The top summary region's reference height is `46` and always equals the target menu-bar height; expanding grows only horizontally.
- The content region below it is the list viewport plus the footer: the viewport is at most `508 × 240` with three rows visible and vertical scrolling, and the footer is `496` wide by its own content plus a `6` bottom margin — `30` in this single-product form. The viewport is two `6`s wider than the footer: the row block is inset only `6`, the row adds `6` back, and in-row text lands at `12` with the footer.
- A healthy empty list and global availability states use a `520 × 124` thin layer, with a `48` body and a `30` footer.
- The footer must be the same height with and without sessions, with no padding appended beneath it beyond the `6` its own height already includes. It is separated at the top by the same hairline as the header and list; the left holds today's token total and the reset copy, and the right a `32 × 32` Settings hit target with a `16 × 16` gear.
- Figma and the product UI both use SF Pro.

## 3. Key release gates

Phase 0 must prove each of these separately rather than inferring them from existing fields:

| Capability | The real value required | Behaviour when missing |
| --- | --- | --- |
| Thread identity | A stable root `threadId` and navigability | Blocks V1 |
| Live Turn status | Start, Input, Approval, Running, Completed | Blocks the live monitor |
| Desktop unread | Membership changes matching the blue dot | Blocks the terminal lifecycle |
| Desktop Project | Project id/name and `Chats` | Blocks Project display; cwd is not a substitute |

| Quota | The current account's primary rate-limit window | Degrades only to a grey unavailable ring |
| Today's tokens | The local today bucket in `account/usage/read.dailyUsageBuckets` | Degrades only to `--`; never extrapolated from lifetime or a quota percentage |
| Current content | The prompt/progress/final the user can see | Hides only the preview |

The official App Server's Thread/Turn/status/quota protocol is the main foundation, but its current public fields do not include Desktop Project or unread membership. A standalone App Server also cannot be assumed to share a runtime with Desktop. Unread and Project use the approved, registered private read-only adapters of §1.3 and §1.4; other internal Desktop resources may be used to understand a problem and may not become production dependencies without separate approval, a fail-closed design and a registry entry.

Processing time introduces no new data source: `startedAt` comes from the `received_at` of the official `UserPromptSubmit` hook, the same event stream the status decision uses, so it adds no non-public dependency (§12).

## 4. Domain data model

`SessionStatus` has no Connected or Disconnected. The two system statuses the collapsed state shows with an empty membership set are derived by `MonitorAggregation.status`: **`Connected` when any product is open with availability ready, `Disconnected` otherwise**. Availability is still `MonitorAvailability`, but it no longer decides the collapsed value alone — "open but out of reach" and "not open" both fall to `Disconnected`.

Presence is `AgentSnapshot.presence` (`AgentPresence`: open / not open / unknown), an independent fact beside availability:

- **Codex**: `NSRunningApplication.runningApplications(withBundleIdentifier:)`, a kernel fact, so never unknown.
- **Claude Code**: `ClaudeCodeSessionListing.presence()`, answered by whether the active session list is non-empty. The list is cached, so only it can report unknown — see §15's trust ceiling.

**Presence and registration health must come from this refresh, on every branch without exception.** Both are measured at the top of `fetchSnapshot`: presence comes from the running-application list and can neither time out nor go stale, and registration health comes from the registrar and never asks the App Server. So a failed request preserves only **observations** (availability, rows, quota), while those two are written from this pass's values — never inherited from a preserved old snapshot, and certainly never left to `AgentSnapshot`'s initialiser defaults of `.open` / `.active`, which would let one `thread/list` timeout paint a Connected marker on a Codex Desktop the user has plainly quit (violating PRD §6.3 and §12) and report a `reviewRequired` in Settings as healthy (CR-Fable-005).

`ClaudeCodeSessionListing`'s two methods answer two different questions and must not be merged: `liveSessions()` answers which sessions exist, and the Turn reducer answers what they are doing. **Presence draws the matrix and the reducer lights it.** A session with no Turn running is still an open Claude Code.

**One exception, and only one: a session says whether it is still working.** Besides identity, `claude agents --json` gives `status` (`busy` / `waiting` / `idle` / `shell`) and `waitingFor` — this document and the code comments both used to say that output was byte-identical whatever the session was doing, and measurement against 2.1.235 on 2026-08-18 proved that wrong. The reading enters `ClaudeCodeSession.activity` and **may do exactly one thing**: end a Turn the reducer already holds open. It carries no Turn identity, so it may never open, name or describe one.

The only reason this path exists is user interrupts. `Esc` fires no hook — the CLI's hook event table has no cancel event and every interrupt path returns before the `Stop` hook runs — and `AGENTS.md` §6.2 forbids inferring business state from a timer, so "the session no longer says it is busy" is the only evidence (CC-019 / #38). Measured on this machine: `busy` within 150 ms of submitting a prompt, `waiting` within 150 ms of an approval dialogue opening (`waitingFor: "permission prompt"`), and **`idle` within 160 ms of pressing `Esc` with the dialogue still open** — the last being exactly the case that leaves a row at *Approval needed* forever.

The rules are in `HookEventRepository.endTurnsForStoppedSessions(_:)`, three of them:

- **Only a positive stop counts.** `busy` and `waiting` mean the session is working (under `waiting` the Turn is alive, merely parked in front of the user, which is the reducer's own state); **an absent field** does nothing — a desktop-hosted session never has it (#41), older CLI versions do not either, and silence is not another way of saying idle.
- **The reading must be entirely later than the Turn's last event**, comparing against the moment the command **started** rather than when it answered. The list is cached for up to 30 seconds and the answer in hand is usually older than events arriving after it; comparing at answer time would let a read spanning a submission report a Turn it never saw as idle.
- **Ending is Completed.** The product has one terminal state, and an interrupted Turn is a Turn that ended.

**The same reading answers another question: is there a dialogue in front of the user.** Claude Code emits no hook when a person **grants** an approval, and the next event after `PermissionRequest` is that call's own `PostToolUse`, which lands when the tool finishes rather than when the dialogue closes. Measured 2026-08-23 on 2.1.241 (a subagent sleeping 12 s, the parent Turn already `Stop`ped): `PermissionRequest` at +6.22 s, the person approving at +9.35 s, `PostToolUse` at +22.72 s — 13.4 seconds of *Approval needed* after the approval. Throughout, the session reports `busy`; while a dialogue is open (including one raised by a **subagent** after the parent Turn's `Stop`) it reports `waiting` / `waitingFor: "permission prompt"`.

The rules are in `HookEventRepository.endAnsweredApprovalWaits(_:)`, four of them:

- **Only `busy` counts, never "not `waiting`".** `idle` does not prove the dialogue is gone — pressing `Esc` with it still open reaches `idle` within 160 ms (CC-019). A session reporting no status again does nothing here.
- **End only, never open.** The reading carries neither Turn identity nor `agent_id`, so it speaks to every approval wait this thread currently holds — the Turn's own and each subagent slot's — and can open none. Input pending is unaffected: it is necessarily closed by its own `PostToolUse`, and with both waits present §6.2 shows Input.
- **The ordering guard is pinned to each wait itself** (`PendingApproval.openedAt`) rather than the Turn's `lastEventAt`: a read that **started** before a dialogue opened cannot have seen it and may not close it. The cost is at most one refresh, and `waiting → busy` rewrites the session record, so that edge already exists.
- **It does not move `lastEventAt`.** This is not the Turn doing anything, and that stamp is membership reconciliation's only constraint.

**A desktop-hosted session does not say this either, and its answer lives in a third place.** Such a session never reports `status` (reason below), so none of the above applies to it — which is the environment the user reproduced the misreport in. First, the more basic thing was measured: registering all **31** hook events from the binary at once on 2026-08-23 against 2.1.241 showed **26 seconds between the approval and `PostToolUse` with no relevant event**, so there is no hook to miss on this path. Desktop writes both ends into its own log, joined by a request id:

```text
18:10:40 Emitted tool permission request c930390d-… for Bash in session local_6c63f909-…
18:10:45 Received permission response for c930390d-…: once (tool: Bash)
```

It is read by `ClaudeDesktopPermissionLogReader` and applied through **the same entry point** as above (both pieces of evidence say one sentence):

- **Only the opening line names a session and only the response line proves a person answered**, so the request id is the only pairing; a response that cannot be paired with an opening line is attributed to no session, failing towards leaving the wait in place. Desktop's id joins to the CLI's through `sessionId ↔ cliSessionId` in Desktop's records, the same source as read state.
- **The decision itself is not read.** Approve, always-allow and deny all equally mean a person answered — which incidentally fixes desktop denials too.
- **Each question holds its own cursor.** The focus reading reads the same file, and a shared offset would let whichever asks first swallow the other's line.
- **It reads, and builds its edge, only while an approval is genuinely open.** The focus reading originally refused to watch this file ("an oauth query would wake it too"), a reason that holds only while nothing is waiting on it; `permissionLogWatcher` therefore points at it only during that period.

See ADR 0011's two 2026-08-23 addenda.

**A desktop-hosted session's interrupt is likewise written elsewhere.** Claude Code's desktop runs the CLI as a `stream-json` subprocess with no terminal interface, and `status` is written by the terminal interface — so such a session's record never has that field, the first rule above does nothing under "silence is not idle", and the row sits at *Running* or *Approval needed* (CC-022 / #41). What it does leave is something else: when Claude Code aborts a Turn it writes a `user` record into the transcript, and that record **names the Turn it aborted**.

The rule is in `ClaudeCodeTranscriptReader.interruption(forSession:workingDirectory:turnID:after:)` and applied in `HookEventRepository.endInterruptedTurns(_:)`:

- **The rule is structural, not textual.** A `user` record whose `message.content` is exactly one `text` block, with no `promptSource` and no `isMeta`. Measured 2026-08-19 across every transcript on this machine — 205 files, 7,438 `user` records — it matched 15 of 15 interrupt records and **nothing else**. CC-019 rejected this route on the grounds that it would mean "either reading message bodies, or a structural rule that cannot separate an interrupt record from a slash-command record"; the rule that can separate them asks one more question about `content`'s shape: all 202 slash-command and `<local-command-stdout>` records write content as **a string** rather than a block array. That question is necessary rather than belt-and-braces — 23 of those 202 had the model still working on the same `promptId` afterwards, and without it those running Turns would be retired, the one direction that must never be wrong.
- **It names a Turn and is therefore pinned to it.** The record's `promptId` is the hook's `prompt_id`, which is the reducer's Turn identity (measured on 2.1.237: `UserPromptSubmit` and the interrupt record carry the same id). Naming a Turn the reducer does not hold does nothing. This also makes "an interrupt record differs from a real prompt by one `promptSource`" safe: a prompt opens a **new** Turn id, so even a version that stopped writing `promptSource` could not end the Turn it just opened.
- **The ordering guard has the same source and is sharper.** It compares against the moment the record was **written** (records carry an RFC 3339 timestamp), not when this app read it.
- **Not one character of body text is read.** The decoding structure has no text field, the same approach as `AgentHookListener`'s decoder; only the transcript's last 64 KiB is read, cached on `(size, mtime)` and dropped when the session goes.
- **Only the sessions that need asking are asked.** Only a session that reports no status and currently holds an unfinished Turn is asked — a session that reports for itself is answered by its own answer, and a file read nobody is waiting on is not worth doing.

That edge must also be built: an interrupt does not rewrite `~/.claude/sessions/<pid>.json` (there is no status in that record to flip), so `ClaudeCodeSessionRecordWatcher` cannot see it. `ClaudeCodeMonitorService.transcriptWatcher` therefore watches those sessions' transcripts by file (`PathSetChangeWatcher`, the same reasoning as the record watcher: appending fires no directory-level event). It does **not** mark the session list stale — the one difference from a record edge: this edge says "a file this app reads itself has changed", and the answer comes from a 64 KiB tail read rather than a `claude` launch.

`TurnEvidence` is the in-memory reducer truth and is never persisted directly. A Turn begins at Running; Input needed and Approval needed only temporarily override Running on the same active Turn, awaiting a resuming signal back to Running; and any trustworthy execution-finished signal enters the irreversible Completed. A missing, timed-out or unknown signal creates no fifth status and keeps the last trustworthy value.

## 7. Integration lifecycle

### 7.1 First install

1. Detect whether Codex Desktop exists and read its version.
2. Show Welcome, changing no system state.
3. State which local metadata will be read, what is not persisted, and that it is reversible.
4. Install and register only after the user presses `Set Up Integration`.
5. Respect Codex's trust and review mechanism for local hooks and integrations, never bypassing it.
6. Complete capability detection; show Ready only once every required capability passes.
7. `Start Monitoring` enters connecting and rebuilds from an empty set.

The installer must record the minimum configuration fragment it manages and never overwrite the user's other configuration.

**Rewriting any definition costs it its trust, so a definition is never rewritten once written** ([ADR 0014](adr/0014-the-codex-hook-definition-is-never-rewritten.md)). Codex records trust by hashing definition content under `[hooks.state."<hooks.json path>:<event>:<group>:<handler>"]` in `config.toml`; change the content and Codex **silently stops executing that definition** until the user trusts it again via `/hooks`. Every untouched definition keeps its hash and keeps firing, so nothing looks wrong from the app side — delivery evidence is satisfied by those, and the UI keeps showing connected. Measured 2026-08-15, `PreToolUse` did not fire for two consecutive Turns with no indication at all.

So versioning moves entirely into the **script** (which is not hashed) and the definition carries only a stable path:

```json
{"type": "command", "command": "/bin/sh '<support>/agents/codex/hook.sh'", "timeout": 3}
```

The registered events are `UserPromptSubmit`, `PermissionRequest`, `SubagentStart`, `SubagentStop`, `PreToolUse`, `PostToolUse` and `Stop`, all without a matcher. `SubagentStart` and `SubagentStop` are the most recent additions, for the reason in §9.2's subagent passage: they are the only events that can answer whether work is still in flight after a Thread's own Turn ended. `SessionEnd` is no longer registered: it reduces to nothing while costing a process launch per session end and one more definition for the user to trust, and rows for vanished sessions are retired by App Server membership correction. `PreToolUse`/`PostToolUse` stay catch-all — narrowing them to `^(request_user_input|request_permissions)$` would cut about 90% of the event volume, but an ordinary tool's approval is a `PermissionRequest` carrying `tool_name` and no `tool_use_id`, which can only attach to the id a catch-all `PreToolUse` just announced, and inferring a refusal additionally requires seeing activity on **other** calls. The answer to event volume is a cheaper helper, not a matcher.

**`PermissionRequest`'s definition is the one exception, and the only one on either product.** It registers `timeout: 3600` on Codex and `86400` on Claude Code, and hands the helper the literal `wait`, which selects a `nc -w` window a person can answer inside instead of the `-w 1` every other event keeps. That is what makes the hook's own stdout a reply channel: the connection stays open for the length of a human decision, and the app writes that product's hook-output JSON back onto it ([ADR 0019](adr/0019-the-helper-answers-on-the-stream-adr-0013-silenced.md)). The timeout and the argument live on `ManagedHookDefinition` rather than on the configuration, so a definition that varies neither produces the bytes it always produced — which on Codex is the difference between one re-trust and seven ([ADR 0014](adr/0014-the-codex-hook-definition-is-never-rewritten.md), amended). `PreToolUse` is deliberately not a second such definition: it fires on every tool call, so a window a person could answer inside would be a window every tool call waits in. Codex's `PreToolUse(request_permissions)` — a Desktop approval, which sends no `PermissionRequest` at all — is therefore read here and answered in the product.

**The descriptor is handed over, never held on the read queue.** `AgentHookListener` gives `deliver` the descriptor along with the bytes and closes it only if nobody took it; `HookEventRepository` takes it for the answering event and hands it straight to `HookReplyRegistry`, which is lock-protected rather than actor-isolated for the same reason the preview store is. Holding it on the serial read queue would park every subsequent event from that product for the length of a human decision. The registry also keeps that request's `tool_input`, because answering a question means handing the tool back its own input with the answers merged in — so those bytes live exactly as long as the connection and never reach the snapshot or the view.

**Letting go is a reconciliation, not a release.** After every drain the registry is told which tickets the reducer's waits still name and closes the rest, so a wait cleared by any of its seven paths — the paired close, the inferred resolution, the turn ending, a session going away, a reading that says the dialog was answered elsewhere, a subagent stopping, a turn boundary — releases its connection without any of them knowing one exists. `AgentRequest.canBeAnswered` is `replyTicket != nil` and nothing else, so what the row offers and what the app can deliver cannot disagree. `RequestAnswering` is one provider per product: both spell an approval identically, and only Claude Code accepts a question's answers through `updatedInput`.

**The surface reaches that channel through one method and never sees a key name.** `AgentMonitoring.answer(_:on:)` takes an `AgentAnswer` and the ticket its request arrived on, and returns whether the whole answer reached the peer; the two live services forward it to their repository, and the protocol's default answers *not delivered*, so a store with no services, a drawing specimen and a test double are all truthful without a stub. `false` is an ordinary outcome — the product may have been answered in its own window and killed the hook process, which is discovered only when the write fails — and it is [`answer-in-notch.md`](answer-in-notch.md) §8's *not delivered*: the row closes, keeps what was typed, and says so on its preview line.

**What the store holds while a row is open** is `MonitorStore.answerProgress`, keyed by row and living exactly as long as that row: which question of a set is showing, how far the set has been walked, and — **per question rather than per row** — that question's field text, ticked options and expanded descriptions ([`answer-in-notch.md`](answer-in-notch.md) §5.7). It is deliberately **not** `@Published` — the field is an AppKit text view that owns its own string, and a keystroke is not a layout change (`AGENTS.md` §7). **Two kinds of key reach past the field**, both on the same condition and for the same reason. A bare `1`–`4` is offered to `MonitorStore.takeNumberedOption(_:)`, which takes that option only while the white ground is still on one and an empty field says nothing has been typed, and returns whether it did so the field can type the digit when it did not (§9.2, §15 q08). A bare `←` or `→` is offered to `MonitorStore.takeQuestionStep(_:)`, which walks the set only while the field is empty and returns whether it did so the text system can move the caret when it did not — offered from the delegate's command table rather than read off the event, because `moveLeft:` arrives only for an unmodified arrow. What is published is where the white ground is (`answerGround`, derived from what has been typed rather than stored beside it), whether an answer is in flight, whether the affirmative has finished arriving, and two counters: `answerRevision` for a drawn change the row's identity cannot express — the next question of a set, a tick — and `answerDraftGeneration` for the two moments the store itself replaces the field's text, which is the only thing that may refill it under somebody's hands.

Installation health requires exactly one current handler for each registered definition, with the command and the timeout matching that definition's exactly and the group carrying no matcher; any subset, a duplicate definition, or an altered field must fail closed to `mismatched` (shown on the card as `repairRequired`) rather than Ready.

> The count is deliberately not restated in prose anywhere in this file — it has read five, six and seven at various points. Count `managedDefinitions` in `HookIntegration.swift`.

Two merge rules, both justified by the measured shape of the trust key — 2026-08-20 this machine held `[hooks.state."…/hooks.json:pre_tool_use:0:0"]`, whose third segment is the group's **index** in the array:

1. **Append at the tail only, remove from the tail only.** Removing a group from the middle renumbers every group after it, so **the user's own** definitions silently lose trust.
2. **An already correct installation writes nothing.** `install()` returns immediately on `complete`, neither rewriting nor reordering a file that is already correct.

The reducer additionally uses "`PostToolUse` seen without `PreToolUse`" as a run-time probe for lost trust and emits a diagnostic. With definitions frozen this app can no longer reach that state itself, and the probe is left for the cases it cannot create: a user editing `config.toml` by hand, or a Codex update re-hashing. Removal removes only the fragment this app manages.

### 7.2 Launch and reconnect

```text
launch
→ ignore SIGPIPE
→ bind hook.sock; write hook.sh if its bytes differ from the bundled one
→ read install.json (lastEventAt only); initialize an empty in-memory reducer
→ compute registration once from ~/.codex/hooks.json
→ Connecting (≤ 5s)
→ capability handshake
→ reconcile active + unread terminal membership
→ subscribe events
→ ready
```

A connection succeeding within five seconds shows no intermediate error; after a timeout it enters Update required, Version unsupported or Disconnected by cause. Codex is never launched automatically when it is not running.

**The first thing launch does is ignore `SIGPIPE`.** The only pipe this process writes to is the `codex app-server` subprocess's stdin, and the moment that subprocess goes (a crash, a force quit, a Codex update replacing the executable) its read end closes. `SIGPIPE`'s default disposition is to **terminate the process**, and it is delivered synchronously to the thread issuing the `write(2)`, so the throwing `FileHandle.write(contentsOf:)` never gets to see `EPIPE`. Between the subprocess disappearing and the termination handler reaching the actor and nilling the write handle, any request that arrives — the background metadata loop, a quota read, a watcher-triggered refresh — writes into that broken pipe and Notchline vanishes on the spot, leaving the user neither a diagnostic nor a usable crash report (CR-Fable-006). Ignored, the write fails with `EPIPE` and falls back to the existing `disconnected` reconnect path.

The disposition belongs to the **process** rather than the transport, so it is installed in `NotchlineApp.init()`: earlier than SwiftUI building the store (and therefore than the App Server transport starting) and earlier than `applicationDidFinishLaunching(_:)`. Writes to the hook socket in the test suite are the same class of risk, and the `SO_NOSIGPIPE` used there is a per-descriptor remedy that does not apply to pipes.

**Helper upgrades happen only at launch and install, never on the refresh path.** The installer compares the on-disk helper with this version's bundled string and overwrites when they differ; `hooks.json` is untouched to the byte and the user need not re-trust ([ADR 0014](adr/0014-the-codex-hook-definition-is-never-rewritten.md)). **There is no install marker**: it existed only to separate "an old helper this app installed, upgrade it" from "a file this app never installed, do not silently replace it", and that distinction is not worth a file — the treatment is the same either way, write the current script. It also never provided tamper resistance, as the old code's own comment admitted: whatever can change the script can change the marker beside it.

This once hung off **every refresh** (`upgradeManagedHookIfNeeded()` reading about 4 KB of script for a string comparison) to answer a question that changes only when this app upgrades itself.

**Registration completeness is likewise not recomputed on a cadence.** It changes at exactly three moments: this app writes `hooks.json`, the user asks for a re-check, or that file changes under us (an FSEvents edge). The first two invalidate the cache directly; the third **is not subscribed to** — the same edge wakes the registrar and the refresh, the scheduler decides which runs first, and if the refresh runs first it reads the pre-change cache and leaves it there, with no second edge to correct it (CR-028). Instead, reads compare `DirectoryChangeWatcher.changeCount`: the count increments **before** the edge is delivered, and the cached reading is stored with its count, so order no longer decides the answer. Attaching also counts once — nobody was watching while it could not attach, and a conclusion drawn then should not outlive a successful attach (which is the case on first run, when `hooks.json` does not yet exist). `installationRevalidationInterval`, the cache scan and `hasManagedSupportFootprint` were deleted with it.

Install and remove both **fail closed** on the user's `hooks.json`, enforced by [`ManagedHooksConfiguration`](../Notchline/Notchline/ManagedHooksConfiguration.swift), with three rules only:

1. **Change only the event keys this app manages**, preserving every other key, unknown field and custom key inside a group.
2. **Never change a structure it cannot read.** Only when a key that **must** be written is already such a structure does it refuse wholesale with a visible error, because writing there would overwrite the user's content. An unrelated event with an odd structure is skipped rather than treated as an error, or the user could never uninstall cleanly.
3. **Removal additionally does a full-document deep scan** confirming none of this app's commands survive in a shape it cannot change. If any does it refuses, and **does not delete the helper** — deleting it would leave a dangling reference in the user's configuration.

There is a guard on each side of a write: before writing, the file's bytes are compared against what was read (avoiding mutual overwrites with a concurrent Codex `/hooks` write); after writing, it re-reads and verifies that every managed definition is present, or removed. With no change it does not write at all, so the user's formatting is never reordered pointlessly.

**No content hash is recorded here.** The `managedHookSHA256` that once existed sat in the same directory with the same owner and permissions as the helper, so whatever could rewrite the helper could rewrite the hash, and it provided no tamper resistance; and `repairRequired` does not deregister the helper from `hooks.json`, so Codex would go on executing it. In other words, faced with a replaced helper, automatically upgrading back to the bundled version removes foreign code faster than flagging `repairRequired`. A missing definition, an inexact definition structure, or a helper present with no install record (this app has no record of installing it, so its origin is unknown) still fail closed to `repairRequired`; the Settings master switch shows Off and repair happens only when the user explicitly switches it on again. This means an app upgrade need not have an unchanged, trusted helper re-accepted; but a complete registration set and historical trust cannot by themselves put the runtime into Ready. Only when a current-state source confirms the set really is empty may "nothing is working" be inferred from an empty set. The same rule constrains presence symmetrically: only genuinely reading an empty session list counts as "not open", and being unable to read it is **unknown**, which falls to `Disconnected`.

### 7.3 When the set is corrected

- On the first successful connection.
- On observer reconnect.
- On waking the Mac from sleep.
- On an account switch.
- On an unread, archive, delete or Project event that could affect membership.
- Every 30 seconds as a low-frequency safety correction covering missed events — **only while the hook reducer still holds a Turn**: the membership set's consumers are all on the live-hook branch, so with no Turn it neither books this deadline nor re-reads (CR-Fable-023). When a hook names a thread not yet listed, one background correction is scheduled immediately, but hook status must not wait for it and the full history must not be scanned per second. Background requests merge into a single in-flight task, with at least 60 seconds before a retry after a failure; when hook observation is lost, outstanding membership and metadata requests are discarded along with their backoff markers — only the live-hook branch can pick them up, and keeping them is a wake-up reason nobody can clear.
- Before a click, a target-level lightweight correction: one `thread/read` for the clicked Thread only, never a full pagination of the membership set ([ADR 0018](adr/0018-the-click-asks-about-one-thread.md)).

## 8. The membership algorithm

For each root Thread, take the current active Turn; with none, take the most recent terminal Turn Desktop marks unread. It enters the set only when all of:

```text
isRoot
AND isNavigableInDesktop
AND !isArchived
AND !isDeleted
AND (turn.isActive OR (turn.isTerminal AND thread.isUnread))
```

Set-diff rules:

- `added`: read a minimal Thread/Turn/Project snapshot and build a row.
- `updated`: locate by exact `threadId + turnId` first, then merge by `revision` or a stable event sequence; an old Turn's events and unassociable results can never overwrite the current Turn.
- `removed`: delete from the repository immediately.
- `thread/closed`: means only a runtime close and never maps directly to removed.

A restart reads neither this app's old list nor old reducer Turns, and runs the same correction from an empty set. That no longer needs a check to hold it: hook events do not touch disk, so the next launch has nothing that could restore a terminal boundary, create a Turn or modify current state ([ADR 0015](adr/0015-hook-events-go-straight-into-the-reducer.md)). All that remains on disk is `install.json`'s `lastEventAt`, which establishes only hook-configuration health.

## 9. The status reducer

### 9.1 Mapping

| Signal | Product status |
| --- | --- |
| Awaiting user input, active flag / request | Input needed |
| A fresh `waitingOnApproval` active flag | Approval needed |
| Turn active with no pending request | Running |
| `Stop`, or terminal `completed` / `failed` / `interrupted` | Completed |

The state machine permits only: `Running ↔ Input needed`, `Running ↔ Approval needed`, `Approval needed → Input needed`, `Running → Completed`. Running is the entry point and Completed the irreversible terminal; with no legitimate new signal the status stands. Reaching a terminal state clears that Turn's pending requests, and an old Turn's late events cannot change a new Turn.

`Approval needed → Input needed` is the only wait-to-wait transition that skips Running, and it exists for §9.2's last rule: a refused borrowed-id wait never receives a closing event, and the `PreToolUse(request_user_input)` that follows is both evidence a person has answered and the new wait itself. Without that transition, `resolveInferredApproval` clears the pending approval while the row still reads Approval needed — and since aggregation puts Input before Approval per §6.2, the collapsed state would even under-report urgency (CR-Fable-009). The reverse does not hold: Input pending is necessarily closed by its own `PostToolUse` and cannot linger, and with both waits present §6.2 shows Input.

### 9.2 Identity admission and request pairing

- Every hook that changes Turn status must carry a non-empty `session_id` and `turn_id` (Claude Code spells the latter `prompt_id`, and field selection merges them in `HookPayload`). It must never fall back to the current Turn, `"unknown"`, temporal proximity or Thread update time; a payload lacking identity writes a diagnostic and is dropped — there is nowhere to quarantine it to, which is why `.invalid` files no longer accumulate (155 had once collected here). **The "writes a diagnostic" half must genuinely reach someone**: unreadable payloads (a connection delivering not one byte included) and readable-but-unfittable events are counted separately, accumulated for the run, and composed with the "registered but not firing" probe into one sentence that reaches that product's row in Settings through `AgentSnapshot.diagnostic`. Reporting once and clearing is the same as not reporting — the user opens that window because something looked wrong (CR-029). **An over-long identity is the same as a missing one**: text may be truncated and identity may not — half a `session_id` is a different session — so an identity field over `HookPayloadDistiller.maximumIdentityBytes` (1 KiB) is dropped entirely and the payload with it (CR-030).
- With no such Thread in the repository, a supported event may establish a Turn from its own exact identity. With a current Turn present, a `UserPromptSubmit` that updates in order and has never been retired **or held back** by that Thread may establish the next Turn; and a later live `PermissionRequest`, `PreToolUse`, `PostToolUse` or `Stop` may also take over the same Thread with a new `turn_id` that is neither retired nor held — which is what recovers a Thread whose `UserPromptSubmit` this app never saw, because it launched mid-Turn or the reducer was emptied under it. On takeover the old Turn id immediately enters `retiredTurnIDs`, the original start time and prompt preview are kept, and old wait evidence is cleared; the event itself then decides Running, Input needed or Completed. A late event for any retired Turn can never revive the old identity. **`heldTurnIDs` is the one addition to that gate, and the next rule is why it exists.**
- **A Thread has one agent and one open Turn: an open Turn cannot be displaced by a `UserPromptSubmit` with another `turn_id`.** The takeover rule above originally applied to `UserPromptSubmit` too, and Codex's `--approve-for-me` reviewer walks straight into it: it is a nested agent with a rollout of its own whose `session_meta.session_id` is the **parent Thread** and whose `turn_id` is **its own**, while its `UserPromptSubmit` **carries no `agent_id`** — so the next rule's `agent_id` gate does not stop it. Taken as the same Thread's next Turn, the real Turn id enters `retiredTurnIDs` at once and the main agent's own `Stop` is then dropped as a late event for a retired Turn: the row sits at Running forever, the timer restarts from the reviewer's prompt, and the reviewer's instructions become the row's preview. Reproduced end to end on a Release build 2026-08-24 (driving that one `UserPromptSubmit` into the real socket produced all three symptoms at once).
  **It cannot displace, but it is not lost either: that prompt is held (`HookTurnState.heldTurnStart`) until something says whose Turn it is.**

  **What redeems it used to be "any event arrives under that `turn_id`", and that was not evidence (2026-08-31).** The sentence that test stood in for is *this Turn is this Thread's after all*, and a nested agent's own events arrive under its own `turn_id` exactly as a resumed Turn's do — so the test was satisfied word for word by the one caller it was written to exclude. It held only while the reviewer emitted nothing but its prompt, which is what the 2026-08-24 measurement found (CLI `0.149.0-alpha.4.3`, isolated `CODEX_HOME`, once via `codex exec --approve-for-me` and once via `codex app-server`'s `approvalsReviewer: auto_review` with Desktop's own `features.code_mode_host=true`: both runs produced only the parent Turn's own nine events). A reviewer that runs **one read-only check** — which its own base instructions permit, *"You may use read-only tool checks to gather any additional context you need"* — supplies the redeeming event and walks straight back into the takeover above. Reported 2026-08-31: a row that said `Working...` for ever whose preview read *"The following is the Codex agent history added since your last approval assessment"*, could not be right-clicked away because dismissal was for finished rows only, and went away only when the app was restarted.

  **The reviewer's prompt is not one prompt.** One guardian thread runs a **fresh Turn per approval assessment** — measured 2026-08-31 over 83 guardian rollouts and 1 970 Turns on this machine (CLI `0.151.0-alpha.7.2`, `thread_source: "guardian_review"`), up to 8 per parent Turn. Turn 1 opens *"…whose request action you are assessing"* and Turns 2…N open *"…added since your last approval assessment. Continue the same review conversation."* So the refusal is a **set** (`HookTurnState.heldTurnIDs`) rather than the one candidate slot: an event under the reviewer's first Turn arriving while its third is the candidate must be refused too, and the set is carried across Turn boundaries exactly like `retiredTurnIDs`, bounded by the same thing — the Thread leaving the repository.

  **Redemption is now the Thread's own record**: a `turn_context` in **this Thread's** rollout naming that Turn, read by `CodexRolloutTurnAbortReader.turnOnRecord(inRolloutAt:)` and applied by `HookEventRepository.adoptTurnsOnRecord(_:)` from the same refresh sweep that reads that file for aborts — one cached tail read answering both halves of ADR 0011, *which Turn is this Thread on* and *is it over*. A nested agent's Turns are written to a rollout of **its own**, so this Thread's record never names one, and **no reading has to say "no"**: silence is the refusal, so an unreadable file, a missing path, or a Turn that has appended more than the 64 KB tail holds all leave the prompt held, which is the safe direction. The two guards on promotion are that the Thread is already holding that exact start, and the same monotonic rule every other route obeys.

  **Codex only, because the caller is (`AgentHookVocabulary.settlesHeldTurnsFromRecord`).** Claude Code has nothing that runs under a Thread's identity without saying so — its subagents stamp `agent_id`, and the read-only fork Claude Desktop opens fires no hook at all (`CONTEXT.md`, *Side chat*) — and no rollout to ask instead. So a held prompt there is the user's own next Turn, and it has exactly one case: **a human refusing an approval aborts that Turn with no hook whatsoever** (measured 2026-08-23, CLI `2.1.241`, twice), leaving it open with the next prompt held behind it. On that product the first event under the held id still redeems it, as it did on both before Codex's reviewer proved that test worthless on Codex.

  **What this does not close.** A prompt arriving when the reducer holds *nothing at all* for that Thread still establishes a Turn outright, so a reviewer's prompt landing in the window after a launch or a `discardTurns` can still open a phantom — recovered by the real Turn's own next event, which may take that Thread over because it was never held. And right-click dismissal now works in every state (§17), which is the general answer to a row that should not be there.
  **This rule is necessary rather than incidental for "the user speaks again after an interrupt"**: Codex sends no terminal state for an interrupted Turn — measured 2026-08-24, and again 2026-08-29 on CLI `0.151.0-alpha.7.1`, after `turn/interrupt` there is neither a `Stop` nor even the `PostToolUse` for the call still open — so no *hook* ends an interrupted Turn, and the user's next prompt is exactly the one held, recovering its own start time and text by redemption. **The rollout does end it** (§9.5, [ADR 0011](adr/0011-a-turn-may-end-on-evidence-that-is-not-a-hook-event.md)), and that does not weaken this rule: the abort is read on a refresh and may be late, may find no path yet, or may find the rollout already moved by an archive, so the user speaking again must still land on the held prompt rather than on a takeover that retires the Turn.
  **The test is "the previous Turn has not ended", not "the previous Turn is parked on an approval"**, even though the reviewer during an approval is the only thing that reaches here today: what must be guarded is the identity rule itself rather than the one known violator, or Codex's next nested agent will require widening it again. Writing the held record does not advance `lastEventAt`, for the same reason as `reduceSubagentToolEvent` — that is not this Turn's activity and must not be used to fend off membership reconciliation.
- **An event carrying `agent_id` does not describe this Thread's Turn, so it takes that subagent's own slot rather than the Turn's** (`AgentWaitSlots`, indexed by `agent_id`, held on `HookTurnState.subagentSlots`). That path **never touches Turn identity**: it does not enter `mutateExactTurn`, does not read `turn_id`, does not advance `lastEventAt`, and does not advance `lastSubagentBoundaryAt`. It recognises the same five signals as a Turn (`toolCallOpened` / `inputWaitOpened` / `approvalWaitOpened` / `approvalWaitInferred` / `toolCallClosed`), and a `UserPromptSubmit`/`Stop` carrying `agent_id` is still discarded.
  **Why separate slots rather than sharing the Turn's.** Codex stamps a subagent's hooks with the **parent Thread's `session_id`** and the **subagent's own `turn_id`** (measured 2026-08-22 and 2026-08-23: a subagent rollout's `session_meta.session_id` is the parent Thread, and `agent_id` is its own thread id). The takeover rule above would take a subagent's first `PreToolUse` as a new Turn on the same Thread, retiring the real Turn id at once, after which the main agent's own `Stop` is dropped as a late event for a retired Turn — and nothing can then end the Turn that remains. Claude Code stamps with the **parent Thread's `session_id` and the parent Turn's `prompt_id`** (measured 2026-08-23, CLI `2.1.241`: `agent_id` is on the base schema every hook input inherits), so the takeover defect cannot arise, but something else does: `openToolUse` and `pendingApproval` are one slot each on the Turn, and a subagent's calls are a second stream through them — its `PreToolUse` would displace the main agent's still-open call and its `PostToolUse` would close the main agent's approval. Separate slots remove both faults, and both products use the same code.
  **These events were previously discarded in pairs, at the cost of the very reason this product exists.** A subagent's own `PermissionRequest` could not reach the row, so the row drew Running or a subagent badge while the product was in fact stopped at a dialogue. Measured 2026-08-23, the arrival shape is identical on both products: `PreToolUse` with a `tool_use_id`, then 20–30 ms later a `PermissionRequest` with `tool_name` and no `tool_use_id` (Codex `0.149.0-alpha.4.1` and Claude Code `2.1.241`). **The lost-trust probe still counts in pairs**: a subagent's open and close both enter §7.1's two counters, and counting only one half would misfire.
  **This slot closes on three rules plus a cap**: (1) a closing event on the same `(agent_id, tool_use_id)` (an approval, and Claude Code's automatic-mode classifier refusing); (2) activity on **another** call by the same agent (a human refusal — neither product emits anything, see the borrowed-id rule below); (3) that agent's `SubagentStop` deletes the slot outright; and (4) the drawn flag recognises only agents in `runningSubagentIDs` (`HookTurnState.subagentsAwaitingApproval`), because both products stamp `agent_id` on agents that **never announced themselves** — Claude Code's is the TUI's own background agent, and Codex's is the `--approve-for-me` reviewer (a nested agent with its own rollout and no `SubagentStart`, measured 2026-08-23). The cap also guarantees the flag **cannot outlive the count**.

- **The same rule governs `MessageDisplay` folding.** That path diverts inside `deliver` and never reaches the reducer's gate, and what it writes is text the user sees — what a subagent says is not this row's answer. This follows from the schema rather than measurement: two `-p` runs (2026-08-23, CLI `2.1.241`) saw only the main thread emit `MessageDisplay`, but `-p` does not display subagent text anyway, and `agent_id` is on the base schema.
- **After row composition there is one more place the reader is rewritten: the gate asks whether this Thread is still working.** Both `LiveCodexMonitorService` and `ClaudeCodeMonitorService` hand `MonitorAggregation.effectiveStatus(of:)` rather than the row's own status to `TerminalUnreadMembershipGate` (the Claude Code side's four read paths read the same derived answer), with the settling window's boundary likewise taken from `HookTurnState.terminalBoundaryAt`, and the Turn's own end — which dates every read test — taken from `HookTurnState.turnEndedAt` (`CONTEXT.md`'s derived status). A terminal row with a subagent still running therefore takes the non-terminal path — shown as usual, its entry dropped, no per-second re-check booked — exactly like a Running row; once the last subagent wraps up it becomes terminal again and the window counts from that moment. The same derived answer is what `MonitorAggregation.status` and `rowOrder` read (`PRD.md` §6.2), **and it never enters a row's rendering**: that would restart the timer and stop it ever reaching the final answer, the defect `65e63ab` fixed.
  **The derived answer has three clauses, the second beating the first and the third beside it.** While one of this Thread's subagents is stopped at an approval dialogue (`MonitoredSession.subagentsAwaitingApproval`), the derived status is `approvalNeeded` rather than `running`, whether or not the Turn is terminal — measured in both orders. It does not beat the Turn's own `inputNeeded` (§6.2's priority, and `SessionStatus.transitioned`'s "approval yields to input"). On the Codex side that flag passes one more gate: a subagent inherits the parent thread's `approvals_reviewer` (measured 2026-08-23, all 72 subagents of 119 rollouts here whose parent was also on disk agreed, with both values represented), so on an `auto_review` thread a subagent's approval likewise reaches nobody, and `LiveCodexMonitorService` subtracts it with the same `approvalsReachTheUser(threadID)` the row uses. **The row's rendering reads it in exactly one place**: the brightness of the row-end cell (`PRD.md` §9.3), which does not change what the row draws.
  **The third clause is Claude Code only and governs the instant between a subagent wrapping up and the parent Turn waking.** `SubagentStop` empties `runningSubagentIDs`, and Claude Code immediately wakes the parent Turn under a `prompt_id` of its own — measured 2026-08-23 (CLI `2.1.241`) at 50 ms in a pty session and 130 ms under `-p`. A row reading the count alone would write `Completed` and then `Running` back in that instant. That Turn's `Stop` had already said which kind of terminal it was: `background_tasks` is officially described as letting a hook distinguish "the session ended" from "the session is paused waiting for background work to wake it", an empty array when nothing is in flight — so the reducer records it on `turnEnded` as `HookTurnState.pausedForBackgroundWork` (`MonitoredSession.isPausedForBackgroundWork`), and `effectiveStatus` reads it beside the count. **It is a Turn-level fact rather than a Thread-level one** — unlike the two Thread-level sets above: it is written by that Turn's own terminal state and so may not outlive that Turn, with the next Turn's terminal state answering for itself (that one being an empty list, so the row goes Completed). It is an assignment rather than an or, so a Turn pausing twice takes the last. Codex does not send this field, where it is permanently false and this clause is the identity transform. There is also **no timer involved** (`AGENTS.md` §6.2): one event writes it and another clears it, and if the field disappears it reverts to the old behaviour — one more flash, fabricating no state.
  It is read only on `Stop`, never on `SubagentStop`: the latter carries the list too, but still lists the subagent that is stopping (measured twice, 2026-08-23), so it is not an absolute reading of what remains. The list itself is `HookPayloadDistiller`'s third carried kind (`HookPayload.CarriedValue.list`): kept whole or not at all, never truncated like text — half a list is not JSON, and "how many remain" is the entire reading; the `maximumListBytes` ceiling is 16 KB, past which the field is dropped, at the cost of that row entering Completed one instant early rather than the whole event being lost.

- **The request a person is being asked, on the events that ask them.** `tool_input` is the fourth carried kind (`HookPayload.CarriedValue.request`), and it is the only one whose rule is about the *event* rather than the key. Both products put it on `PostToolUse` as well, describing a call already run and behind which sits the tool result this whole selection exists to step over — so carrying it by key would put the hottest event's variable size straight back on the read queue (CR-030). The gate is `AgentHookVocabulary.carriesRequest(forEvent:toolName:)`, **derived from each product's own signal table rather than listed a second time**: an event that opens a wait carries its request and no other event does, which makes `PostToolUse` refused by construction. Measured 2026-09-05 over 30,909 tool calls under `~/.claude/projects`, that admits 56 of them — 0.18% — where "`PermissionRequest` and `PreToolUse`" would have admitted all of them and copied about 28 MB.

  **A second key joined it on 2026-09-06**: `permission_suggestions`, the persistent rules Claude Code offers to write if the request is granted. It is inside the same gate rather than beside it — it arrives only on a `PermissionRequest`, which the gate already admits — so it can never widen what any other event carries. Two `.request` keys made the distiller's *hold* per key rather than a single slot re-emitted under a hard-coded name: Claude Code's keys arrive alphabetically, so `permission_suggestions` would have won that slot on every payload and been decoded as `tool_input` — a rule list drawn as the command a person is being asked to approve. The emit order is read off `CodingKeys` rather than off the holding dictionary, because a `Dictionary` iterates differently between instances holding equal values and the projection compares rendered strings.

  Kept **whole or left out** for the same reason a list is: half an object is not JSON. `maximumRequestBytes` is 128 KiB — 2.4× the largest `ExitPlanMode` plan measured on this machine (54,411 bytes) and above 99.997% of that corpus — and deliberately eight times `maximumTextBytes`, which is affordable only because of the gate. Mechanically, the scan cannot decide when it reaches the key, because neither `hook_event_name` nor `tool_name` is promised to precede it and on Claude Code neither ever does; the value is **held as a range into bytes already in hand** and emitted after the loop, so a refused request costs no copy, no decode and no second pass. Where the key arrives twice the **first** wins, which is what `JSONDecoder` does with a repeated key.

- **The request is read into its drawn form inside the reducer**, by `AgentHookVocabulary.request(forEvent:toolName:toolInput:permissionSuggestions:openedBy:)`, and never in the view (`AGENTS.md` §6) nor on `HookPayload` (which would put both products' tool names into a product-free type) nor in the two row builders (where the mapping would be written twice). `AgentRequest` carries the wait's id — the **borrowed** one on a `PermissionRequest`, neither product putting a `tool_use_id` on that event — the tool's name, and one of five forms: a command, a document, a question set, a bare question, and the `Elicitation` this app declines to draw (`answer-in-notch.md` §2.2). For approvals, `argumentFields: [ApprovalArgument]` also preserves each key, label, rendered value and typography role, projected from `JSONValue` at this boundary. Keys are sorted so equal inputs have equal projections. Nested values retain sorted JSON structure; unfamiliar and empty fields are preserved. The command string remains a compatibility reading for plain-command callers, and the view never parses it. `RequestBodyLayout` wraps each field using its actual font and measures label, value and inset heights; `RequestBodyView` draws those same lines (`answer-in-notch.md` §4.2). A sole `command`/`cmd` field or bare-string approval uses the original machine-text body without a label. Question and document forms retain their existing layout.

  It also carries `offeredRules`: the persistent rules that product offered to write, parsed from `permission_suggestions` into `PermissionRuleOffer` — a transcription of Claude Code's `PermissionUpdate` union, which is also the type its `allow` decision accepts back as `updatedPermissions`. **Read and drawn nowhere** ([`answer-in-notch.md`](answer-in-notch.md) §6.5): `AgentAnswer` has no case for it and a grant from the notch writes no rule. Empty is a statement rather than a gap — that product sends either a suggestion or `suppressAlwaysAllowRule` and never both — and one member the parse cannot read empties the whole list, because the members are alternatives within one grant and keeping the readable ones would describe a narrower grant while looking complete. Codex takes the argument and does not read it: it documents `updatedPermissions` reserved and fails the hook closed on it.

- **The request lives on the wait, not beside it.** `PendingApproval.request` and `PendingInput.request`, so that all seven places already clearing a wait clear the request with them and there is no eighth site to forget — the alternative, a table keyed by `(agent_id, tool_use_id)`, is exactly the shape CR-030 turned out to be. `HookTurnState.requestAwaitingAnAnswer` chooses the one request a row can open, in the order `PRD.md` §6.2 already reads and taking the **oldest** waiting subagent, because a row is `agent:threadID:turnID` and a subagent has no row of its own. A subagent's *question* is tracked and deliberately not offered, exactly as its count is not drawn. It reaches the UI as `MonitoredSession.request` on the one data contract, and `renderedProjection()` carries that request's id and form name — never its body.
- `PreToolUse(request_user_input)` establishes Input pending only when it carries a non-empty `tool_use_id`, and `PostToolUse` clears it only when both `turn_id` and `tool_use_id` match that pending exactly. An unmatched result leaves the status alone.
- `PermissionRequest` has no `tool_use_id` of its own and therefore cannot be approval evidence by itself; but it carries `tool_name`, and the call being approved was announced by the immediately preceding `PreToolUse`. The reducer therefore records "the tool call still open" per Turn (`openToolUse`: written by `PreToolUse`, cleared by the `PostToolUse` with the same `tool_use_id`), and `PermissionRequest` borrows that id to establish Approval pending. With no open call to pair with, or with `tool_name` disagreeing with the open call, the status stands — a wait that cannot be closed is never created. `PostToolUse` on its own still may not be used to guess approval status.
- **This section used to say "an automatically approved request opens and closes within one batch and cannot linger as a false wait", and that is not so**: a borrowed-id wait closes on the call rather than the decision, so it spans "decision + execution" rather than only "a person is looking". Measured 2026-08-22, automatic review took 2.5 s (2.1–5.9 s on the Desktop side), so the reducer genuinely opens an Approval on every reviewed call — which is not the reducer's fault, since what it proves is true. The correction lands at **row composition**, next rule.
- **The approval-routing gate (Codex; a cross-source decision, hence in `LiveCodexMonitorService`).** `CodexRolloutTurnReviewerReader` first reads that Turn's own `turn_context.approvals_reviewer` (next paragraph), and when it cannot, `CodexDesktopApprovalRoutingRepository` falls back to `.codex-global-state.json`'s `electron-persisted-atom-state.heartbeat-thread-permissions-by-id.<threadId>.approvalsReviewer`. Where the value is `auto_review` (Desktop's "Approval for me" / `guardian-approvals`), approvals on that thread never reach a person — an automatic reviewer has only allow and deny with no exit back to a person — so `CodexSnapshotParser.session` reduces that row's `approvalNeeded` to `running`, passing `inputNeeded` and `completed` through unchanged. **The direction is one-way**: only a thread proven `auto_review` is reduced, while an absent entry, an unrecognised value or an unreadable file preserve prior behaviour, because the claim being made is "nobody will be asked" and absent evidence is no claim. The reducer does not know this and should not: it sees only events, while this gate must know both events and a Desktop file. No field in the official `permission-request.command.input` schema can replace it (`permission_mode` is `default` under both settings, measured 2026-08-22).

  **The gate's answer belongs to the Turn, not to "the thread's setting right now".** Desktop rewrites `heartbeat-thread-permissions-by-id` the instant the reviewer changes, while a `ThreadSettings` override **does not rewrite the running Turn**: it keeps the reviewer it started under and goes on asking a person one call at a time. Measured 2026-08-24, thread `01a03241` opened as `user`, was switched to `auto_review` five minutes later, and five approval dialogues afterwards were all answered by hand while that Turn's rollout `turn_context.approvals_reviewer` stayed `user` throughout; `01a03130` had the same shape. Consulting the map at composition time would silence all five — the row sitting at Running while the user is being asked. So `TurnApprovalRoutingPin` (`CodexDesktopApprovalRouting.swift`) takes the answer once when `LiveCodexMonitorService` first sees a `(threadID, turnID)` and pins it until that Turn no longer appears in the reducer's state (`retain(turns:)` reclaims by the Turn set each composition actually walked, avoiding unbounded growth over a long run). **It is symmetric in both directions**, because "which reviewer this Turn used" is itself a two-way fact.

  **The fallback map must also pass a time test.** The map and the unread set share `.codex-global-state.json`, whose persistence can be starved indefinitely by typing (§1.3). So `TurnApprovalRoutingPin` accepts only a map whose `DesktopApprovalRoutingSnapshot.currentAsOf` falls inside `[startedAt, startedAt + 2s]`: one earlier may still name the reviewer the user just switched away from ("switch to yourself → type → send", where the switch reached memory and typing pinned it there), and pinning that would silence every dialogue this Turn genuinely raises; one later describes "this thread now", which is the previous paragraph's bug. Neither end **pins**, so the next credible reading answers as usual. The window's width is supported by measurement: sending clears the composer and the draft is a persisted atom, so Desktop necessarily writes this file about half a second into every Turn, and that write also repairs the starved old value; two seconds is four times that margin, while a deliberate mid-Turn switch measures in minutes (5:22, 1:08). With no credible reading inside the window, the row shows approvals as reaching a person until the `turn_context` authority overrides it. **That upgrade has been made.** A pin cannot fix the first glance: if this process's first refresh for a Turn falls before Desktop writes the switch down, the pin captures the stale answer for the whole Turn. What was reported on 2026-08-25 is exactly that face — false *Approval needed* on sessions switched from manual to automatic mid-Turn, and never on sessions that opened in automatic mode, because the latter have nothing for Desktop to write. So `CodexRolloutTurnReviewerReader` became the **first source**: it reads the last `turn_context.approvals_reviewer` at the tail of that thread's rollout, which is the reviewer this Turn was genuinely handed. **Read once, not once per refresh** — that record is written **before** the hook that tells this app the Turn exists: measured 2026-08-25 (CLI `0.149.0-alpha.4.3`), `turn_context` at `…491.593` and `UserPromptSubmit` at `…491.660`, with `--approve-for-me` likewise 65 ms — so failing to read it once means the rollout is simply not there rather than not yet caught up. The rollout path is not searched for separately: `thread/read`'s `path` field is it, and a Turn with no thread payload draws no row anyway. The 512 KB tail window is margin for a late refresh rather than for the normal case: at read time the Turn has just begun, and the record measures about 1 KB from EOF. Two guards: the record must be this Turn's, and only `auto_review` reduces, with unreadable, unrecognised and absent `approvals_reviewer` all not reducing. The map is demoted to the fallback, answering only for Turns it cannot read, with the pinning semantics unchanged.

  **"Read once" was right about *when* and wrong about *where* (2026-08-31).** Reported: false *Approval needed*, several times over, on a thread that had been "Approve for me" from its first moment — the difference from every earlier report being that the Turn was not started directly. The user started it, stopped it with a double Esc, edited the prompt and sent it again. **Codex writes a Turn resumed after an interrupt into a new rollout for the same thread.** Reconstructed from the user's own records (thread `01a058c7`, CLI `0.151.0-alpha.7.2`): interrupted at `17:08:38.039`, a new rollout opened at `…44.592` (`sessions/…/rollout-<date>-<threadId>_<rolloutId>.jsonl`, `thread/read` reporting it as the thread's `path` from that instant), its `turn_context` — `auto_review`, like every other one on that thread — at `…46.229`, and the resumed Turn's `UserPromptSubmit` 34 ms later at `…46.263`. The record still precedes the hook; the *file* moved. This app's last `thread/read` had gone out at `…36.206`, so the reviewer was looked for in the rollout the interrupted Turn was written to, whose newest record named that Turn, and the reading came back empty. Recorded as final, it cost the Turn its whole life on the map, which was outside its window too — and each of the three calls Codex's guardian reviewed at `17:09:03`, `…12` and `…30` was announced as a person being asked. Two changes, and the fix needs both: (1) an empty reading now records **which file it was made in**, and is final only when the App Server reported that path at or after the Turn began — otherwise the question stays open and is re-asked once per newer path, so the read stays bounded at one per rollout the Turn could be in; (2) a Turn new to a thread whose record predates it asks for the path again immediately instead of waiting out `threadMetadataRefreshInterval` — once per Turn, since the retry machinery owns what happens when that read fails. Separately, the record **names its Turn**, so `turn_id` now decides whether it is this Turn's, with the 2-second window kept only for a record that does not carry one: the window read "written when this Turn started" as "written for this Turn", which the file a resumed Turn leaves behind can satisfy while naming the Turn the user interrupted.
- Approval pending therefore comes in two kinds (`PendingApproval.isInferred`). `request_permissions` carries its own id, is guaranteed a paired `PostToolUse`, and is closed only by that event. A borrowed-id wait never receives a closing event on a **refusal**, so it is additionally closed by "a `PreToolUse`/`PostToolUse` for any other `tool_use_id`" — the product sends nothing while blocked on an approval, so activity on another call is evidence a person has answered. Both kinds fall back to `Stop` entering Completed. The rule is strictly limited to borrowed-id waits and must not be widened to `request_permissions` or Input pending. **The Claude Code side has a third closing path**, which governs **approval** rather than refusal: there `PostToolUse` lands when the tool finishes rather than when the dialogue closes, so approving a slow command leaves the row misreading *Approval needed* for the whole execution; a session reporting `busy` is evidence the dialogue is gone, see §4's "a session says whether it is still working" and ADR 0011's 2026-08-23 addendum.
- **"A person refused" is silent on both products, so both need that inference.** Codex, measured 2026-08-15: after a refusal that `tool_use_id` produces no further event and `Stop` arrives 67 seconds later. Claude Code was once recorded as an exception because `PermissionDenied` names the refused call — measured 2026-08-23 (CLI `2.1.241`) overturned that: the event has exactly one production site in the binary whose only call site is gated on `decisionReason.classifier == "auto-mode"`, so **it reports the automatic-mode classifier refusing, not a person**; and in two interactive runs, choosing `No` produced no `PermissionDenied`, no `PostToolUse` and not even a `Stop` (the refusal interrupted that Turn, and the official hooks have no interrupt event). So `ClaudeCodeHookVocabulary.reportsApprovalDenials` changed from `true` to `false`. The other half of the original reasoning for `true` — "`Stop` was measured arriving before its own subagent's `PermissionRequest`, so out-of-order delivery would let unrelated activity close a wait a person is still looking at" — does not hold either: that is not disorder but the shape of an asynchronous subagent (the `Agent` call returns immediately, the Turn ends first, and the subagent asks later), and with per-agent slots those two events land in two different slots. A subagent's slot infers on either product, for the same reason.
- Only a live `Stop` received after this launch clears pending input/approval and takes that same exact Turn straight to Completed. The product does not distinguish completed/failed/interrupted, and there is no terminal-pending window. A replayed historical `Stop` never enters the Turn reducer at all.

### 9.3 App Server current-snapshot correction

Hooks are the sole source of the four statuses; the App Server supplies presentation metadata only. The hook reducer publishes status using cached Thread titles and Desktop Project private state first and refreshes metadata asynchronously; no App Server request may sit on the hook → UI critical path. A Thread payload contributes only the root-thread test, the title and the preview, and takes no part in deriving status — no field of it can express Turn-level runtime truth in this topology (§1.1's measured boundary).

A standalone App Server does not share Desktop's current runtime, so it is neither a substitute for hooks nor a participant in status correction. A metadata read hitting a missing field, a timeout or a protocol error keeps the last trustworthy in-memory state and never changes a four-state value because of it.

### 9.4 Arrival order and late events

**There is no replay, so there is no live cutoff.** A payload comes down a socket into this process from a helper that ran moments ago, so an arriving event is current by construction; lifecycle signals during a crash or a quit were never written anywhere and cannot be impersonated at the next launch ([ADR 0015](adr/0015-hook-events-go-straight-into-the-reducer.md)).

**A Turn lives and dies with the Desktop process that produced it.** The previous paragraph is about this app restarting; this one is about the monitored side restarting. Codex Desktop sends no `Stop` when it crashes or is replaced by an update, and can never send one afterwards: the event that would end that Turn was its to send. (Whether a deliberate quit emits a final `Stop` before closing is unmeasured — that would mean quitting the user's own Desktop mid-Turn; the answer does not change what is done here, since emitting it means the row goes Completed and is then retired, and not emitting it means the path below.) The PID gate previously bound only **whether to publish** (`hasCurrentHookObservation`) rather than the Turns it vouched for, so rows correctly disappeared while Desktop was closed and then **the first hook** from any thread after reopening republished the whole reducer along with that zombie Turn, its timer still counting from before the crash — and nothing could then retire it: the thread was still listed and unarchived so membership correction kept it, no hook would ever mention that retired `turn_id` again, and the Codex side has no activity reading like `claude agents --json` to finish it ([ADR 0011](adr/0011-a-turn-may-end-on-evidence-that-is-not-a-hook-event.md)). **§9.5's rollout reading does not rescue this one either**, and the difference is the point: that reading answers a Turn Codex *stopped*, and a Desktop that died wrote no `turn_aborted` any more than it sent a `Stop`. The evidence for a dead producer is the dead producer. Every refresh now takes the current PID first: a PID differing from the one vouching for those Turns calls `discardTurns()` before the drain, and no process found retires again after the drain (a dying process's helper may still be in flight). `hasObservedEvent` / `hasObservedLiveEvent` are untouched — those hooks genuinely fired, and the Settings product row must not revert to "never received" because the user restarted Codex Desktop (CR-Fable-007).

**Arrival order is guaranteed by the transport's serial read queue, not by registration.** Connections are accepted in arrival order and handed to one serial queue, so `deliver` is called in the order payloads landed. Handing to an actor cannot use `await` — two `Task`s spawned in order are not two `Task`s that run in order — so payloads go in order into a lock-protected inbox and one drain takes the whole array.

**`retiredTurnIDs` stays.** A proposal argued for deleting it, reasoning that arrival stamps on a serial queue are monotonic so a late event for a retired Turn cannot exist. That holds for the transport, not the executor: ADR 0013 records Claude Code delivering `Stop` ahead of its own subagent's `PermissionRequest` under one `prompt_id`, and the reducer is shared by both products; the Codex half is unmeasured. Lateness and disorder are still stopped only by `mutateExactTurn`'s moment comparison and `retiredTurnIDs`.

Unknown fields and enums are written to diagnostics and never crash the app. A diagnostic keeps only the method name, the version and the enum identifier.

### 9.5 A Turn may end on evidence that is not a hook event

Four readings may **end** an already-open Turn and may never open, name or describe one. They enter the reducer through three methods and nothing else: `endTurnsForStoppedSessions(_:)`, `endInterruptedTurns(_:)` and `endAnsweredApprovalWaits(_:)`. The decision, its four boundaries and the measurements are [ADR 0011](adr/0011-a-turn-may-end-on-evidence-that-is-not-a-hook-event.md); what belongs here is which reading answers for which host.

| Product | What is read | What it may end | Why no hook can |
| --- | --- | --- | --- |
| Claude Code, terminal-hosted | `claude agents --json`'s `status` (`idle`/`shell` ends a Turn, `busy` ends an approval wait) | Whichever Turn or wait the thread holds — it names none | No hook event means cancelled or interrupted, and none fires when a person approves |
| Claude Code, desktop-hosted | The interrupt record in the session's transcript, by structural rule | Only the Turn its `promptId` names | Desktop runs the CLI with no terminal interface, so `status` is never written |
| Claude Code, desktop-hosted | Claude Desktop's own permission log, both ends joined by a request id | The waits that thread holds | Same absence, and no approval hook on either host |
| **Codex** | **`event_msg`/`turn_aborted` in the thread's rollout** | **Only the Turn its `turn_id` names, and that Turn's subagent bookkeeping with it** | **Pressing stop sends nothing at all — no `Stop`, and not even the `PostToolUse` for the call left open** |

The Codex row is the newest and it closes the gap this document named repeatedly as unclosable: with no activity reading of its own, a stopped Codex Turn had **no exit but the user's own hands**. It is read from the tail of the rollout `thread/read` reports as `path`, cached on that file's `(size, mtime)`, asked only of Turns still open, and woken by `LiveCodexMonitorService.rolloutWatcher` — pointed at those rollouts and at nothing else, since an append inside a directory fires no directory-level event. The Turn ends at the moment Codex stamped on the record rather than the moment this app read it, so the row's elapsed readout is the turn's real length. `reason` is not read: a word this build does not recognise must not be the difference between a row that ends and one that never does.

**The Codex row is the one reading that retires more than a Turn's status, and the reason is measured.** `runningSubagentIDs` is a thread-level fact carried across turn boundaries, and `MonitorAggregation.effectiveStatus` reads a Completed row with one as Running — right for a Turn that ended on its own `Stop`, wrong for one the user stopped. Measured on CLI `0.151.0-alpha.7.1`: the stop kills the `collaborationwait_agent` the Turn was collecting its subagent with (that `PreToolUse` never closes) while the subagent runs on and does eventually report, so the row went on announcing work the stopped Turn could no longer receive, for as long as the orphan lasted. `TurnInterruption.orphansSubagents` therefore empties that Turn's `runningSubagentIDs` and `subagentSlots` at the stop. It defaults to false, so the identity-free session reading and Claude Code's interrupt record are unchanged — Claude Code runs a subagent's own `SubagentStop` on an interrupt, so nothing sticks there. The cost is that an orphan can no longer raise an approval on this row, which is the same judgement in the same direction.

Two limits are deliberate. A `turn_aborted` naming a Turn the reducer does not hold does nothing, and only the **newest** abort in the tail is considered — an older one naming the open Turn would describe a Turn that ended before one the same rollout has since recorded ending. And archiving moves the rollout into `archived_sessions`, so an archive close behind its own interrupt takes the file away before the read; that row then waits for membership reconciliation exactly as it did before, which is a wait rather than a wrong state.

## 10. Aggregation and sorting

The summary priority is:

```text
Approval needed
> Input needed
> Running
> Completed
```

**Approval before Input** — both are the product waiting for a person, but Approval is a decision the agent cannot get past while Input is a question of when the user arrives (`PRD.md` §6.2, and `MonitorAggregation.rowOrder`, where `.approvalNeeded` is priority 0). This section previously carried the reverse order, which predates that decision.

With an empty set the collapsed state is `Connected` or `Disconnected`: the former when at least one product is open and ready, the latter otherwise. A non-ready availability clears that product's list, and the specific cause (not yet integrated, too old, connection dropped) does not enter the collapsed state and is explained only in the expanded panel and Settings.

The list sorts by that same priority, and by `observedAtMs` descending within a priority. The repository commits the order immediately, while the UI preserves the visible anchor while the user is scrolling or hovering and shows a lightweight update indicator when the change is outside the viewport.

## 11. Current content preview

`PreviewExtractor` receives only items already shown to the user:

1. Input needed: the current question text.
2. Approval needed: the fixed `Approval requested`, reading no command, path or rationale.
3. Running: the latest public commentary/progress; failing that, this Turn's prompt.
4. Completed: the start of the final answer; failing that, the last public progress.

"Latest" in rule 3 is literal: it must be **the step being taken**, not the step just finished. Neither product managed that before, for two different reasons — Codex had no text source at all, and Claude Code had a source but no edge putting it on screen. The two fixes are in the two subsections below.

Processing: strip control characters → collapse whitespace → take the first visible line → apply the memory limit → hand to the UI's alpha mask. Never write to a log, a database, UserDefaults or a diagnostic bundle.

### How text reaches this process (Codex)

**Text arrives with the event it belongs to, over the same connection.** The helper forwards stdin verbatim into `hook.sock` with no filtering; field selection, truncation and event naming all happen in Swift (`HookPayloadDistiller`, `HookPayload` and `HookSessionPreviewStore.normalized`) rather than in a Python string literal only one integration test ever reaches. **Selection happens before decoding**: what grows is always a field this app does not read (`tool_response`, a pasted `prompt`), so one pass picks out the keys it knows and `JSONDecoder` receives a few-hundred-byte object, and a tool result's size no longer decides whether a lifecycle event is heard (CR-030, [ADR 0015](adr/0015-hook-events-go-straight-into-the-reducer.md)). `UserPromptSubmit` carries `prompt` and `Stop` carries `last_assistant_message`, both on events the reducer already handles.

**There is no second socket and no `event_id` splicing.** `preview.sock`, `claimPreview` and the retention cap on unclaimed previews all existed only because message text was not allowed into an event file; one socket carrying the whole payload has no such split ([ADR 0015](adr/0015-hook-events-go-straight-into-the-reducer.md)).

Text still never touches disk, but that is now by construction rather than a rule to keep: there is no file anywhere on this path. With no listener the helper simply drops it, giving "no preview" rather than "a stale preview".

**Between connect and write, the app may already have accepted.** The listening socket is non-blocking so the accept handler can drain the backlog rather than stalling on the next connection, and Darwin's `accept` passes that flag to the connection it returns. The receive loop then reads `EAGAIN` from a client that is connected but whose write has not landed, and it cannot distinguish `EAGAIN` from the end of a message — so the payload was permanently discarded rather than re-read a moment later. The 250 ms receive timeout was set for exactly this step but constrains nothing on a non-blocking descriptor, so "it never fired" was not evidence of ample margin. `receivePayload` now clears that flag first, making the timeout genuinely effective (CC-023/CC-024). The same read loop has a smaller version of the same problem: a `read` returning `EINTR` from a signal also looks like the end of a payload, so it is retried separately, and only the remaining answers (a 0 from the writer closing, and a timeout's `EAGAIN`) end that read — whatever was read is what there is, and field selection decides what remains (CR-030). This trap was first found on `preview.sock`; it is a property of accept, so it moved with the transport both products now share.

`thread.preview` cannot be substituted: it measures as **the thread's first user message** and does not advance with Turns (a 17-Turn thread still returns Turn 1's text), so it cannot satisfy PRD §7's current-content preview.

#### A Running row's text comes from a read rather than an event

The path above covers `UserPromptSubmit`'s `prompt` and `Stop`'s `last_assistant_message` — the **fallback** for a Running row and the text for a Completed one. It cannot cover Running itself: Codex sends no assistant text mid-Turn and no hook carries any. So `Running` showed the user's own prompt for the whole Turn, unchanging, because it is the one thing in that Turn that cannot change.

`LiveCodexMonitorService.refreshTurnProgressInBackground` now fills it with one `thread/items/list` read, shaped:

```
{ threadId, turnId, sortDirection: "desc", limit: 6 }
```

`turnId` is correctness rather than optimisation: without it, a new Turn that has not spoken answers with the previous Turn's closing line, and the row describes finished work as what is happening now. Descending order with a small `limit` is likewise not optimisation — every item on a page must be decoded, and `commandExecution` carries `aggregatedOutput` (largest of 381 command items here, 290 KB), so page size is the worst case's multiplier. Six is enough to step over the `reasoning`/`commandExecution` items Codex inserts between sentences (measured on 0.149.0-alpha.4.3, at most 4 apart across three observed Turns); and if a message does fall out of the window, `TurnProgress.text` keeps the last sentence seen and clears only on a Turn change.

**When it reads.** The key is the Turn's own `lastEventAt` rather than a clock interval: this read has nothing new to say while the Turn is not moving, so a Turn stuck on a ten-minute command reads once and a Turn making back-to-back tool calls reads once per call. For that the reducer gained one wake-up: `PreToolUse` enters `changeEvents()` on this product (`AgentHookVocabulary.wakesOnToolCallOpened`) — it changes no field in `renderedProjection()`, but it is exactly when the row's sentence changes, because Codex speaks commentary before calling a tool. The paired `PostToolUse` does **not** wake it: a tool finishing prints nothing.

**Failure directions, and why it is recorded per thread rather than per server.** `-32601` has **two** causes, both encountered: a Codex without this experimental method (`codex app-server generate-json-schema` does not even generate it without `--experimental`), and **a thread whose `historyMode` is `legacy`** — on the same server, `paginated` threads answer fine while `legacy` ones answer `thread/items/list is not supported yet`. Measured 2026-08-25: a thread created by `thread/start` without `historyMode` is `legacy` and is necessarily refused, while every Codex Desktop-created thread is `paginated`.

So a refusal is recorded in the `threadsWithoutItemsRead` thread set rather than as a global switch. **This came from an end-to-end run rather than from reasoning**: the first version recorded it globally, the probe thread in a Release end-to-end run happened to be `legacy`, and one refusal switched off live progress for the entire panel — so with one legacy thread open, every other row went mute. The two causes are not distinguished by message text: the cost is only "a Codex without the method is asked once per thread", in exchange for one thread never muting the rest.

Every other failure affects one row and falls back to the prompt preview (the behaviour from before this read existed): a timeout (3 seconds, this file's shortest budget), a single failed read, and an empty page from a mismatched `turnId`. When the connection needs rebuilding, outstanding requests go back as they were and are asked again at the next refresh.

**Measured (2026-08-25, CLI `0.149.0-alpha.4.3`)**: on a Turn another process was running, this call returned in 1–4 ms with ordinary pages of 0.6–4.3 KB; after a `find /usr/share -type f | head -20000` the same call became 378 KB, which is the measurement that set `limit` to 6. The hook's `turn_id` and the `turnId` `thread/items/list` accepts are measurably the same value (captured `01a037e8-4fbc-…` off `hook.sock`, and the page it scoped returned that Turn's `agentMessage`).

**End to end (Release build, isolated `CODEX_HOME`, a real Turn)**: the row showed `I'm starting the check.` (0:13), `I'm now applying the fix.` (0:26) and `I'm verifying the fix.` (0:38), becoming `Stop`'s `I'm done.` when the Turn ended. The same probe showed the user's prompt for the whole Turn before being changed to `historyMode: "paginated"` — that "failure" is the degradation path above, and is how it was found.

### How text reaches this process (Claude Code)

**Both products are now one shape: one helper, one socket, one store.** The only difference from Codex is where the text comes from — twice a Turn, arriving with lifecycle events there; `MessageDisplay` 3.4 times a second in a speaking Turn here. So this side has one extra rule: `MessageDisplay` stops inside `HookEventRepository.deliver` and folds into a lock-protected preview store, **never entering the reducer's mailbox**. The folding stays on the listener's serial read queue rather than taking an actor hop — that path runs 3.4 times a second, and a hop would put it on the product's critical path (`AGENTS.md` §6.3).

**This channel was previously `type: "http"` pointing at `127.0.0.1:51741`; the reasons for replacing it with a helper have nothing to do with text, [ADR 0013](adr/0013-claude-code-hooks-run-a-helper-not-a-port.md).** In one sentence: while this app is not running the port belongs to nobody, so the CLI prints a `connect ECONNREFUSED` line into the user's session for every event, and it cannot be turned off — neither of which registration can fix.

The source is the official `MessageDisplay` hook ("While assistant message text is displayed", with the public payload `turn_id, message_id, index, final, delta`). It had never appeared in this repository's event table, and it is absent from Phase 0's 30-event list — which is where the conclusion "text cannot be obtained" came from.

**Measure first, then write.** Driving an interactive session over a pty with registrations pointing at a separate listener in a temporary `--settings` file (**leaving `~/.claude/settings.json` untouched**), CLI 2.1.234 measured: a 1561-character message arriving as **11 deltas** 0.20–0.44 seconds apart (mean 0.29 s), each payload 728–865 bytes. Everything below follows from that — three times a second is the only thing this path needs designing for.

`AgentHookListener` does four things with it:

1. **Divert before the reducer.** `deliver` recognises `MessageDisplay`, folds it into memory and returns: never queued, never reduced (whether it wakes the panel is below, decided by whether the row's line changed rather than by a delta). It previously also had to avoid an event directory — writing a file three times a second and having the reducer read and delete one is the most expensive possible treatment of this path, and that directory no longer exists.
2. **One serial read queue, ordered rather than fast.** Connections are accepted in arrival order and handed to one serial queue, so `record(_:)` sees the order payloads landed. This needs saying separately now, because the `command` schema **does** have an `async` key (the `http` schema does not, confirmed by reading the schema 2026-08-18; this document previously assumed a written `async: true` would simply be dropped by the settings parser). Measured on 2.1.237: `async: true` lets `PreToolUse` and `PostToolUse` for the same `tool_use_id` overtake each other, and **drops `Stop` entirely under `-p`** — the process exits before the background hook finishes. So registration is synchronous, at a cost of 6.3 ms per event on the session (against Codex's Python helper at 30 ms).
3. **Keep only each message's first 240 characters.** Memory is decided by a constant rather than by how much the model said: once the head is full, later deltas stop before being scanned into any retained structure.
4. **One pass, scanning only the new delta.** The folding function seeds from the already-normalised head and writes onwards, carrying the length as an `Int`. The previous form rebuilt `carried + delta` and took `.count` after every character — and `String.count` walks grapheme boundaries, making truncation quadratic in length and additionally copying the whole delta (the ceiling then being `maximumBodyBytes`, 1 MB; a delta is now a text field truncated at selection to `HookPayloadDistiller.maximumTextBytes`, 16 KiB). An over-long delta now costs the same as an ordinary one.

`delta`'s official wording is "**newly completed lines**", and it measures that way — and it is **incremental rather than cumulative**: consecutive deltas of one message begin `1. `, `2. `, `3. `, each starting where the last stopped (cumulative deltas appended block by block would repeat the whole message). All but the last **end with a newline**, which normalises to one trailing space, so the next delta appends directly and no separator has to be invented; `pendingSpace`'s seed exists only for a message's last delta, the one that stops mid-line. Non-interactive `-p` is a different shape: one delivery, `index: 0`, `final: true`, with a multi-line message arriving whole including its newlines.

**It does not enter the reducer's mailbox, but it does wake the panel — by whether the row's line changed rather than by a delta.** This once read "and it does not enter `changeEvents()` either, with one exception (from nothing to something)", and that design was wrong on an implicit premise: it assumed "the row already has a line and it went stale" would be repaired incidentally by **a refresh caused by that Turn's own lifecycle events**. There is no such refresh. An ordinary tool call opening and closing changes no field in `renderedProjection()` (the status is still Running and both preview fields are untouched), so **no refresh happens at all** between two status changes and the row sits on whatever message happened to be half-printed at the last one, while the session has said three more things. What the user sees as "live progress" is therefore **the previous step**, or older.

The edge reported now is "**the line the row will draw has changed**": `fold` compares the new text against the old as the row reads it (trailing space removed) and signals only when it differs. It is still not a redraw per delta, and that is guaranteed by the head's ceiling rather than by a rule — once a message fills 240 characters, every subsequent delta returns before being stored anywhere and wakes nothing. On CLI 2.1.234's measurements (1561 characters / 11 deltas / 142 characters mean), a long message wakes it twice and then goes silent, and a short one once. **The wake-up frequency therefore equals how often this agent starts saying something new**, which is exactly the frequency this row should track. Whitespace-only changes do not count: the stored form deliberately keeps a trailing space so the next delta can append (above), and the row never draws it.

"From nothing to something" still stands separately, because **pruning** can make `existing` describe text this store no longer holds: the row goes empty again, and putting anything back is a change.

And it is reported only for sessions **listed at the previous refresh** (the set `retainPreviews` receives) — text for a session the list omits is pruned by the refresh it triggered, so the next delta is a change again, which is not a wake-up but a loop running at delta rate, for a row that is not on screen anyway.

This product does **not** enable `wakesOnToolCallOpened`: its text is already in this process and `fold` knows when the row changes, so waking again per tool call is a second wake-up for the same edge — and a tool-heavy Turn is where that costs most.

Previews are pruned by the live session set (the same set as the title cache), so text cannot outlive its row.

**Text is asked for per Turn, falling back to the prompt.** The store is keyed by session and a session outlives a Turn, so a row must be able to ask what **this Turn** said: `HookSessionPreviewStore` stores each piece of text with its Turn, `preview(forSession:inTurn:)` answers only the matching one, and `ClaudeCodeMonitorService` falls back to `HookTurnState.promptPreview` when it cannot. This is the same argument as the Codex half's `turnId` (this section's opening: "without it, a new Turn that has not spoken answers with the previous Turn's closing line"), differing only in that one scopes the request and the other stores a stamp.

The Turn stamp is `prompt_id` rather than `HookPayload.turnID`: `MessageDisplay` is this product's only event carrying both `turn_id` and `prompt_id`, and they **differ**, while the reducer's Turn identity has always been `prompt_id`. Measured on CLI 2.1.234 and re-measured on 2.1.251 on 2026-08-28 (a single `-p` Turn with hooks registered on a temporary `--settings`, **leaving `~/.claude/settings.json` untouched**): one Turn's `UserPromptSubmit`, `MessageDisplay` and `Stop` all carry the same `prompt_id`, and only the middle one additionally carries a `turn_id`. So `HookPayload` keeps a separate `promptID` field, because `turnID`'s "either spelling" would pick the wrong one on this single event. Text with no Turn stamp (a hypothetical build no longer sending the field) is treated as answering to anyone — the behaviour from before this rule, rather than an empty row.

The folding wake-up gained an edge to match: a changed Turn is a change even when two pieces of text are identical character for character. Before this Turn speaks, the row draws the prompt, so this Turn's first delta replaces "the prompt" rather than "the previous text".

`UserPromptSubmit`'s `prompt` is enabled by `AgentHookVocabulary.carriesPromptText` — a switch previously called `carriesTurnText`, where one switch governed both the prompt and `Stop`'s `last_assistant_message`, so the correct judgement "this product's final answer comes only from `MessageDisplay`" incidentally switched the prompt off too. It is now two: `carriesPromptText` true for both products, and `carriesFinalAnswerText` true for Codex only.

## 12. Processing time

Product semantics are PRD §8.2; this section covers implementation constraints only.

**Time source**: `MonitoredSession.startedAt` comes directly from `HookTurnState.startedAt`, the `received_at` of the official `UserPromptSubmit` hook. Continued execution within one Turn keeps the original `startedAt`, and a new Turn on the same Thread takes a fresh one. No private Desktop time field is read, so this adds nothing to the non-public dependency registry.

**Computation**: `SessionElapsedFormatter` recomputes `now - startedAt` and never accumulates. That is why waiting and sleep count automatically, and why a missed refresh causes no permanent drift. A missing start or time going backwards returns `nil`, and the caller falls back to the status dot rather than rendering a guess like `0:00`.

**Aggregation**: `MonitorStore.longestRunningSessionStart` takes the earliest `startedAt` among sessions where `status.keepsTiming`. The test uses `SessionStatus.keepsTiming` (false only for `completed`) and must never be written `== .running`, or a Turn would vanish from the collapsed reading the moment it entered Approval needed.

**Refresh**: `MonitorStore` holds the one timing task, sleeping through `MonitorClock` and starting and stopping with the session list — with no unfinished Turn the task is cancelled and there are no idle wake-ups. Each sleep aligns to the timed Turn's next whole second, so a fixed one-second sleep cannot accumulate drift and skip a digit. On restarting, the task refreshes `timerNow` first, or a timestamp frozen while idle would make a new Turn's first second read negative.

**Panel geometry**: collapsed width is measured from the timer text, so the timer advancing must trigger a re-measure; `NotchTimerText` uses monospaced digits so it does not jitter every second. Tabular figures are only half of standing still, and both halves had to be added. The width the timer contributes is fractional whatever its digits do, and until `OverlayPanelLayout.frame` rounded the window onto whole points that fraction was re-animated on every publish, jittering the right edge by a point (`figma-design.md` §3.4). And tabular figures hold a reading still only *inside* one digit count: `9:59 → 10:00` is `8` pt. The collapsed surface was billed for a `00:00:00` slot (`timerReservationWidth`, since removed) so that those crossings were a re-*draw* rather than a re-measure; both forms have since given that up and are billed for the digits (`PanelMetrics.drawnTrailingReadingWidth`), so a crossing moves an edge, on the slot's own curve, and `elapsedLayoutRevision` moves the panel rather than only re-measuring inside it (`figma-design.md` §4.8 / §6.4). What the whole-point frame still buys is the rest of it: an unchanged layout compares equal and stands still.

**Accessibility**: `SessionElapsedFormatter.spokenElapsed` provides the duration form separately from the drawn text, because VoiceOver reads `12:34` as a clock time.

## 13. Quota, today's usage and the expanded footer

After connecting, two account reads happen asynchronously once the core session snapshot has been published:

- `account/rateLimits/read`'s primary window gives `usedPercent` and `resetsAt`; the ring shows `100 - usedPercent`.
- `account/usage/read`'s `dailyUsageBuckets` gives a `yyyy-MM-dd` date string and a token total. Today's key is generated with the target Mac's current Gregorian calendar and time zone and matched exactly on `startDate`; a valid array without today means today is `0`, while a missing array or a failed request means unavailable.

The account fingerprint is corrected every 30 seconds, and quota and today's usage refresh at most every 60 seconds; the two usage requests run concurrently while their parsing and degradation stay independent — a failed today's-usage read must not clear an available ring, and a failed quota read must not hide an available token total. On an account identity change both are cleared before the new account is read. Today's value must never be extrapolated from `lifetimeTokens`, `peakDailyTokens`, session-row tokens, a remaining percentage or an old snapshot.

**All three of those reads need a screen (2026-08-26).** The two numbers they buy are drawn only in the expanded footer, which the user must put the pointer on the notch to open — so with the display asleep or the session locked it is not "probably unwatched" but unwatchable. That gate previously existed only on the Claude Code side (§15.1), while the Codex side sent three requests a minute all night, and the conditions for paying were broader than expected: the "no hook observation at all" branch in `fetchSnapshot` — the state where Codex Desktop is not even open — also books this refresh, so it kept buying for as long as the App Server transport was alive.

The gate lands in two places, and skipping either saves nothing: `scheduleQuotaRefreshIfNeeded()` refuses the read, saving the request; and `nextRefreshDeadline()` also stops publishing the quota and account deadlines, saving "waking only to be refused" — which would be a past moment no refresh could ever clear, precisely CR-Fable-050's busy loop from a different source. The screen returning is an edge already merged into `stateChangeEvents` (`ScreenAvailabilityWatcher`), so the read skipped all night is bought at the first refresh after the user returns; the cost is that at the moment of unlocking `cachedQuota` may be a whole night old until that one JSON-RPC round trip lands — the same trade as the Claude Code side, for the same reason.

### 13.1 Footer format

> **Superseded by [`quota-footer-v2.md`](quota-footer-v2.md), implemented 2026-09-05.** The footer is `22` at rest — today's spend and the disclosure — and `19W + 30P + 17` with the table open. The `40 pt` box, the `•` between the two readings, and the gauge above them are all gone. What survives here is the two formatters, and one of them changed wording; both are below, corrected.

The outer view follows the panel's `12 pt` horizontal inset, so a `520 pt` panel gives `496 pt` of footer content width.

The token total uses fixed `en_US` compact notation with `1 ... 3` significant digits, keeping necessary decimals and dropping trailing zeros — `13.4K`, `323K`, `2.8M`, `1.03B` — while `0 ... 999` shows the integer. Unavailable data shows `--`, in the figure's own place and with the unit kept: `-- today`, `-- left`.

The reset is computed from **remaining duration** rather than the local calendar day — `Resets today` is equally true at 00:30 and 23:30 and therefore says nothing. It is written as a countdown of at most two units, because it stands in a column where every line is one: `47m` under the hour, `2h` under the day, `3d` and `3d 12h` above it; a stale time already in the past reads `Now` and is corrected at the next refresh. The absolute instant survives in the accessible name — `resets Friday at 09:00` beside a drawn `4d 6h`.

No reset time has two meanings, distinguished by **what else is known about the window**: Claude Code's 5-hour window only starts at the first request, and before that its line has a percentage and no `resets …` clause — a window that has not started rather than a failed read, written `Not started` (unconsumed, i.e. `100% left`). Everything else is **`--`**, which is the general rule for a field this app could not read: replace the figure in its own place and mark it in no other way. It read `Reset unavailable`, which sounded like the quota display being broken — the one thing it was not.

**The signal that rode the old wording survives the change intact**, because it never rested on the words. A window that is **consumed** but whose reset cannot be read is exactly the sign that Claude Code's output wording moved; what distinguishes it is the percentage beside it, against an unconsumed window at `100% left` that reads `Not started`. After this change the signal is a share beside a `--`.

The left side's production font is SF Pro Regular `11/14` in secondary text; the Inter in Figma is only a rendering substitute for MCP font unavailability. The right side uses a `32 × 32` native `Button` hit target with a `16 pt` `gearshape`, the VoiceOver name `Open Settings`, and SwiftUI's `openSettings` to open the existing `Settings` scene rather than duplicating the settings UI inside the overlay.

Failure policy:

1. A single request uses the App Server client's 15-second timeout; after a failed read the UI stays usable and retries silently after a 60-second cool-off.
2. If primary still fails, quota is unavailable and the grey ring shows immediately; if the today bucket still fails, the footer uses `--`.
3. No old value is kept, and nothing is estimated from lifetime, peak or other fields.
4. On an account identity change, quota and today's usage are cleared before the new account is read.
5. A failure in any account usage field changes neither availability, nor session status, nor navigation.

## 14. Navigation

A successful click is defined per product, with one navigator each, dispatched by `AgentNavigationRouter` on `MonitoredSession.agent`; a product with no registered navigator fails under its own name rather than being handed to the first in the table. What is passed is the whole row rather than a thread id — a Codex row is a deep link and a Claude Code row is a process plus a working directory, and no single identifier holds both.

### 14.1 Exact navigation (Codex)

`CodexDesktopNavigator.open(threadId:)`:

1. Ask the repository about **this one** Thread: it continues only if `thread/read` (`includeTurns: false`) hands it over and it passes the navigable-root-thread test. **This is the pre-click re-confirmation**, the same shape as the Claude Code side (§14.2 step 1) and the same question that let this row exist under [ADR 0017](adr/0017-a-row-requires-a-thread-the-app-server-vouches-for.md) — so a click never demands more evidence than drawing the row did. A remote error is an **answer** (this thread is out, and the refusal is recorded per ADR 0017, retiring the row); a transport failure is not an answer and must be thrown, so the user sees "could not confirm whether the session still exists" rather than "archived or deleted". An older Codex without `thread/read` probes once and falls back permanently to full pagination, the same degradation as the metadata path.
   **Archiving is not in this gate**: archiving ends the row's monitoring lifecycle rather than the thread's reachability, and that lifecycle is already owned by the 30-second membership reconciliation (`removeThreads(notIn:)` retires the Turn directly) — so a row the user can still see is one the last reconciliation still listed. It also cannot be asked cheaply: `thread/read` hands over an archived thread with no archived marker at all, and the `thread/archived` notification that would carry it goes only to the client that performed the archive and can never reach this app's own App Server (both measured 2026-08-26). See [ADR 0018](adr/0018-the-click-asks-about-one-thread.md).
2. URL path-component encode the `threadId` and construct the official `codex://threads/<thread-id>`.
3. Hand the URL to bundle id `com.openai.codex` through `NSWorkspace`; never fall back to a browser or the Codex home page.
4. There is no public receipt that the page finished rendering. Run-time success means only that Launch Services accepted the request; "opens the same Thread and creates or resumes no Turn" is guaranteed by versioned end-to-end compatibility tests.
5. Collapse the panel once the request is accepted; never mark anything read.
6. On a failed pre-flight or open, keep the panel and the row, show non-destructive feedback, and trigger a set correction.

Forbidden: a home-page fallback counted as success, undocumented URLs, private IPC, Accessibility clicking, title matching.

### 14.2 Raising the host (Claude Code)

ADR 0004's exact-navigation gate binds Codex only: no supported interface can focus an existing Claude Code session, and the official deep links always create. `ClaudeCodeNavigator.open(_:)` therefore raises the host, a **declared capability boundary** rather than a fallback disguised as success. The row carries no marker for it (a row carries one marker, and that marker is the timer), and the difference is stated only by `NavigationOutcome`'s sentence.

1. Ask `ClaudeCodeMonitorService` for that `threadID`'s current pid, answered from the same `claude agents --json` session list. **This is the pre-click re-confirmation**: a finished session is not in the list, so the click fails and triggers a set correction. The pid is not written onto the row in advance — a stale pid is not a dead link but somebody else's process.
2. Walk the process ancestor chain with `sysctl(CTL_KERN, KERN_PROC, KERN_PROC_PID)`'s `e_ppid` and `proc_pidpath`, **starting at the parent**: a desktop-hosted `claude` itself runs inside a bundle (`~/Library/Application Support/Claude/claude-code/<version>/claude.app`, `com.anthropic.claude-code`), so counting the session process itself would make every desktop session "host itself". Each ancestor's outermost `.app` is taken, so a helper is attributed to the application that spawned it.
3. Claude Desktop (`com.anthropic.claudefordesktop`) appearing among the ancestors means desktop-hosted: activate it. Take the **highest** ancestor with that bundle id, because the nearest is `Claude.app/Contents/Helpers/disclaimer`, and a helper is not an application the window server recognises.
4. Otherwise the nearest `.app` is the host terminal. Take that session's controlling terminal device (the same `sysctl` + `devname_r` path as terminal read state) and hand it to the terminal's **own public scripting dictionary** to select that tab: Terminal.app's `tab` has `tty` and iTerm2's `session` has `tty`. A terminal that cannot report a tty gets only its application activated — Ghostty has a full dictionary with no tty anywhere in it, only a title and a working directory, and matching on those is exactly the guesswork the PRD forbids.
5. **Automation authorisation does not make a click wait for a person.** While undetermined, one authorisation request is made in the background and the click degrades on the spot to activating the application; after a denial the system itself stops prompting, this app stops asking, and no error is produced — the user still sees `Raised X`. Script execution has a 5-second ceiling, so a stuck terminal cannot hold the "one navigation at a time" slot indefinitely.

   Measured on a real session in Terminal.app 2026-08-19 (`claude` pid 69273, `/dev/ttys015`):

   | Moment | Observation |
   | --- | --- |
   | Undetermined, the prompt on screen | The first click returned `raisedApplication(host: "Terminal")` in **0.02 s** — the prompt did not block navigation, so this design holds |
   | The user pressed Allow | Every click afterwards returned `focusedTerminal(host: "Terminal")` in 0.06–0.14 s; Terminal came to the front and `/dev/ttys015`'s access time advanced at that moment — **that tab was selected, not merely that application** |
   | The user pressed Don't Allow | Two more clicks in the same process returned `raisedApplication` in 0.03 s / 0.09 s; two fresh processes clicking three times each returned `raisedApplication` in 0.01–0.02 s all six times, **with no second prompt and no error**, and Terminal still came to the front |

   The desktop half was verified separately (`claude` pid 94822): the ancestor chain answered `desktop(com.anthropic.claudefordesktop, pid 24014)` — the application itself rather than the `disclaimer` helper, so step 3's "take the highest ancestor" holds on a real machine. Both clicks returned `raisedApplication(host: "Claude Desktop")` in 0.00 s, and the foreground went from Chrome to Claude Desktop without `NSRunningApplication.activate()` falling back to Launch Services.

   The system prompt's text (the template comes from `TCC.framework`'s `REQUEST_ACCESS_SERVICE_kTCCServiceAppleEvents`, with the two `%@` filled with the two application names and this app's `NSAppleEventsUsageDescription` appended). **The first half is transcribed verbatim from the measurement; the closing sentence was rewritten to the version below** — the measurement that day still used the Chinese one, later rewritten with the general move to English, with the template untouched:

   > "Notchline.app" wants access to control "Terminal.app". Allowing control will provide access to documents and data in "Terminal.app", and to perform actions within that app. Notchline uses this to bring the terminal tab running a Claude Code session to the front when you click its row.

   Two things worth recording. First, **the usage description really is displayed**, so that sentence is copy the user reads rather than merely a required field. Second, the application name in the prompt is **`Notchline.app`** — with the `.app` suffix and no space, because it comes from the bundle's filename rather than `CFBundleName`. Changing it means changing `PRODUCT_NAME`, which drags in the scheme, the binary name and the bundle name, and is out of scope here.
6. **Activation must follow the window to its desktop, or the click has done nothing.** When all the host's windows are on another Space, making it frontmost only moves the menu bar: the user is still looking at their own desktop and nothing on screen has changed. Measured item by item 2026-08-22 against an application with all three windows on another Space:

   | Approach | Result |
   | --- | --- |
   | `NSRunningApplication.activate()` | The app came to the front, not one window moved |
   | `activate(options: .activateAllWindows)` | As above |
   | AppleScript `tell application "X" to activate` | As above |
   | `NSWorkspace.openApplication` (`activates = true`) and `open -a` | As above |
   | Repeating all four with Mission Control's "When switching to an application, switch to a Space with open windows for the application" on | As above — that preference governs the user switching applications, not a programmatic activation |
   | Accessibility: the app's `AXWindows` / `AXMainWindow` | Windows on another Space are **not in there at all** (Xcode with three windows open answered 0, and `AXMainWindow` answered `kAXErrorNoValue`), so there is nothing to raise — the PRD excluding Accessibility therefore costs this path no capability |
   | `hide()` then `activate()` | **The desktop follows**, and that window comes to the front |

   The last is the only one that works, for one reason: **what takes the user across is not activation but the application ordering its own window front**, and the way to ask it to do that in public API is to hide it first. It holds across three implementation stacks — Xcode (AppKit), Ghostty (its own AppKit layer) and Claude Desktop (Electron), and also when the host is already the frontmost application with its windows on another Space.

   **That reading was wrong about one thing, and it was the thing that mattered: who is asking.** The 2026-08-22 table was measured from a throwaway process, and concluded that it "holds with the caller a background process". A background *process* is not a background *application*, and the window server tells them apart. This app is the second kind — an accessory application whose panel is a `nonactivatingPanel`, so it is never in the foreground — and its request is declined. Measured 2026-08-30 from inside the running app, host Ghostty windowed on a desktop that was not showing:

   | What the app did | What it was told | What actually happened |
   | --- | --- | --- |
   | `hide()` then `activate(options: [])` | `activate` answered `true` | The host came back from hidden; 400 ms later it still had no window on any desktop in view |
   | `NSWorkspace.openApplication` (`activates = true`), straight afterwards | no error | Still no window in view |
   | `NSApp.activate(ignoringOtherApps:)` first, then the same hide and activate | `activate` answered `true` | **The desktop followed** and the host came forward |

   The identical two calls made against the same host at the same moment by a throwaway process — from a shell and from `launchctl` alike — were honoured every time, which is what places this on the caller rather than on the calls. So the raise takes the foreground first, on the entitlement `SettingsWindowPresenter.reveal` already claims for the gear: it answers a click the user has just made on this app's own surface, and it holds the foreground only until the host takes it away. A raise that fails gives it back (`NSApp.deactivate()`), or the user is left with an application in front of them that has no window to show.

   Four details. First, **hide only when a desktop change is actually needed**. `WindowServerOccupancyReporter` first asks the window server whether that pid has a layer-0 window with alpha above 0 in the current Space (`.optionOnScreenOnly`'s list holds exactly the windows on the currently visible Space, reading only `kCGWindowOwnerPID`, `kCGWindowLayer` and `kCGWindowAlpha`, none of which Screen Recording gates); a host already in view is simply activated — no foreground taken and no hide, or the user would watch all its windows flicker. That path is measured working from the app as it stands. An unreadable list answers "not present", because erring that way costs one extra flicker while erring the other way is the defect itself. One call per click, median **554 µs**, p90 582 µs, max 694 µs (`-O`, 43 windows on screen), the same order as `OverlayConcealment`'s 583 µs. Second, **not one of the three calls reports its own result**, so each is followed by the state it is supposed to produce: `hide()` answers `false` on every host measured while `isHidden` goes true immediately after; `NSApp.activate(ignoringOtherApps:)` is answered by `NSRunningApplication.current.isActive`, and waiting for it is load-bearing — an activation sent while this app is still on its way to the foreground is declined exactly like one sent from the background, measured 2026-08-30 as the difference between a click that worked and one that did not. Third, **`activate`'s answer is not read at all**, and the window server's yes/no is asked again in its place, every 50 ms to a ceiling of 1.5 s, stopping at the first yes (a raise that lands answers in 300–500 ms). This replaces the old two-second safety net, which could not see this failure: activation unhides the host on its way to declining, so `isHidden` was already `false` when the net looked. A raise that never arrives now puts the host back at once and returns false, and the user reads `Could not raise Ghostty.` rather than a sentence claiming a raise they cannot see. An application the user hid themselves is neither hidden again nor unhidden for them. Fourth, **the tab path does not do this separately**, and the 2026-08-22 reason given for that — that Terminal.app's and iTerm2's scripts already carry the user across — is only true of an ordinary desktop. Against a **full-screen** host it is false: measured 2026-08-30, `set frontmost of theWindow to true` plus `activate` left Terminal.app's full-screen window exactly where it was.

   Verified end to end on a real machine (host Ghostty, the session row clicked for real, the host's window parked on a second ordinary desktop by moving it between displays): before the change the click hid the host and left the user where they were, three times out of three; after it, the desktop switched and Ghostty came forward three times out of three. With the host already on the current desktop, the host's `isHidden` and its window's presence were sampled across the click and neither moved — no hide, therefore no flicker.

   Two boundaries remain, one old and one newly measured. A host that cannot report a tty, like Ghostty, still has its own most recent window raised rather than the session's, and the difference is still stated only by `NavigationOutcome`'s sentence. And **a host whose window is full-screen cannot be reached at all**: a full-screen window is its own desktop, and measured 2026-08-30 nothing public crosses into it — `activate`, `.activateAllWindows`, `activate(from:)`, `NSWorkspace.openApplication`, `open -a`, `hide()` then any of them, an AppleScript `activate`, a scripted window ordering, and `AXRaise` with `AXFrontmost` all left the desktop where it was, with Mission Control's Space-switching preference both off and on. The two things that did cross were Launch Services opening a document the application already holds — which is why the Codex row, navigating by `codex://` deep link, does not have this defect — and the host's own `activate window`, which only Ghostty publishes. Such a click fails honestly rather than silently.

7. `~/.claude/sessions/<pid>.json` is not read: it does carry `entrypoint`, but that is a private schema while the ancestor chain is a public kernel fact. That file serves only as corroboration when the two disagree.

Forbidden: matching a tab by window title or working directory, Accessibility clicking, GUI automation, connecting to `/tmp/cc-socks/*.sock`.

## 15. Availability and partial degradation

Every "thin layer" below means **the expanded panel**. The collapsed state has only the two system statuses `Connected` and `Disconnected`, and reasons do not appear collapsed (§4 and `figma-design.md` §6.6).

| Failure | Collapsed | Expanded panel |
| --- | --- | --- |
| Nothing active or unread-terminal, product open | `Connected` | Thin layer `No active sessions` |
| App Server connecting, session snapshot outstanding | `Disconnected` | Thin layer `Connecting`, ≤ 5 s |
| Integration not registered (the product may be open) | `Disconnected` | Thin layer `Set up integration` |
| Version too old | `Disconnected` | List cleared, thin layer `Update required` |
| Version unknown/unverified | `Disconnected` | List cleared, thin layer `Version unsupported` |
| App Server unresponsive, failed to launch, or dropped | `Disconnected` | List cleared, thin layer `Disconnected` |
| Desktop unread main state missing, corrupt or incompatible | unchanged | Keep not-yet-hidden terminal rows and show a diagnostic; a backup/LKG empty set is never read evidence |
| Quota failure | unchanged | Grey ring; the list is unchanged |
| One row's preview fails | unchanged | Hide that preview; other fields unchanged |

### 15.1 Presence's trust ceiling

Codex's presence is a kernel fact with no cache and no staleness. Claude Code's comes from an external `claude agents --json` read and therefore needs three independent time parameters:

| Parameter | Value | Meaning |
| --- | --- | --- |
| `freshness` | `30s` | How long after the **last attempt** to read again — only while the list is **non-empty** and the kernel says one of its sessions has gone, or the last attempt **got no answer**, and both additionally require a screen |
| `edgeFloor` | `2s` | After an **edge** reporting the list is already wrong, the minimum since the last attempt before reading early |
| `trustCeiling` | `90s` | After an attempt has **failed**, how long since the last answer before a stale answer stops being believed (three consecutive failures) |

A failed read still returns the previous result and does not update "last succeeded". That is right for **rows** — one failure is not evidence every session ended and must not retire them all. But presence now decides `Connected` versus `Disconnected`: once `claude` is uninstalled, renamed or moved out of `PATH` the read fails permanently, and with the two parameters merged the pill would show `Connected` for the rest of the process's life. Past `trustCeiling`, presence is **unknown**, and unknown falls to `Disconnected` — which under §4's semantics is not a compromise but the literal truth: we have no usable connection at all.

**Finding a `claude` to run at all is the step above that one, and it had a hole the size of a whole class of user.** `ClaudeExecutableLocator` tried `NOTCHLINE_CLAUDE_PATH`, then `~/.local/bin/claude`, `/opt/homebrew/bin/claude`, `/usr/local/bin/claude`, then this process's `PATH` — which for an app launched from Finder is launchd's and not a login shell's. Every one of those assumes the user installed the terminal command. **Claude Desktop ships its own copy of the CLI and runs desktop-hosted sessions with it**, and installing the terminal command is a separate step in its install hub, so a Desktop-only machine has none of those paths. The consequence was total and silent: no executable, so `claude agents --json` never ran, so presence never left `unknown`, so no mark was drawn and every hook event was dropped at the row gate for naming a session no list vouched for — on a machine whose hooks were registered and firing perfectly, and whose settings card said `Connected · hooks installed` throughout.

Desktop's copy is therefore the last candidate, at `~/Library/Application Support/Claude/claude-code/<version>/claude.app/Contents/MacOS/claude`. It is a private packaging path and is registered as such in [`non-public-codex-integration-features.md`](non-public-codex-integration-features.md); the same tree's session records already reach the app through `NOTCHLINE_CLAUDE_DESKTOP_HOME`, and that one override now moves both, so a test pointing one at its own tree cannot leave the other reading the developer's real Claude Desktop. More than one version directory exists at a time (`2.1.255` beside `2.1.258`, measured 2026-09-02, the day after an update), so the newest is chosen on the dotted integers in the name and never on the string — `2.1.9` sorts above `2.1.10` on any string comparison. A directory whose name cannot be parsed that way is still offered, last, and one with no runnable file in it is passed over: what decides is `isExecutableFile`, not the `.verified` marker Desktop drops beside a version it has checked. It is tried **after** the user's own installs, because a CLI somebody installed is the one they update and drive; both read the same `~/.claude/sessions` and either answers correctly.

**And the settings card no longer outranks the notch on this.** `ProductSettingsCopy.claudeCode` read the registration alone, so it said `Connected · hooks installed` in exactly the state above. The service now reports `.disconnected` whenever presence is `unknown`, which is what the notch had already concluded, and writes a diagnostic separating the two ways of getting there: no `claude` anywhere (install it, or set `NOTCHLINE_CLAUDE_PATH`) and a `claude` that will not answer (run the command and see what it says). Telling the second user to install what they already have would send them the wrong way entirely, which is why this is two sentences and not one. See [`integration-settings-behaviour.md`](integration-settings-behaviour.md) §4 and §6.

**A list known to be empty is no longer re-read on the clock (CR-Fable-002).** `freshness` is a ceiling on how stale an answer may get, not a reason to buy a fresh one nobody asked for. But every store wake-up asks every service for a snapshot, and the store wakes at worst every `heartbeatInterval` (60 seconds; 30 from the account read while the Codex integration runs) — by which time a 30-second window has always expired. So `claude agents --json` was started every 30–60 seconds for the process's life: idle machine, no Claude Code open, screen locked, still running. That command's price is wholly out of proportion to what it buys; measurements and arithmetic are in `system-architecture.md` §6.

The test therefore became: **the last attempt got an answer, that answer was empty, and no edge has said otherwise** — that state is held and returns the cache without running the command. Every other case still follows the clock:

- **A non-empty list** is re-read on `freshness`, **and only once the kernel says the answer may have changed**. The half that cannot be skipped has always been that a row may need **retiring**, and one route there produces no edge — a `SIGKILL`ed session cannot delete its own record, and only that command's own `pid` + `procStart` validation sees the ghost. What 2026-08-26 added is the second half: this app can do that validation itself, one `sysctl` per listed session, microseconds, no process — against the command's 0.29 s of CPU, 187 MB peak resident, and starting the user's MCP servers besides. So the cadence decides **when it may be asked** and the kernel decides **whether it is worth paying to ask** (`ClaudeCodeSessionRegistry.everyListedSessionIsStillAlive()`). Start times are anchored in place on every answered read and afterwards compared only against its own earlier readings — so a reused pid also counts as a ghost; a pid that cannot be anchored or read right now counts as "not still alive" and falls back to the command, the behaviour from before the change. This does not hand the decision to the kernel: false only **permits** running the command, and whether to retire is still decided by the command's answer.
- **A failed or unparseable attempt** is retried on `freshness`. "Answered empty" and "nobody answered" look identical in the cache and mean the opposite, and holding the latter would displace the retry path that can both recover and reach `trustCeiling` — an uninstalled `claude` would leave this product reporting `closed` rather than `unknown` for the rest of the process's life.
- **Edges** answer no sooner than `edgeFloor`, empty or not.

**Both clock branches also need a screen (2026-08-26).** A cadence is a guess about how stale an answer is, and with no display that guess is bought for nobody — the notch it would correct is not being drawn. Edges are exempt, deliberately: an edge is someone reporting the list is already wrong, which is evidence, and neither a dark screen nor a live pid is a reason to refute evidence. The screen waking is itself an edge already merged into `ClaudeCodeMonitorService.stateChangeEvents` (`ScreenAvailabilityWatcher`), so the read skipped all night is bought the moment the user returns. The second bullet (retry after failure) is behind this gate too, and the first (non-empty list) passes this gate and then the liveness one.

`trustCeiling` is likewise written as what it always meant: **it constrains failures, not elapsed time**. An answer this app deliberately stopped asking about is not stale evidence but unrefuted evidence, and ageing it into "unknown" reports not knowing something we do know and merely have not paid to buy again. Once an attempt genuinely fails, the ceiling counts from the last answer as before.

**Attaching the directory watcher is itself an edge.** `~/.claude/sessions` does not exist before Claude Code's first run, so a user who registered hooks before opening a session has nothing to attach to at launch, and the watcher attaches only at some later refresh's `attachIfNeeded()`. The "empty" held before that was read blind, and the first session the user opens is exactly the one that creates the directory. The watcher cannot deliver that message itself (attaching only advances its `changeCount`, with no filesystem event to yield), so `ClaudeCodeMonitorService` recognises the transition in a refresh and calls `invalidate()`.

The cost, recorded: this path now genuinely rests on the directory edge rather than treating it as a latency optimisation. If the edge fails silently, a session that is open but has never submitted a prompt does not light its mark on the notch — and the moment it submits, that hook event invalidates the list through the "a hook event is itself evidence" fallback below, bringing the row and the mark back together.

**A failed attempt must occupy time on the cadence too.** `freshness` once counted from the last **answer**, so a failure occupied no time at all: the next caller saw the answer still expired and ran the command again immediately, and so did the one after. This side's refreshes are hook-driven and a busy Turn asks several times a second, so **one failed read became a chain of `claude` launches at hook frequency**. Measured (fault induced, real machine, Debug build): 71 launches in 110 seconds where the cadence permits 4; and separately, 24 concurrent `claude agents --json` took 1.6 seconds each against 0.25 alone — so the storm made each read slower in turn. Counting from the last **attempt**, with single-flight on the read (one refresh asks twice by design: once for rows and once for the mark, below), the same conditions gave 3 in 76 seconds. That also restores `trustCeiling` to what the table says: "three consecutive failures" is genuinely three only when a `freshness` separates them.

**An edge must be able to truncate the freshness window, or a newborn session is invisible for a whole Turn.** `freshness` is a guess about how long the list still counts, while a change in `~/.claude/sessions` is someone reporting that it already does not — a session file appearing or disappearing is precisely what turns the cache from stale into wrong. Waiting the guess out anyway costs one product everything: a CLI session is a process a person starts and then sits at a prompt for a while, so by the first prompt the list has long caught up; **a Claude Code desktop session is created by its first prompt** — process, `~/.claude/sessions/<pid>.json` and `UserPromptSubmit` all within a second — so the whole Turn runs inside the window where the list says that session does not exist, and `ClaudeCodeMonitorService` discards Turns whose session is not in the list (which is right; the list simply has to be told). Measured on 2.1.234 (2026-08-18, a session driven with the desktop's own parameters and entrypoint): the row appeared 20 and 23 seconds after that Turn's `Stop` — so *Running* was never drawn at all, and *Completed* arrived long after the Turn it described.

There were two faults here, each enough to swallow a whole Turn. First, that watcher was **constructed inline with only its stream retained**: an `AsyncStream` does not retain what produced it (the subscription is a continuation held inside the watcher, and the termination callback holds the watcher weakly), so the instance deinitialised at the end of the expression that created it, and `deinit` finished every continuation and cancelled the dispatch source — so this edge was not slow but already finished before `init` returned. It was the only watcher in the app written that way; the hook queue's and the Codex unread adapter's have always been stored properties. Second, the edge would not have told the session list anyway: the refresh it woke asked a cache up to `freshness` old, whose answer predates that session existing. The fix has the edge mark the list stale **before waking anyone**, so the refresh it causes is the one that re-reads; `edgeFloor` only limits how fast a burst of edges can make this app launch `claude` — measured over the same period, `~/.claude/sessions` changed **0 times in 45 seconds** (one active desktop session plus two idle ones).

That zero was once explained as "these files are written only when a session starts and ends", which is half right: a CLI session rewrites its record on every `busy` / `waiting` / `idle` flip, several times a Turn. But it rewrites **in place without renaming**, and a directory-level vnode event does not fire for "a file inside was written" — measured 2026-08-18 with this app's own event mask: an in-place rewrite gives 0 events, while create, delete and atomic-replace give 1 each. So edges genuinely are as rare as that number says, **and status flips never arrive as edges**, becoming visible only when someone next re-reads the list. An interrupted row would therefore wait at best for the next refresh (a 60-second heartbeat, a 30-second list freshness). So **the record files are watched too** (`ClaudeCodeSessionRecordWatcher`, still only as a signal, never parsing contents): watching `<pid>.json` for **every session in the list**, with the edge likewise calling `invalidate()` before waking a refresh.

**That scope was once narrowed to sessions with a Turn still running, and an idle session's record is the one that matters most.** The reasoning then was: a session sitting at a prompt need not be watched, because when it starts its next Turn a hook reports it and the record flips to `busy` at that same moment, so watching it only buys a wasted `claude` launch. That holds only while the hook and the list **call the same session by the same name**. A session id is not a process's lifelong identity: `/clear` and an in-session `/resume` swap it **in place** — same pid, same `<pid>.json`, same inode, with only the `sessionId` inside becoming new. Measured on this machine 2026-08-21: a record still describing the process started at 23:14, with its pid and `startedAt`, had a `sessionId` whose transcript did not begin until 01:14, two hours apart; and the pid-named `.key` sibling (`sha256("/tmp/cc-socks/<pid>.sock")`, verified) was likewise not rebuilt. So that rename **creates and deletes no file**, the directory edge cannot see it, and the narrowed record watcher happened not to be watching that record: the list went on reporting the old id for the whole `freshness` window while every hook from the rename onwards carried the new one, and `ClaudeCodeMonitorService` again discards Turns whose session is not in the list — **so the user saw the notch reading only Connected for a whole Turn, with no row at all** (a Turn shorter than the window never gets its row, and a longer one only appears part way through). This is the same failure as the desktop session's "invisible for a whole Turn", differing only in that that one was rescued by a newly created file, and an in-place rename has no such edge.

The cost is still absorbed by how quiet these files are: measured 2026-08-21, sampling every second for 90 seconds across six running sessions (two of them terminal sessions sitting at a prompt) — **not one record was rewritten**. Writes happen only on `busy` / `waiting` / `idle` flips (several times a Turn), of which the one nothing else reports (`busy` / `waiting` to `idle` with no `Stop`) is the very reason this edge exists, and a burst of edges is still bounded by `edgeFloor`.

**A hook event is itself evidence that a session exists, and a reading older than it does not count.** The record edge fixes that one rename; the list can also become wrong in other ways, and that class of failure has one shape: the reducer holds a Turn while the list does not recognise its session. So there is one more path-independent fallback, expressed in terms of **order** rather than ids: if such a Turn has moved **since the reading started** (`lastEventAt` later than `ClaudeCodeSessionListing.listReadStartedAt()`), the reading is wrong rather than the Turn stale — a read that started earlier cannot report what happened after it started (the same reasoning as `ClaudeCodeActivity`'s ordering guard). It then calls `invalidate()` and re-reads the list and presence **in the same refresh**, so that row is drawn during the Turn it describes rather than whenever a reading happens to land. Both ends are bounded: a Turn that has not moved — a session that vanished without a `Stop`, say — never asks for anything, so a Turn the list will never recognise again cannot become "one `claude` launch per refresh"; and whether an invalidation actually costs anything is the registry's decision, with `edgeFloor` holding it to at most one read every two seconds. The reading's **start** is taken rather than its answer, because `claude agents --json` takes 0.25 seconds alone and 1.6 concurrently, and a session born inside that window is exactly the one this read never saw.

`invalidate()` deliberately **has no protocol default implementation** (unlike `presence()` on the same protocol). An actor may legally satisfy an `async` requirement with a synchronous method, but then `await source.invalidate()` on the concrete type resolves to the extension's empty implementation rather than the actor's own — both compile and only one does anything. With no default, forgetting to implement it is a compile error rather than a silent no-op.

**Presence and rows must come from the same evidence.** The previous paragraph's "rows do not retire with presence" has a premise recorded in the same place: the interface retires them by turning to `Disconnected`. The interface was not honouring that half — `MonitorAggregation.status` looked at rows before presence, so a product whose mark had already left the notch (presence unknown, no matrix drawn) still had rows reading `Running`. What the user saw was Claude Code "dropping out and disappearing, yet still running". `ClaudeCodeMonitorService` therefore reports no rows while `presence` is not `open`; the list itself is not discarded but held, and recovers on the next successful read without waiting for any hook.

**This app's own quota read is not a user's session.** For the second or two it runs, `claude -p "/usage"` is a real Claude Code session, and `claude agents --json` reports its `kind` as `interactive` — byte-identical to one a person opened (measured on 2.1.234, 2026-08-18) — with the only distinguishing feature being which directory it runs in. What matters is that it **answers presence**: a user with no Claude Code open at all would see that product light up in the notch once per quota-read cadence (five minutes then, thirty now) because this app had just run `claude` itself. (It once cost one more row: that transcript has two `user` records and **no `assistant` record at all** (a slash command never reaches a model, `num_turns: 0`), so the `stop_reason` needed to end a Turn never appears, and the pre-launch rebuild then read it as a *Running* row named after this app's own folder, alive for a whole freshness window. The rebuild is gone, and this filter now serves presence only.)

That directory is therefore named once by `HookIntegrationPaths.quotaWorkingDirectory` and given to three collaborators: the quota read is pinned to it, the session registry excludes it, and the hook listener discards events carrying it. The exclusion is in the registry rather than the interface, because presence is decided in the registry: dropping the row afterwards would still leave the product reported as open. The listener half is redundant today — a `-p` slash command measurably fires no hook — but it is wired anyway: "fires no hook" is a property of somebody else's command, not a promise to this app.

**stdout is not guaranteed to hold only that array.** `claude` starts the user's MCP servers, and one measurably writes an extra line to the command's stdout (`Client.listTools() called but server does not advertise tools capability - returning empty list`, in two runs of five). `JSONDecoder` rejects the whole stream over trailing text, and at this boundary "an unparseable list" and "the command did not answer" are indistinguishable — so somebody else's log line costs not just one read but pushes this product towards the trust ceiling and takes the mark off the notch. The quota read had long decoded line by line to avoid the same thing; the array here is pretty-printed across lines, so that approach does not apply.

**"From the first `[` to the last `]`" does not work either (CR-Fable-039).** Its reasoning was that such a span could never be the lines printed around the array, which holds only while no surrounding line contains a bracket — and the measured line happened not to, while the most common shapes of log line do: `[INFO] …`, `[2026-08-21T…] …`, `[server] …`. One such line above the array and the span starts inside log text; one below and it runs past the array's end. Both are unparseable, so this defence stopped only the one contamination source it was written from and failed on the same problem's most common form, with consequences identical to the paragraph above: sessions still running while the product moves towards `Disconnected` and every row is held back.

**Instead the decoder decides where the array starts, because nothing else can.** Every balanced `[ … ]` span in the stream is scanned out and handed to the decoder in the order they **start**, and the first that parses is the answer, so it no longer depends on what the user's MCP server happened to print. Brackets count as structure only outside strings (a working directory's name may contain brackets, and counting those would truncate an entry mid-way), and string state resets at every newline — a JSON string cannot contain a raw newline, so a stray quote in somebody's log line cannot swallow the array below it, while an unclosed bracket makes that span simply not offered rather than carrying the rest of the stream and the array with it. **A parseable empty array is taken last rather than first.** `[]` is a very likely thing to appear in a log line, and at this boundary an empty list is a list **known** to be empty, which reports the product closed and takes every row with it; so a non-empty span below beats an empty one above, and empty is returned only when nothing else in the stream parses.

**Parsing is not being the array (CR-Codex-001).** Every field on `Reported` is optional — the schema belongs to Claude Code, and one field this app has not seen should not void the whole list — at the cost of that type parsing **any** JSON object. So "non-empty spans first" handed the answer to the first non-empty object array in the stream, whether or not it was a session list: an MCP server printing `tools: [{"name": "read_file"}]`, or any object array above the real one, would be taken as the reading, each of whose entries is then dropped in `sessions(in:)` for lacking a `sessionId`, and the empty list that remains is at this boundary a list **known** to be empty — reporting the product closed, retiring every row, and being held that way until some edge invalidates it. CR-Fable-039 taught this rule where an array starts, and did not make a candidate prove it is the array being looked for.

**So a candidate is accepted only when every entry carries `sessionId`, `pid`, `cwd` and `startedAt`.** Every one rather than most: an array that is half sessions and half something else is not a session list missing a few rows but a misread span, and dropping the entries it cannot explain would silently lose live sessions from an answer still marked trustworthy, with nothing anywhere saying so. Rejecting costs one read — `performRead()` keeps the previous list and retries on the cadence — and this side can afford being wrong while reporting the product closed cannot. The cost is that if Claude Code ever invents an entry with no `pid` / `cwd` / `sessionId` / `startedAt`, the whole list goes down with it where today only that entry is skipped. That direction is bearable, because a rejection ages into `unknown` (we do not know) rather than `closed` (we know it is shut).

### 15.2 Deadlines on subprocess reads

Both `claude` commands (`agents --json`, `-p "/usage"`) run on their own DispatchQueue, because `Process`'s `readToEnd`/`waitUntilExit` are blocking calls and would occupy one of the cooperative pool's few threads inside an async function. The subprocess carries a deadline (10 seconds for the session list, 30 for quota), `SIGTERM` at that point and `SIGKILL` 2 seconds later.

**But a deadline on the subprocess is not enough (CR-Fable-038).** When that function returns depends on `readToEnd`, and `readToEnd` waits for EOF; EOF does not come from the subprocess but from the **last copy** of the write end closing. `claude` starts the user's MCP servers, and anything that inherited stdout from it holds a copy — killing `claude` does not make them let go, so the read still never returns. The consequence is far larger than one lost reading: the session-list read is **single-flight**, so `inFlight` can never clear and every subsequent `liveSessions()` / `presence()` queues behind a read that cannot complete; `fetchSnapshot` awaits both, so the refresh loop's task group never finishes and `scheduleNextWake()` stops running — **the Codex side stops refreshing too**, leaving only an app restart.

So stdout is read by this app itself (`poll` + `read(2)` into a reused buffer, no longer through `FileHandle` and therefore no longer needing an `autoreleasepool`), stopping at whichever of three conditions comes first:

| Reason to stop | When | What the read counts as |
| --- | --- | --- |
| EOF | The last copy of the write end closes | As usual, judged by the subprocess's exit code |
| The subprocess has gone, the pipe has not closed | `0.25 s` with no new bytes after the subprocess exited (restarted on every arriving chunk) | **Accepted** when the exit code is 0: it has finished speaking, and whatever holds the pipe is not it |
| Hard deadline | 3 seconds past the subprocess deadline | Failure; if the subprocess is still there, `SIGKILL` it on the spot |

The middle one is what actually saves time. With only the hard deadline, one quiet orphan would drag **every** read out to `timeout + 3` seconds — 13 for the session list and 33 for quota — which is no longer a deadlock but is quite enough to make the product look broken.

**A killed command always counts as a failure, even with bytes already on the stream.** Half an output printed ahead of `SIGKILL` is not an answer: the exit code remains the sole test, and abandoning the read early changes only when the judgement is made, never what is judged.

The single-flight claim is likewise cleared by the read itself (`ClaudeCodeSessionRegistry.readClearingClaim`) rather than by whichever caller happens to be awaiting it. The boundaries above already make "the read does not return" impossible, and this puts the invariant somewhere visible rather than resting on an argument about a caller two layers away.

## 16. Settings and persistence

### 16.1 What is persisted

Permitted:

- The stable identifier of the user's chosen display; a temporary disconnection does not overwrite that preference.
- Integration installation state and compatibility results.
- Evidence that a legitimate hook has been received, containing no Thread, Turn or content. It is one `lastEventAt` line in `install.json`, written once per run — the card asks only whether anything has ever arrived, and writing it per event buys precision nobody reads.
- Non-sensitive app version and migration markers.
- Which blocks of the panel the user has opened: `quotaExpanded` and `recentExpanded`. Both are a fold, not a content cache — `recentExpanded` remembers that somebody wants to see what the list let go of, and nothing about what that was.

Forbidden:

- Session list snapshots, thread title caches, Project caches, unread state.
- **The Recent queue itself.** It looks exactly like the kind of thing that would be persisted and deliberately is not ([ADR 0017](adr/0017-a-row-requires-a-thread-the-app-server-vouches-for.md), [`expanded-panel-v2.md`](expanded-panel-v2.md) §2.4 rule 03): a stored queue would be the one thing on this surface offering navigation to a Thread nobody vouched for this run. It is empty at launch, holds only rows this run drew, and is empty again after five quiet hours.
- The hook reducer's Turn identities, lifecycle and pending input/approval evidence. This is now guaranteed by the architecture rather than held by a rule: there is no file anywhere on that path.
- Prompts, progress, final answers, raw reasoning.
- Full paths, commands, diffs, tool arguments, credentials, old quota values.

### 16.2 Settings behaviour

- The expanded footer's gear calls the system `openSettings` to open the existing Settings scene; it installs no integration, modifies no preference, and creates no second settings UI inside the panel.
- `Display`: moves the component to the chosen display immediately; falls back while the target is temporarily unavailable and restores the preference when it reconnects.
- `Recheck`: re-runs the read-only capability checks and silently changes no configuration.
- Integration switches: **one per product**, at the end of that product's own row in the `Products` card (`figma-design.md` §8.1). On installs or repairs that product's required event definitions, Off removes only the configuration fragment this app manages, and Settings stays reachable afterwards. While a change is in flight **only that row's** control is disabled; a failure restores the pre-toggle display and gives a non-destructive error. Status, switch position, in-flight markers and convergence tasks are all kept per product in `MonitorStore` (`setupStatusByAgent`, `integrationSwitchIsOnByAgent`, `integrationBusyAgents`, `integrationTasks`), so switching one product off touches neither the other's switch nor its rows in the merged list.
  - Codex: writes its definitions to `~/.codex/hooks.json`. After a first install or a definition change the user still reviews them under Codex `/hooks`, and the app must never alter the trust state.
  - Claude Code: writes `~/.claude/settings.json` ([ADR 0016](adr/0016-write-the-users-claude-code-settings-and-keep-a-copy.md); ~~previously a `Set Up…` rather than a switch, per ADR 0010~~). **Before every write** the file is copied to `settings.json.notchline-backup` in the same directory, with the copy meaning exactly "the file as it was immediately before this app last changed it". That rule lives in the shared `ManagedHooksFileEditor` and **applies to Codex too** — `~/.codex/hooks.json` is likewise copied to `hooks.json.notchline-backup` before every write, for ADR 0016's reason: Codex records trust by group index, and restoring a stale copy would silently shift trust off the user's own definitions. Writes touch only this app's own keys, refuse rather than coerce an unrecognised shape, compare bytes before and read back after; `install()` writes the helper first and refuses outright if it cannot. There is no trust step.
- ~~`Clear the session list`: clears only this app's rows, deleting no Codex session; disabled with an empty list.~~ **The feature is deleted entirely** rather than merely removed from the card: `MonitorStore.clearSessions()` / `clearSessionsAndWait()` / `isClearingSessions`, `AgentMonitoring.clearSessions()` and both products' implementations, and the `HookEventRepository.clearTurnsPreservingObservation()` that existed only for it, are all gone. The user's only manual removal is right-clicking a row (§17). The two originally shared one removal record (today `dismissedSessionIDsByAgent`) and the survivor keeps using it; the difference is that a right-click is given while the user is looking at that row, whereas a clear-all has to open the settings window first and then act on a set of rows the user is not looking at, one of which may be an answer they have not read.
- `Quota reading transcripts`: reports the total size of the transcripts this app's quota reads leave in Claude Code's own project directory, ending in `Show in Finder` to open it (**size only**: the count half answers a question nobody asks, since judging whether it is worth clearing depends only on size); it **measures and never deletes**, for the reason in `ClaudeCodeUsageTranscripts`. **This row has three readings, not "a number" and "no row".** The directory is found from an already-completed read, so nothing can be counted before the first one lands: until then it writes `Calculating…` with the button disabled; measured, it writes `43.2 MB` and enables it; and where a read has completed and the directory still cannot be found, it writes `Unavailable`. The test is "has a read ever completed" (`ClaudeCodeUsageReader.attemptedAt`) rather than a failure count — `session_id` is recorded inside `read`, so a completed read's directory cannot still be reported as pending; and on a machine with no `claude` that work in progress has already stopped, making `Calculating…` a progress claim that no longer holds. A product that leaves no files at all (Codex) has no such row — representing that and "not yet measured" with the same nil is exactly what made the card grow a row by itself in CC-020. The button's disabled state is decided by the single source "is there a directory", with no second flag, so the two cannot contradict each other.
- `Show in Finder`: one per `Products` row, last in each row (after the switch), so the three icons form a column; borderless, the symbol fitted to `12 × 12` with `resizable` (not `.system(size: 12)`, which means "beside 12-point body text" and measures `folder` at `17 × 13`), a `22 × 22` hit area, and a `5`-corner ground (`MacOSWindowColor.hoverBackground`) appearing only on hover, with `Show in Finder` as both tooltip and accessibility label. The two product rows point at that product's hooks registration file, taking the path from `HookIntegrationPaths.live(for:)` rather than re-composing it in the view — so the button and whoever actually writes that file cannot point at two different places; the transcripts row points at the quota-read transcript directory as before. The destination comes from `FinderRevealTarget.revealing(_:)`: `activateFileViewerSelecting` when the file exists, `NSWorkspace.open` on the folder that should contain it when it does not, and `nil` (disabled) when neither does. **The middle case is necessary rather than considerate**: with the switch never turned on, `~/.codex/hooks.json` and `~/.claude/settings.json` do not exist, and `activateFileViewerSelecting` does nothing, silently, for a path with no file at the end. It is an assertable value rather than a closure per row, for `ProductSettingsCopy`'s reason: no test in this window can press a button, but "which folder pressing it opens" is an answer a test can assert directly.
- `Quit` (~~`Quit Notchline`~~: the button is inside the app's own settings window whose title bar already carries the app name, and repeating it only widens the button): the capsule on the window's last row, calling `NSApp.terminate`, after which the collapsed component leaves the menu bar. It belongs to no group — it is not a setting but the only app-level action this window can offer, since the overlay has no window of its own and closing Settings does not quit it.

## 17. The SwiftUI boundary

The product UI layer depends only on a stable view model:

```swift
@MainActor
protocol MonitorViewModelProtocol: ObservableObject {
    var availability: IntegrationAvailability { get }
    var aggregate: AggregateState { get }
    var quota: QuotaSnapshot { get }
    var sessions: [MonitoredThreadSnapshot] { get }
    func open(threadId: String) async
}
```

Mock and real implementations share the protocol, previews and tests keep using the mock, and the production entry point injects the real repository. SwiftUI never parses protocol events, reads local files, or constructs navigation URLs.

**Right-click removal of a row goes through this boundary too**: the view emits only intent (`MonitorStore.dismiss(_:)`), and the store records that row's `MonitoredSession.id` under that product in `dismissedSessionIDsByAgent` and **re-runs the merge and publishes** — the list, the top-level summary and the product marks are all derived from the rows still shown, so changing only the array would leave an invisible row still lighting a product mark. **It applies in every state, and used to apply to Completed rows only (2026-08-31).** The restriction read well — a running Turn has not told the user anything yet, so a stray click threw away a notice they could not get back — and it was protecting the wrong thing. A Turn stuck open by a defect is by definition never Completed, so the one gesture that removes a row was missing in exactly the state a user needs it in, and quitting the app was the only way out (§9.2's nested-agent takeover, reported that day). The cost is accepted rather than argued away: it is one right-click on a row the user is looking at, it names the Turn and not the Thread, so the Thread's next Turn draws a new row and what an accident costs is one Turn's notice. **It is not a stop button**: nothing is sent to either product and the Turn behind the row goes on exactly as it was. SwiftUI has no secondary-click gesture and `contextMenu` gives a one-item menu, while this panel collapses as soon as the pointer leaves; so a `SecondaryClickCatcher` (`NSViewRepresentable`) is laid over the row, whose `hitTest` claims the event only when it is a `rightMouseDown`/`rightMouseUp` and returns `nil` otherwise, letting left clicks, hover and cursor tracking reach the button beneath — `SecondaryClickView.claims(_:)` is factored out precisely so this can be asserted. It is installed on every row.

**That record must also reach the provider that owns the row (CR-Fable-003).** Filtering only at this layer leaves the row a listed, unread terminal row inside its own product, which is exactly the condition under which the terminal gate books a re-check every second — so after the user dismisses the last row and leaves that CLI at a prompt, the app goes on running a two-product refresh every second to sample a read-state test that can no longer change anything. Ownership of the record is unchanged (the store is its only holder, and only it can distinguish "the user dismissed it" from "the Turn ended", next paragraph); what changed is that every `AgentMonitoring.fetchSnapshot(dismissedRowIDs:)` carries that product's share down: the service stops evaluating those rows, `retain` drops their existing gate entries, and they book no further re-check. **The service still reports those rows** — holding them back would tell the store the Turn had ended, which is what the next paragraph describes as making a dismissal be forgotten. `dismiss(_:)` requests a refresh itself after recording, so that share goes down immediately rather than waiting for the re-check the row booked.

**When that record may be forgotten (CR-Fable-004).** The set must be bounded — a dismissal that can never be forgotten is a leak — but "it is not in this snapshot" is not "that Turn is over". A product stops reporting its rows for entirely ordinary reasons, none of which clears the reducer behind it: Codex Desktop quitting makes the provider send an empty list immediately (presence is a kernel fact and precedes any message about Turns); App Server flapping past the 3-second stability window sends `.disconnected` with an empty list; and Claude Code with no window open **holds rows back rather than discarding them** (§15.1). The original took a `formIntersection` against the whole merged snapshot, so any of those three erased that product's entire record — and the row the user right-clicked away would return to the notch at the next hook event, exactly what `PRD.md` §4.2 item 5 and §14 item 15 say must not happen.

The test became **a visible product no longer listing it**: that product is `isConnected` in this snapshot (open, and able to answer) and this Turn is not among the rows it lists. A product that cannot be seen is not a witness, and its records stay untouched until it can speak again. The set is therefore stored per product too: one product's health disposes only of its own share and has no say over the other's. The key is still the Turn (`MonitoredSession.id` carries the turn id), so the same session's next Turn is unaffected.

**What the list has let go of crosses this boundary the same way, and adds no new kind of crossing.** The view emits three intents and holds no state of its own: `MonitorStore.toggleRecent()` for the fold, `removeFromRecent(_:)` for a secondary click on a retired row, and `open(_:)` — the live row's own call, unchanged, because a retired row keeps the whole `MonitoredSession` and both navigators read only its `agent` and `threadID`. What it renders is two published values, `recentDepartures` and `recentReadAt`; the store decides membership, order, expiry and the instant the ages are drawn against. **Archiving is not an intent and reaches no view**: it happens inside `apply(_:)`, where a row this app last saw terminal leaves the list under a product that was there to have read it ([`expanded-panel-v2.md`](expanded-panel-v2.md) §2.5).

**Whether the panel is on screen also goes through the AppKit side rather than the view model.** `OverlayConcealmentWatcher` samples the on-screen window list every 250 ms and hands it to the pure function `OverlayConcealment.menuBarPresence(onDisplay:windows:otherDisplays:)` to decide who owns the target display right now: the target display's menu-bar window absent from the on-screen list means concealed (an app or video is full-screen there, or the menu bar is set to auto-hide), and present means it stays on screen. That is the only test, so the answer is a `Bool` rather than a reason enum; Mission Control does not hide the menu bar and therefore falls on the "stays" side (`PRD.md` §9.2.1). The callback fires only on a change and does exactly three things — collapse (`MonitorStore.collapse()`, since a window pulled away receives no pointer exit), `orderOut`, or recompute the frame and `orderFrontRegardless`. While concealed the panel still follows frame changes and merely does not re-enter the screen. When the display cannot be determined (`DisplayOption.displayID` is `nil`, meaning `identifier(for:)` took the fallback) it never hides, per `PRD.md` §9.2.1; **and with no screen it likewise does not hide** — the stopping side puts the overlay back and forgets the previous answer, `system-architecture.md` §7. The sample's ticket is carried all the way to `apply(_:ticket:)`, because a main-queue hop separates the test from going on screen while `sampleNow()` goes on screen immediately on the main actor and would cut ahead of an already-queued hop. The signal itself and the polling cost are in `system-architecture.md` §6.

Geometry remains the existing AppKit overlay's: it uses the full `NSScreen.frame`, every intermediate frame keeps the same `maxY`, and the top height comes from the target display's panel band — the cut-out on a notched display, the menu bar band on every other (`figma-design.md` §3.5). Horizontally the expanded form locks `midX` while the notched collapsed form anchors to the cut-out's right edge, with the window leaving one corner radius of shoulder on each side of the body (`figma-design.md` §3.4). Three visible session rows give a total expanded height of `panelHeight + 270` (`240` viewport + `30` footer), and empty/global states `panelHeight + 78` (`48` body + `30` footer) — so at the `46 pt` reference those are `316` and `124`, and a notch-less `24 pt` menu bar with three rows is `294`.

## 18. Phase 0 verification plan

1. **Versions and schema**: record the Desktop and embedded CLI versions, generate and read the official schema, and build unknown-field compatibility fixtures.
2. **Same-runtime visibility**: prove an observer can passively see Desktop's current active Turn without resuming or taking over a request.
3. **Request status**: verify Input, and both approval shapes (a dedicated approval tool and an ordinary tool such as a Bash command) appearing, resolving and returning to Running; cover both approval and refusal, verifying that after a refusal the Turn returns to Running when it calls another tool and converges to Completed via `Stop` when it does not; verify that a lone `PermissionRequest` and one naming a different tool never misreport Approval; **verify that under automatic review (`approvalsReviewer = auto_review`) neither approval shape reaches Approval needed while `request_user_input` on the same thread still reaches Input needed**; **verify that a reviewer changed mid-Turn leaves that Turn on the answer it started with** — a thread opened as `user` and later recorded as `auto_review` must still reach Approval needed, and its next Turn must not; **and that which reviewer this Turn used is governed by the rollout's `turn_context`** — a thread whose map still says `user` while that Turn's `turn_context` is already `auto_review` must not reach Approval needed; **and that a Turn resumed after an interrupt is read from the rollout it is actually in** — stop a Turn on an auto-reviewed thread with a double Esc, edit the prompt, send it again, and the resumed Turn must not reach Approval needed even though Codex has moved the thread's rollout under it.
4. **Terminal states and unread**: verify a live `Stop` and all three App Server end results take Running straight to Completed; verify a terminal unread Turn is kept and removed immediately once read in Desktop.
5. **Project/Chats**: cover single-repository and multi-repository Projects and a Project-less Chat.
6. **Delete/archive**: verify both events and set correction remove them automatically, and confirm closed does not mean deleted.
7. **Processing time**: verify session rows and the collapsed state advance every second; verify the timer does not pause on entering Approval needed and stops on Completed; verify the collapsed state takes the longest among unfinished Turns and the reading disappears once all are finished; verify the timing task stops waking with an empty or fully finished list.
8. **Quota and today's usage**: verify primary, multi-window fields, `account/usage/read`'s today bucket, account switching, the 15-second request timeout, the 60-second retry and mutually independent unavailability.
9. **Navigation**: the adapter and unit tests are done; end-to-end verification across the version matrix that it reaches the same Desktop page and creates or resumes no Turn is still needed.
10. **Multi-client safety**: prove the observer never answers Desktop's server requests and never changes runtime state.

The deliverables are a capability matrix, redacted event traces, a version compatibility table and a go/no-go conclusion.

## 20. Test strategy

### 20.1 Unit tests

- Legal and illegal reducer transitions, out-of-order and duplicate events.
- A missing `session_id`/`turn_id` fails closed; an old Turn's Permission/Stop cannot change a new Turn.
- `request_user_input` is cleared only by a `PostToolUse` with the same `tool_use_id`; an unrelated Post clears neither Input nor Approval.
- Pre-launch backlogged UserPrompt/Permission/Input/PostTool/Stop/SessionEnd never enter the Turn reducer; the persisted file keeps only the boolean configuration-health marker, and memory stays empty after migrating an old `turns`.
- The monitored set's active/unread/archive/delete rules.
- Legal transitions among the four statuses, Completed's stickiness and the summary priority.
- No approximate Project fallback, and the title fallback.
- Desktop Project private state's exact local/remote/Chats parsing, `thread.section` isolation, main/backup/last-known-good degradation, and `Project unavailable` on a missing assignment.
- The Running status name (`Working...`) and quota reading are unaffected by time advancing.
- Compact token number boundaries, today/tomorrow/multi-day reset copy and the local time zone's day boundary.
- Quota/today's usage account switching, the 15-second request timeout, the 60-second retry and independent unavailability.
- Concurrent business timeouts start only one `thread/loaded/list` probe; a successful probe or a late response inside the grace period does not restart, and only a probe that also times out rebuilds the transport.
- The footer is `40 pt` with and without sessions, and the expanded heights contain a `280`/`88 pt` content region respectively.
- The Settings gear's accessibility name and its opening of the existing Settings scene.

### 20.2 Integration tests

- Three concurrent Threads: Input, Running and unread Completed.
- Identically named Threads and identically named Projects do not merge.
- Multi-repository Projects and `Chats` display consistently.
- Reading, archiving and deleting in Desktop remove rows automatically.
- Restarting Notchline shows no cached flash and rebuilds correctly.
- Desktop not running, an old version, an unknown new version, and reconnecting.
- Clicking every row reaches the same Thread; a missing target keeps the panel.

### 20.3 Integration-boundary tests

- Confirm diagnostics and logs write no credentials outside the user's own paths; this Claude Code channel no longer has a token to write.
- Confirm neither Accessibility nor Screen Recording is requested — an installation-friction trade-off rather than a privacy promise: both need the user to go into System Settings, and what this product can do with them is not worth that price.
- Confirm the observer sends no method that would change a Thread or Turn.
- Confirm removing the integration deletes none of the user's other configuration.
- Confirm the master switch installs and removes the complete set on On and Off; that a missing or duplicated definition, or an altered matcher/handler/timeout, enters `repairRequired`; and that switching on again repairs it without deleting the user's other hooks.

## Question drafts and presentation (2026-09-07)

`MonitorSnapshot` remains the UI's only data contract. Existing `AgentQuestionOption.label` and `description` values feed `RequestBodyLayout.Option`; the layout wraps them once per evaluation at the drawing width and exposes the exact visible lines and height. A question with options has a `300` pt body cap, and the live viewport grows to fit its open row. Approval and plan bodies retain `140` pt.

`AnswerProgress` holds the request identity, the current question, the furthest question reached, and one `Draft` per question — selected option IDs, expanded-description IDs and field text — in memory. Single choice replaces the selection and multiple choice toggles it. **An answer is derived from its question's draft rather than recorded on the way past** ([`answer-in-notch.md`](answer-in-notch.md) §5.7): `answer(to:from:)` is the one place a draft becomes an `AgentQuestionAnswer`, and it decides both whether a question may be left and what finally goes back, so a set walked backwards cannot send an answer the person came back to change or a short set missing one they emptied. Trimmed non-empty draft text replaces all selected labels; otherwise labels are joined in source order. No annotation is generated from this input. ~~Advancing clears the current draft, selection and disclosure state~~ — advancing clears nothing and draws the next question's own draft, which is what makes `Back`, `←` and `→` possible; a replacement request clears the entire progress even when the Thread row identity is unchanged. The existing per-product answer encoder and reply-ticket transport are unchanged.
