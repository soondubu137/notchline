# Registry of integrations without official public support

This file records only production features that depend on implementation details **not** covered by official public documentation or public schema, one table per product. The point is not to list everything that avoids the App Server, but to locate the real private dependencies quickly when a Desktop update breaks something.

**Verification baselines.** Codex Desktop `26.810.50856` (build `6644`) with built-in Codex CLI `0.148.0-alpha.9`, verified `2026-08-14`. The approval-routing and subagent rows were verified separately on Codex Desktop `26.818.41509` / CLI `0.149.0-alpha.4.1`, `2026-08-22`. Claude Desktop `1.30096.5` and Claude Code CLI `2.1.233`, verified `2026-08-16`; the Claude Code subagent row on CLI `2.1.241`, `2026-08-23`. Both tables' "a subagent stopped at a dialogue" rows were verified on Codex CLI `0.149.0-alpha.4.1` (isolated `CODEX_HOME`) and Claude Code CLI `2.1.241` (pty interactive session), both `2026-08-23`. The persistence timing behind "remove a Completed thread once read" was re-measured on Codex Desktop `26.820.60940`, `2026-08-26`. "Current progress on a Running row" was verified on built-in CLI `0.149.0-alpha.4.3`, `2026-08-25` — including comparing method visibility across the experimental and non-experimental schemas from `codex app-server generate-json-schema`, and polling a real in-flight Turn driven by a standalone `codex exec` once a second.

"Officially publicly supported" covers the App Server, Codex Hooks, CLI/SDK interfaces and Desktop deep links defined in official documentation and public schema, plus the public macOS APIs used in the implementation. Merely not going through the App Server is not grounds for an entry. Official [Codex Hooks](https://learn.chatgpt.com/docs/hooks) publishes the lifecycle events, the `hooks.json` location and the trust flow; official [Commands](https://learn.chatgpt.com/docs/reference/commands#deep-links) publishes the Desktop deep link. Neither is listed here.

**One observation deliberately not registered, recorded so nobody re-derives it.** Measured 2026-08-20: the trust key in `config.toml` has the shape `<hooks.json path>:<snake_case event>:<group index>:<handler index>`, where the third and fourth segments are array indices. That is a private detail, but **no feature reads it**: this app's two merge rules (append at the tail, write nothing when the install is already correct) are correct whether or not the observation holds — knowing it only explains why they carry the user's own definitions ([ADR 0014](adr/0014-the-codex-hook-definition-is-never-rewritten.md)). Per `AGENTS.md` §8.1 there is no row to add. Reporting each definition's trust state exactly *would* mean reading that key, which is an ADR-level decision and would add a row here.

## Capabilities deliberately not in this table

- The live Turn lifecycle bridge and hook install / upgrade / master switch / removal use official Codex Hooks, public events and the `hooks.json` configuration location.
- Claude Code session **discovery** uses the official public `claude agents --json` — its `--help` explicitly promises that `--json` prints active sessions including interactive ones and needs no TTY. The `status` / `waitingFor` fields in the same output are a different matter: the command is public, while those fields' existence, vocabulary and semantics are not, and they decide business state, so they are **registered separately above**.
- Claude Code's hook events, the `type: "command"` handler (including the `args` exec form and `timeout`) and the `hooks` configuration location in `~/.claude/settings.json` are all official public capabilities. This app **does write** that file's `hooks` key ([ADR 0016](adr/0016-write-the-users-claude-code-settings-and-keep-a-copy.md), superseding the earlier never-write [ADR 0010](adr/0010-never-write-the-users-claude-code-settings.md)), copying the original to `settings.json.notchline-backup` in the same directory first (and likewise `hooks.json.notchline-backup` for `~/.codex/hooks.json`). It writes an officially public configuration location in an officially public handler shape, so this is still not a private dependency. The helper that handler points at and the Unix domain socket it connects to are both inside this app's own support directory, and `/usr/bin/nc` ships with macOS; none of the three is a private dependency. The previous `type: "http"` was equally public, and the reasons for replacing it have nothing to do with publicness ([ADR 0013](adr/0013-claude-code-hooks-run-a-helper-not-a-port.md)).
- **A Claude Code row's content preview is also not registered**, even though the same row's **title** is. Their sources differ: a title can only be had by parsing a private transcript JSONL, while the preview comes from the official `MessageDisplay` hook — officially described as "While assistant message text is displayed", with the official payload `turn_id, message_id, index, final, delta`, over the `type: "command"` handler already in use. Neither a private schema nor a private path, so per [`AGENTS.md`](../AGENTS.md) §8.1 it is not an entry.
- **The process-ancestor-chain calls used for navigation** (`sysctl(KERN_PROC_PID)`'s `e_ppid`, `proc_pidpath`) and **the Apple Events used to focus a terminal tab** are not grounds for an entry: the former are public APIs, and the latter go through Terminal.app's and iTerm2's **own public scripting dictionaries**, unrelated to Claude Code. What is registered above is **the process shape "an ancestor is `Claude.app` means desktop-hosted" and that bundle identifier**.
- **The three BSD calls used for terminal read state** (`sysctl(KERN_PROC_PID)`, `devname_r`, `stat`) are public APIs, of the same nature as `NSWorkspace`'s activation notification, and are not themselves grounds for an entry; what is registered above is **the observed CLI behaviour of focus reporting**, because that path's coverage depends on it.
- Opening a Desktop thread exactly uses the official `codex://threads/<thread-id>` deep link and public macOS Launch Services.
- Quota, today's tokens, thread lists, titles, Turn detail and status correction use public App Server methods.

## Triage order after a Desktop update

1. Record the new Desktop short version, build and built-in `codex --version`. Advance this file's verification baseline only after re-verifying the private dependencies in the tables.
2. Run `NotchlineTests` first and use the failing tests to locate the feature.
3. Inspect private dependencies read-only: confirm the file, identifier or executable path still exists, then confirm the minimum schema. Never modify `app.asar`, inject into Desktop IPC, or dress a missing value up as success.
4. If official documentation or public schema has gained an equivalent capability, migrate to it and remove the corresponding private implementation notes from these tables.
5. If a feature is temporarily broken it must fail closed: `Project unavailable` for Project; thread status holds its last trustworthy value among the four, with global Disconnected only for an unresponsive App Server; never fall back to guessing from cwd, titles, timing or window focus.

## Maintenance rules

- Any new production feature depending on undocumented or uncommitted Codex implementation details must add or update a row here in the same change.
- Never register something merely because it avoids the App Server: official Hooks, official deep links, public CLI/SDK interfaces and public macOS APIs are all permitted implementations.
- Every row keeps at least the feature definition, the capability gap in the officially supported interfaces, the real implementation, the failure signals, and the code locations.
- A private schema must have fixture tests, missing/corrupt tests and an explicit conservative degradation; a parse failure must never be interpreted as an empty set or as `Chats`.
