# Current Issues

本文用于跟踪代码审查（CR）中尚未解决的问题。问题修复并完成相应测试与文档同步后，将状态更新为 `已解决`；确认无回归后再从本表移除或归档。

优先级说明：`P1` 表示可能持续影响正确性、资源消耗或状态时效性，应优先处理；`P2` 表示存在明确的可靠性、性能或可测试性风险，建议纳入近期优化。

| CR-002 | 未解决 | 任意一批 Hook 事件被消费后都会触发完整、分页的 `thread/list`，高频 `PostToolUse` 事件也不例外。 | 活跃任务可能每秒执行一次全量列表刷新，导致重复扫描、请求拥塞，并增加 `thread/list` 超时概率。 | P1 | 让 Hook 输出可区分的失效原因；仅在线程增删、审批或列表元数据可能变化时标记列表为脏，其他事件走局部状态更新，同时保留低频全量对账。 |
| CR-003 | 未解决 | `thread/list` 刷新进行中收到新的 Hook 失效信号时，调度函数会直接返回，且完成后不会补跑一次刷新。 | 旧结果即使被新鲜度检查拒绝，也可能没有后续请求，审批或线程元数据修正最多延迟到下一次 30 秒对账。 | P1 | 将刷新协调改为 single-flight 加 dirty revision；刷新期间的新失效只更新 dirty 标记，当前请求结束后若 revision 已变化则立即再执行一次。 |

| CR-006 | 未解决 | 活跃状态下每个 1 秒周期最多执行三次 Hook 安装完整性检查，重复读取脚本、Hooks 配置和设置文件并计算哈希。 | 即使没有状态变化，也会产生持续磁盘读取、哈希计算和系统唤醒，增加空闲 CPU 与能耗。 | P2 | 每个周期至多读取一次并复用结果；进一步缓存安装状态，仅在启动、手动重检、文件变化通知或 30–60 秒低频校验时重新计算。 |
