# 已读按产品各自回答，问不出来的那一半就不回答

> **标题在 2026-08-19 的第二次修订里改过一个字。** 原标题是「回答不了的那一半就不回答」，指的是终端里的 Claude Code 会话。那一半现在有答案了，但**不是**因为 Claude Code 开始说了什么——是因为换了个对象问（见「终端里的会话」）。剩下真正回答不了的，是问不出终端的那些会话。

终态轮次的退出条件是「用户已经看过它」（[ADR 0002](0002-use-desktop-unread-state-for-monitor-membership.md)）。Codex 一侧由 Desktop 的蓝点集合回答，已经实现。Claude Code 一侧此前**没有任何来源**，因此一条 Completed 行只有三种消失方式：该会话的下一次 `UserPromptSubmit`、会话从官方会话列表消失，或用户手动清空（CC-013）。用户在 Claude Desktop 里读完那一轮然后去做别的事，行就永远留着——而"读完就走"正是本产品期望的用法。

（"永远"这个词对终端会话成立，对 Desktop 托管的会话不成立：后者被隐藏 900 秒之后会被 Claude Desktop 自己拆掉，行随之消失。这是 2026-08-19 复查时才测出来的，纠正见「第三条」。）

## 决定

**已读是一个按产品各自取源的问题，不是一个可以统一实现的机制。** Claude Code 一侧分成两半，两半的证据完全不同：Desktop 托管的会话问 Claude Desktop 的记录，终端里的会话问内核手里那个终端设备。**两半都不问 Claude Code**——它自始至终没有已读这个概念。

### Desktop 托管的会话：用「最后一次被显示」回答

Claude Desktop 为每个会话在 `~/Library/Application Support/Claude/claude-code-sessions/<org>/<account>/local_<uuid>.json` 里记着 `cliSessionId`（就是 hook 携带的 `session_id`，因此两边的身份不需要猜）、`lastFocusedAt` 与 `isArchived`。对安装包 `1.32885.1` 的只读检查（2026-08-19）表明这个时刻的语义是明确的：

```js
setSessionVisibility(id, isVisible, reason) {
  …
  isVisible && (session.lastFocusedAt = Date.now(), this.saveSession(session), …)
}
```

即**它在会话被显示到屏幕上的那一刻盖章，并立刻落盘**，落盘方式是同目录临时文件 `rename`（实测 inode 变化），所以目录级 watcher 能看见它——行离开通知栏与用户读到它是同一个手势。

判定规则的第一条是：**`lastFocusedAt` 晚于该 Turn 的终止时刻即已读。**

比较的左边刻意取自本应用自己，不取自同一个文件里的 `lastActivityAt`。这两个时刻的差本来就是桌面端自己的未读等价物，但本应用已经掌握了更硬的那一半——那个轮次到底是什么时候结束的，来自结束它的那个证据（`Stop`，或 [ADR 0011](0011-a-turn-may-end-on-evidence-that-is-not-a-hook-event.md) 里那份会话状态读数）。用自己的那一半意味着：桌面端的活动记账延迟、节流甚至完全停写，都不能把一个轮次说成已读；**只有一次确实发生在它结束之后的显示可以**。这也让陈旧数据天然安全——一个旧的 focus 时刻永远追不上一个新的 Turn，所以 last-known-good 快照最多让一行多留一会儿，不会让它提前消失。

归档同样算已读：那是对该会话的一次明确动作，而 Codex 一侧的规则本来就写着「已读、归档、删除后移除」。

### 第二条：应用回到前台，且看到的就是这个会话

第一条规则**测下来不够**。2026-08-19 的实机验证：用户在 Claude Desktop 里开一个会话、提交、切到别的窗口去、等它跑完（notch 上如期出现 Completed），然后**切回 Claude Desktop 读它**——那一行没有消失。

原因不是实现漏了什么，而是那次阅读**在磁盘上不留任何痕迹**：

| 时刻 | 文件变化 | 含义 |
| --- | --- | --- |
| 01:06:33.307 | `lastFocusedAt` ← now | 用户在侧栏里选中该会话 |
| 01:06:43.458 | `lastActivityAt` ← now | 提交，轮次开始 |
| 01:07:37.826 | `lastActivityAt` ← now，`completedTurns` 1→2 | **轮次结束** |
| 之后 | **无** | 用户切走、切回、读完 |

随后对**整个** `~/Library/Application Support/Claude` 目录树做了一次「最近 6 分钟内被修改过的文件」扫描：**0 个**。`lastFocusedAt` 只在 Claude Desktop **把一个会话放上屏幕**时盖章（切换会话、恢复会话），窗口在同一个会话上重新获得焦点时它什么都不写。因此**任何只读文件的适配器都不可能看见这次阅读**，第一条规则覆盖不到的正好是本产品最常见的用法。

第二条规则因此是：**Claude Desktop 在该 Turn 结束之后「回到前台」，且 Desktop 自己的记录显示它最后放上屏幕的就是这个会话。**

三个限定缺一不可：

1. **是「回到前台」这个跃迁，不是「此刻在前台」。** 一个把 Claude Desktop 留在前台然后离开座位的用户什么都没在读；用「此刻在前台」判定，会在行出现几秒后就把它撤掉——这是本产品唯一不能犯的错。跃迁只可能由坐在键盘前的人产生。

   > **2026-08-19 补记：这一句在同一份 ADR 里被第三条推翻了。** 「会在行出现几秒后就把它撤掉」的描述是准确的，被改掉的是最后半句的定性——产品在权衡之后认定，那不是唯一不能犯的错，只是两种错里被选中的那一种。理由、限定与代价见「第三条」。本条对**第二条**仍然原样成立：第二条用的仍然是跃迁。
2. **只对 Desktop 最后显示的那个会话成立。** 窗口回到前台时呈现的就是它。排在它后面的另一个已完成会话没有被读到，行照留。
3. **只对 Desktop 认识的会话成立。** 终端会话不可能被 Claude Desktop 显示，所以把那个应用切到前台，对它一个字都没说。没有这一条，第二条规则会悄悄退化成「碰一下 Claude Desktop，所有 Claude Code 行都消失」。

用到的两件事各自都不是猜测：**哪个会话在屏幕上**来自 Desktop 自己的记录，**应用回到了前台**来自公开的 `NSWorkspace.didActivateApplicationNotification`（该通知直接携带被激活的应用，不需要匹配窗口标题、不需要 Accessibility、不驱动任何 UI）。合起来才构成一次阅读的证据。

### 第三条：用户在它原地待着的时候读了它

第二条**也测下来不够**。2026-08-19 复查，覆盖不到的是最平常的一种：**会话在 Turn 结束之前就已经在屏幕上，而用户从头到尾没有离开那个窗口。** 第一条要一次新的「被显示」，没有；第二条要一次「回到前台」，也没有——窗口根本没丢过前台。

这一次把还没查过的地方都查了，结论是**文件侧到此为止**：

| 查了什么 | 结果 |
| --- | --- |
| 记录里是否有已读字段 | 没有。安装包里 `lastReadAt` / `hasUnread` / `seenAt` / `viewedAt` 全部 0 命中；`markAsRead`、`isRead` 的命中全部属于 Outlook MCP connector，与会话无关 |
| `~/Library/Logs/Claude/main.log` 是否比文件多说了什么 | ~~没有。`[CCD] LocalSessions.setFocusedSession` 只在**切换会话**时出现，是 `lastFocusedAt` 盖章时刻的子集~~ **这一格是错的，见下面「第五条」**：它在关键的那个方向上是超集，因为它还会写 `sessionId=null`。`[SkillsPlugin] Window focused` 之后没有任何 visibility 写入（23:11:42、00:17:05 两次实例都是 0 条），这半句仍然成立 |
| Claude Code 自己 | 仍然没有任何 focus / read / seen 字段落盘 |

同一次复查还纠正了两处此前写下来的事实，两处都写在这里而不是悄悄改掉：

- **`lastFocusedAt` 会在没有人的情况下被盖章。** 2026-08-19 09:29:00 机器从睡眠唤醒，09:29:09 屏幕上那个会话的 `lastFocusedAt` 被重新写了一次，全程没有 `setFocusedSession`。第一条因此有一个方向朝「提前移除」的误判：睡醒时屏幕上是哪个会话，那个会话就被当作读过。它只影响屏幕上的那一个，所以第四条不受它污染（见下）。
- **Desktop 托管的行并不是「永远留着」。** 本 ADR 开头那句话对终端会话成立，对 Desktop 会话不成立：`shouldKillOnIdlePause()` 为真的本地会话在隐藏 900 秒后被 `teardownSession` 拆掉（实测 22:04:26 起算，22:19:27 拆除），进程随之消失、会话离开官方会话列表，行也就跟着走了。所以**切走之后最迟 15 分钟行会自己消失**，真正无限期留着的只有一种：停在那个会话上不动。CC-013 要修的是「读完之后还要再等最多十五分钟」，不是「永远」。

**在结束的那一刻，两种用户完全同形。** Turn 结束那一瞬间，坐在屏幕前看着它跑完的用户，和提交完就走开的用户，**在任何可观察的信号上没有区别**：两个人最后做的都是提交那一下。等下去也不会长出区别——读一段答案本身不产生任何事件。

所以第三条不再试图分辨他们，而是换一个更窄、能诚实回答的问题：**那个答案此刻是不是摆在一块有人可能正在看的屏幕上。**

第三条因此是：**Claude Desktop 持有前台，屏幕醒着、没有锁、没有屏保、当前登录会话在 console，且 Desktop 记录里在屏幕上的就是这个会话。**

**这是本产品唯一一条不需要任何手势的规则，因而也是唯一一条可能撤掉一行没人读过的答案的规则。这是被选中的错，不是疏忽。** 两种错只能挑一种：要么让读完的人对着一行陈旧的记录多看十几分钟，要么让走开的人丢掉一次通知。产品选了后者。反方的理由记在这里，它是成立的、被明确覆盖的：一行留久了用户可以右键拿掉（见下面「拒绝的替代方案」里的补注），而一行撤早了没有任何办法找回来——两种错的可逆性并不对称。

「持有前台」单独用是很差的证据，因为一个应用可以隔着锁屏、暗掉的显示器、屏保和切走的登录会话继续持有前台。三条公开读数把这些减回去：

| 读数 | 来源 | 挡掉的是 |
| --- | --- | --- |
| 显示器醒着 | `CGDisplayIsAsleep` | 走开之后屏幕自己暗掉——大部分「离座时间」实际落在这里 |
| 登录会话未锁定且在 console | `CGSessionCopyCurrentDictionary` | 锁屏，以及快速用户切换之后屏幕上根本不是这个人的桌面 |
| 没有屏保在跑 | 公开的 `com.apple.screensaver.didstart` / `didstop` | 只配了屏保、没配锁屏的那种设置。三条里最不吃劲的一条：默认配置是屏保连着锁屏，上一行已经挡住了；而且它是一个**可能收不到的通知**，另外两条是**读得到的状态** |

**隐藏应用不单列一条**：隐藏会让它交出前台，「持有前台」已经覆盖了。**最小化没有**——窗口进 Dock、应用仍然是活动应用，这一点下面算作未覆盖。

**任何读数都覆盖不到的**是窗口「在前台但不在人眼前」：在另一块显示器上、在另一个 Space 上、或者被最小化而应用仍然活动。要回答这些得去读窗口几何，而窗口检查的禁令不动。落在这三种状态里的终态轮次会被没人看见地撤掉，这是本规则被接受的代价。

实际行为按场景摊开如下（macOS 全局只有一个前台应用，跨显示器也只有一个，这是下面前两行成立的原因）：

| 场景 | 行 |
| --- | --- |
| 在另一个应用里干活（无论它在哪块屏幕上） | **留着**——前台是那个应用，不是 Claude Desktop |
| Claude Desktop 被别的窗口挡着，或在另一个 Space 上，总之没被激活 | **留着** |
| 屏幕关着的时候轮次跑完 | 关着的期间**留着**；用户点亮屏幕之后约 1 秒撤掉 |
| 锁屏 | 锁着的期间**留着**；解锁之后约 1 秒撤掉 |
| 用户就坐在那儿看着它跑完 | 结束后约 2 秒（`terminalReadSettlingInterval`）撤掉，不需要用户做任何事 |
| 用户把窗口留在前台走开了，屏幕还没暗 | **撤掉，没人读过**——这就是被接受的那个代价 |

用到的两件事各自仍然不是猜测：**哪个会话在屏幕上**来自 Desktop 自己的记录，**哪个应用持有前台**来自公开的 `NSWorkspace.didActivateApplicationNotification`。三条读数也全部公开、无需 entitlement、实测不弹授权。不读窗口标题、不读窗口几何、不碰 Accessibility、不做 GUI 自动化。

### 第四条：用户从它身上走开了，去了另一个会话

还剩一种：用户读完之后，在 Claude Desktop 里**切到了别的会话**。第三条要求这个会话正在屏幕上，切走之后不再成立；而 Desktop 只记录会话**被显示**，从不记录它被藏起来，所以被留下的那个会话再也不会被盖章。

第四条是：**本应用曾经看见这个会话带着已经结束的 Turn 停在 Claude Desktop 的屏幕上，而 Desktop 此后把别的会话放了上去。**

- **「曾经看见」是实时观察出来的，不是事后从时间戳里推出来的。** 两种做法都能回答「它结束的时候在不在屏幕上」，但只有前者符合 `AGENTS.md` §6.2：一个比本进程还老的时间戳只能证明某个会话被显示过，不能证明它**当时**在显示；而用户后来删掉一份记录，就会把这个答案悄悄交给次新的那一个。
- **不比较任何时间戳，也不需要。** 这份成员关系是在该会话**正是**屏幕上那个、且它的 Turn 已经结束时记下的，所以把它顶下去的事情必然发生在那之后。这同时挡掉了 Desktop 自己的记账：唤醒重新盖章的是**已经在屏幕上**的那个会话，不会是另一个，所以它落在第一条上，落不到这一条上。
- **成员关系记在 Turn 上，不记在会话上。** 新的 Turn 一开始就清掉，否则下一轮结束时只要用户正好在别的会话上，行会在没人看见的情况下直接消失。

### 第五条不是一条新的判定，是前三条共用的那句话终于有了第二个来源

第二、三、四条都建立在同一句话上：**Desktop 记录里在屏幕上的就是这个会话**。这句话来自「`lastFocusedAt` 最大的那一个」，而 2026-08-19 晚上的一次丢行说明了它缺了什么：

| 时刻 | 用户做了什么 | 磁盘上写了什么 |
| --- | --- | --- |
| 21:02:30 | 切到会话 A | A 的 `lastFocusedAt` ← now |
| 21:03:30 | 打开一个**新会话的输入框** | **什么都没有**——输入框还不是一个会话，没有东西可以盖章 |
| 21:03:58 | A 的 Turn 结束 | 行变成 Completed。本应用仍然认为 A 在屏幕上，于是把第四条的成员关系记给了它 |
| 21:04:18 | 发出新会话的第一条消息 | 新会话被显示 → A 被顶下去 → 第四条成立 → **行没人读过就消失了** |

同一句陈旧的话也会让第三条更早地丢掉这一行（用户敲输入框的时候 Claude Desktop 正持有前台），以及让第二条把「回窗口来发送」算成「回来读 A」。**这不是三个 bug，是一个**：记录只记会话**被放上屏幕**，从不记它被拿下来，而「被拿下来之后屏幕上换成了不是会话的东西」正是新建会话最常见的形状。

第三条那次复查把日志判成「盖章时刻的子集」时漏掉的，就是这一半。Claude Desktop 每次导航都写一行，并且**两个方向都写**：

```js
setFocusedSession(e){ log.info(`[CCD] LocalSessions.setFocusedSession: sessionId=${e ?? `null`}`), … }
```

（安装包 `1.32885.1`。`info` 无条件写出，不受任何调试开关控制。）`sessionId=null` 就是记录写不下来的那一半。

**因此第五条是一个否决权，不是一条新的退出路径**：

> **前三条要求的「屏幕上是这个会话」，从此要记录与 Desktop 的日志同时成立；日志说屏幕上不是会话时，三条一条都不成立。第四条另外要求顶替它的是一个会话——输入框不是。**

方向是刻意单向的，这是接受读另一个应用的日志的全部理由：**日志只能让一行多留，永远不能让一行提前消失。** 记录没声称的会话，日志不能提名；日志缺失、被轮转、被某个未来版本改了形状，`unknown` 就是本条存在之前的原样行为。这样一来，这份依赖的失效模式是「行留久了」，而不是「行没人读过就没了」——两种错的可逆性不对称，理由与第三条那一段是同一个。

两条限定跟着它一起写下来：

1. **只认本应用看着被追加进来的那些行。** `AGENTS.md` §6.2 说业务状态只能来自当前快照或本进程启动之后观察到的事件，一行上周写下的日志两样都不是。启动时已经躺在那里的那段尾巴只读一次，并且**只允许它说 `null`**——那个方向只会让行多留，而它点名的会话一律不算数。
2. **`local_<uuid>` 到 hook 身份的连接仍然来自记录**（记录里的 `sessionId` 字段），不做任何推断；接不上的 id 读成「不是这个会话」，也就是继续保留那一行。

代价照例写清楚：用户在输入框里待着的那段时间，本应用**不知道**那个会话是什么时候离开屏幕的——只知道到某一刻为止它已经不在了。所以「读完答案、随手开一个新会话」这个流程里，被读完的那一行不再由第四条撤掉，要等第三条（回到那个会话上）或它自己的下一次提交。用「新会话诞生」去反推输入框是什么时候打开的，做不到，也不打算猜。

### 这一条推翻了两处写下来的规则

按 `AGENTS.md` §5.2，冲突要说明白：

- PRD 第 3 节非目标里写着「通过窗口焦点、路径、标题、时间接近度或 GUI 自动化猜测会话身份、Project、**已读状态**或导航目标」。
- `tech-design.md` §1.3 写着「Accessibility、AppleScript、标题匹配、定时移除或『Desktop 获得焦点即已读』均不准确并违反安全约束」。

两条都是为 **Codex** 写的，而它们成立的前提在 Claude Code 一侧都不存在：Codex 有一份真的未读集合（所以用焦点去近似它，是用差的证据换掉好的证据），而且 Codex 那边**没有任何来源能说出哪个 thread 在屏幕上**（所以「获得焦点」只能被读成「所有 thread 都已读」，那确实是猜）。这里两点都反过来了：没有别的来源，且屏幕上是哪个会话有记录可查。被推翻的因此不是这两条规则的理由，而是它们的适用范围——它们继续原样约束 Codex。

**第三条推翻得比第二条彻底，必须说清楚。** 第二条只是把「焦点」当成两件可查事实中的一件；第三条直接用了那两份文档点名禁止的那个东西——**「此刻在前台」**——并且还推翻了本 ADR 自己在第二条限定 1 里写下的话。它换来的是本产品唯一一条不需要用户做任何事的退出路径，代价是走开的用户会丢一次通知，权衡见第三条。它仍然不是「获得焦点即已读」：Codex 那边这句话只能读成「所有 thread 都已读」，而这里说的是**Desktop 自己记录在屏幕上的那一个会话**，其余会话一律不受影响。

保留下来的禁令一个没动：不读窗口标题、不读窗口几何、不做时间接近度匹配、不靠等待本身移除任何一行、不碰 Accessibility 或 AppleScript、不把 Notch 点击当已读。

### ~~终端里的会话：不回答~~ 终端里的会话：不问 Claude Code，问那个终端

> **2026-08-19 第二次修订推翻了本节的结论。** 原文与被推翻的部分原样留在下面，因为被推翻的是**结论**，不是它的理由——那些理由至今全部成立。

原文：

> **Claude Code 自己不存在"已读"这个概念，任何地方都没有。** 会话记录 `~/.claude/sessions/<pid>.json` 写的是 `status`、`waitingFor`、`updatedAt`、`statusUpdatedAt`、`entrypoint` 这些；2.1.235 的二进制里没有任何 focus / read / seen 字段落盘（`isFocused` 只出现在 Ink 组件的入参上，是终端界面自己的光标位置）。终端是否在前台、用户是否正在看那个 tab，进程外无从得知，而这恰恰是 `AGENTS.md` §6.2 与 PRD 第 3 节点名禁止去猜的东西。
>
> 因此这类会话的读取状态一律报告为 **unknown**，它的终态行保持既有行为：下一次提交、会话消失，或用户手动移除（在该行上右键，或清空整张列表）。它**不是**被报告成"未读"——差别在于 unknown 的行**根本不进入未读 gate**：一个永远不可能被清除的行如果进了 gate，就会为一个没有答案的问题每秒复查一次，直到会话结束。

**上面每一句关于 Claude Code 的话都仍然成立**，2.1.236 上复查过：`~/.claude/sessions/<pid>.json` 仍然没有任何 focus / read / seen 字段；进程里确实有一个 `userPresence` 对象持有 `lastInteractionTime()` 与 `terminalFocus()`，但它只活在内存里，不落盘、不发 hook。「哪个 tab 在用户眼前」也仍然无从得知，那条禁令不动。

变的是**这一半的问题问错了对象**。原文问的是「Claude Code 能不能说出用户读没读」，答案是不能，于是这一半就此打住。换一个问法：**那个会话的终端能不能说出用户在不在它跟前**——这个问题内核一直在回答，而且是按设备分别回答的。

**判定规则：该会话控制终端的访问时间晚于该 Turn 的终止时刻，且该终端所属的应用此刻持有前台，即已读。**

> 后半句是 2026-08-20 补上的。原判定只有前半句，它被鼠标上报推翻了——理由与修正见本节末的〈访问时间不等于"有人在跟前"〉。下面这一段保留原文的论证顺序，因为它除了那一处之外仍然成立。

`kp_eproc.e_tdev`（公开的 `sysctl(KERN_PROC_PID)`）给出该进程的控制终端，`devname_r` 把设备号变成 `/dev/ttysNNN`，`stat` 给出它的 `st_atime`——**最后一次有东西从这个设备被读走**的时刻。三个都是公开 BSD 接口；不打开任何文件内容、不读窗口标题或几何、不碰 Accessibility。

实测（2026-08-19，Ghostty + CLI `2.1.236`；2026-08-20 在 `2.1.238` 上重测并补上第五行）它在五种情况下前进：

| 动作 | 到达终端的东西 |
| --- | --- |
| 敲一个键（包括开启下一轮的那次回车） | 按键字节 |
| 那个界面**拿到**前台 | `ESC [ I` |
| 那个界面**失去**前台 | `ESC [ O` |
| CLI 自己发出的查询收到回复 | 回复字节 |
| **指针划过那个界面**（不需要前台） | 鼠标上报字节 |

后两种能成立，是因为 Claude Code 自己打开了 focus reporting——`ESC [ ? 1004 h` 就在发布的二进制里，每次离开 alternate screen 都写一次。而它们恰好覆盖终端最常见的那种用法：跑着的时候切走，**回来那一下本身就是手势**。

**同样重要的是它在什么时候不前进**，这是它能用的全部原因：

- **别的 tab、别的窗口、别的应用里发生的任何事都不动它。** 实测：让一个隐藏的界面经历两轮完整的前台切换，它的访问时间 **0 次**变化，而屏幕上那个界面两次都被盖章。一个不在屏幕上的界面收不到任何东西——Desktop 那一半要靠记录才能回答的「哪个会话在屏幕上」，在终端这边由内核按设备天然分开。
- **CLI 往外写答案不动它。** 那是**修改**时间，一轮跑着的时候大约每秒两次；读那一个会把每一次渲染都当成用户。
- **轮次结束本身不动它**，这一条是单独测过的，因为它要是不成立整条路径就白做了：在一个自建 pty 上跑完一整轮（提交 → `Contemplating` → 答案 → Stop hook → `Cooked for 2s`），访问时间只在**启动时的能力查询回复**和**我敲下那句提示**两个时刻前进，此后 67 秒一次没动。轮次末尾那条 `OSC 777` 通知是纯输出，终端不回复。

**它是跃迁，不是状态。** 这与第二条同源，也是它的全部安全论证：一台开着的机器在空椅子前产生不了它，前三种动作都要有人在键盘前。

**第四种不是人**，这一条不绕过去：实测到的查询回复全部发生在 CLI 启动那几百毫秒里，那时该会话还没有任何轮次结束过，所以它不可能被当成读了哪一轮。真正的风险在将来——某个版本如果在会话中途重新查询终端，就会在没有用户的情况下推进访问时间，表现出来是一行提前消失。

**第五种也不是人，而且它不在将来。** 见下。

**因此终端这一半不设第三条那样的规则，这是决定而不是遗漏。** 第三条存在的理由是 Desktop 拿不到任何**按会话**的手势，只好退而问「答案是不是摆在一块有人可能在看的屏幕上」，并接受撤掉没人读过的行。终端这边拿得到按会话的手势，就不必做那个交换——**能拿到更好的证据时，不去用更差的**，这正是本 ADR 反对为 Codex 使用焦点近似的原话。

代价是「坐着看完、然后什么都不做」这一种不覆盖，与第三条要救的是同一种。它在终端上小得多：用户接下来做的**任何**一件事都会撤掉那一行——敲下一个提示（本来就会撤）、切到别的 tab、切到别的应用。真正留着的只有「读完之后继续盯着那个 tab 一动不动」，而那段时间里答案就在他们眼前。

**曾经写作「唯一一条可能撤掉没人读过的行的路径」的**，是失去前台那一下不由用户产生：某个应用自己跳到前台，屏幕上那个界面就收到一次 `ESC [ O`。它比第三条窄——第三条对着一个已经走开的用户也会撤，这一条要求答案在那一刻确实在屏幕上。它不再是唯一的一条，而且**"唯一"这个判断本身就是这次要修的东西**。

**退化方向全部朝保留。** 不实现 focus reporting 的终端（或没开 `focus-events` 的 multiplexer）只剩按键，于是行等的是用户的下一次敲键，而不是回到那个 tab；**根本没有控制终端**的会话——`-p` 且输出被管道接走，以及 Claude Desktop 托管的那些——答 `nil`，它的行保持原文描述的既有行为，并且仍然**不进 gate**。原文那一段关于 unknown 的推理因此一个字都没作废，它只是从"每一个终端会话"缩到了"问不出终端的那些会话"。

### 访问时间不等于「有人在跟前」（2026-08-20 修正）

上面整段的安全论证压在一句没有验过的话上：**访问时间前进 = 终端递给了会话什么**。它是错的，而且错在两层，两层都是当天在这台机器上直接测出来的。

**第一层：它记的是"会话读了这个设备"，不是"设备里有东西"。** 在自建 pty 上逐个系统调用测过：一次返回 `EAGAIN`、一个字节都没读到的 `read` 同样让访问时间前进；而对同一设备的 `write`、`open`、`close`、`tcgetattr`、`ioctl`、`select` 一个都不动它。只要有别的东西让 CLI 去读，这个读数就会动。

**第二层：Claude Code 自己打开了全动作鼠标上报。** `ESC [ ? 1000 h`、`1002 h`、**`1003 h`**、`1006 h`，启动时写一次、会话中途再写一次（`2.1.238` 抓包）。于是终端为指针在窗口上的**每一次移动**写字节进 pty——不需要按键、不需要按下、**也不需要前台**。而 macOS 把指针移动投递给指针底下的东西，与哪个应用活跃无关——这正是本 ADR 上面否掉 `CGEventSource` 鼠标移动时写下的同一句话（「移动投递给指针下面的东西，多屏下可以完全在另一块屏幕上」）。当时把这条危险挡在 Codex 那一半门外，它从终端这一半绕了回来。

**表现出来的就是用户报的那个 bug**：双屏，Ghostty 摆在其中一块屏上跑着 Claude Code 且从头到尾没拿到过焦点，轮次一结束那行就没了。指针只是路过那扇窗，甚至只是在两块屏之间穿过；gate 对已结束的轮次每秒复查一次，而隐藏一旦做出对那一轮是终局（CC-024），所以一次路过就够了，而且不可逆。

**为什么不能"读得更仔细一点"。** 访问时间是一个标量。读到它的时候，它是被一个按键、一个焦点上报还是一串鼠标上报推动的，这个信息已经不存在了。想在这一层里分辨等于要求内核记下它没记的东西。

**修正：把手势和"那个终端在不在人眼前"绑在一起。** 判定改成访问时间 ≥ 轮次终止时刻 **且** 该终端所属应用此刻持有前台（并且屏幕醒着、未锁、未切走用户——复用第三条已经在用的那三个读数）。"所属应用"由进程链回答：从会话 pid 逐级向上，看前台进程是不是它的某一级祖先（`claude` → 登录 shell → `login` → 那个终端），不需要终端名单、bundle id，也不需要判断"哪一级才算应用"。

这是把一个**状态**并进一个**跃迁**，方向与第三条那次反转相同——但这里只做 `AND`，因此**只可能让这条路径更窄**，不可能让它多撤任何一行：

- 指针划过**没有焦点**的窗口：不再算数；
- 某个应用抢前台造成的 `ESC [ O`：不再算数，因为采样那一刻持有前台的是抢走它的那个应用；
- 敲键与 `ESC [ I`：照旧算数，这两件事本来就要求那个终端在前台。

**它仍然首先是一个跃迁**，所以上面「一台开着的机器在空椅子前产生不了它」那句仍然成立：状态本身永远不足以撤掉任何一行。

**新增的代价，两条，方向相反地记清楚：**

- **`tmux` / `screen` / `ssh` 里的会话从此不再自动移除。** 它们向上走链只会走到 `launchd`，宿主永远不持有前台。这是一处**新的退化**，方向仍然朝保留：行改为等下一次提交、会话消失或手动移除。
- **仍然可能撤掉没人读过的行**，两处：指针在**确实持有前台**的终端窗口上移动算已读（与第三条对「窗口摆在空椅子前」的取舍相同，而且更窄——它还要求有人动了指针）；以及前台是在手势之后约一秒才采样的，用户在 `ESC [ O` 与 workspace 通知之间那几毫秒离开终端会被读成没有离开。

**留给下一个人的教训**，因为它比这条规则本身更值钱：这条路径当初测了「一整轮跑完不动它」「隐藏的界面不动它」「写不动它」，每一条都测得很实，唯独没测**这个读数到底在记什么**。测遍了一个命题的推论，不等于测过那个命题。

### 五条互为平级：远程控制让「两半」不再互斥

前面把 Claude Code 分成两半，读起来像是一次划分：Desktop 托管的会话有记录，终端里起的没有，两边正好分完。**远程控制推翻了这个划分。** 打开它之后，同一个会话同时摆在两个地方：终端里那个正在跑的进程，和 Claude Desktop（乃至手机）里那份视图。审批和输入两边都能做，两边看到的是同一轮。

两边由**不同的手势**读，而且只有一边写进本应用看得见的地方：

| 用户在哪里读 | Desktop 记录的 `lastFocusedAt` | 该会话终端的访问时间 |
| --- | --- | --- |
| 终端里 | **不动** | 前进 |
| Claude Desktop 里（若它为该会话建了记录） | 前进 | 不动 |

所以第五条**不是**前四条的兜底，而是与它们平级的一条：**五条任一成立即已读。** 写成兜底的话，一个两边都在的会话会一直听 Desktop 的记录，而那份记录对着一个在终端里读完的用户永远不会前进——行就永远不走，恰好是 CC-013 要修的那件事在新配置下复发。

**反方向是安全的，而且理由是结构性的而不是运气。** 第五条只可能对**真的有控制终端**的会话成立，而 Claude Desktop 托管的会话没有：Desktop 把 CLI 跑成 `--output-format stream-json`、走管道、没有终端界面——这也正是那些会话连 `status` 都没有的原因（[#41](https://github.com/soondubu137/notchline/issues/41)）。因此把第五条摊到所有会话上，动不了 Desktop 那一半的任何行为。

**远程控制也不可能产生一次假的手势**，这一点值得单独写下来，因为它是本条最容易担心的地方：远程送进来的东西走的是 `/tmp/cc-socks/<pid>.sock`，不是那个 tty；而且退一步说，即使它写了 tty 也无害——远程能送的只有**提交**（那会开一个新轮次，行随即变回 Running）和**轮次进行中的审批**（时刻早于该轮终止）。没有任何一种能落在「该轮结束之后、又没有新轮次」这个唯一有意义的窗口里。

**实测 2026-08-19：开着远程控制的 CLI 会话在 `claude-code-sessions` 树里根本没有记录。** 整棵 `~/Library/Application Support/Claude` 里没有任何文件提到它的 `sessionId`，也没有任何文件提到会话记录里那个 `bridgeSessionId`（`session_01…`）——Desktop 对它的了解走的是服务端的桥，不落本地盘。所以**今天**它照旧答 `unknown`，第五条照旧是唯一回答它的人，上面那个分支走不到。这条写进代码是因为它是一个版本的事实，不是产品该依赖的性质。

### 还剩一个洞：远程控制的会话在 Desktop 那边读完，行不走

代价说在前面：用户在手机或 Claude Desktop 上读完一个远程控制的会话，然后不碰终端——**行会留着**。两边都没有证据：Desktop 没为它建记录（上面实测），终端也没被碰过。

用户观察到的「在 CLI 里读完，Claude Desktop 那边的未读标记也消失了」说明两边确实在同步已读，但那份同步**发生在服务端**，本应用够不着——本地一个字节都没写。除非将来它落到本地，或者官方给出一个可查询的接口，这个洞就补不上。

它至少倒在安全的方向：行留着，而不是提前消失。而且它自己会收敛——用户下一次在那个终端里做任何事，或者从任何一边提交下一轮，行都会走。

## 拒绝的替代方案

- **~~「Claude Desktop 此刻在前台」即已读。~~** 原因写的是「它会替一个离开座位的用户把行撤掉」，这句话至今成立。**2026-08-19 这一条被接受了**，接受的是加了限定的版本，见第三条：加上「屏幕醒着、未锁、无屏保、会话在 console」三条读数，以及「只对 Desktop 记录里在屏幕上的那一个会话成立」。被明确接受的代价正是原来那句反对。真正没有被接受的是**不带限定**的版本——那一版会隔着锁屏和暗掉的显示器撤行，也会一碰 Claude Desktop 就把所有 Claude Code 行清空。
- **`ps -o tty=` 推断终端会话的可见性。** 一个终端窗口有很多 tab，把应用切到前台完全不能说明哪个 tab 在看——这与 Desktop 那边「哪个会话在屏幕上有记录可查」正好相反，所以那条路对终端不成立。**这一条至今成立，没有被接受。** 终端那一半用的是同一个 `tty`，但问的不是它，可见性从头到尾没有被回答过：现在的规则问「有没有东西从这个设备被读走」，那是内核按设备记的事实，不是从「应用在前台」推出来的近似。两者的差别正是本条反对的东西——把一个应用级的状态摊到它下面所有 tab 上。
- **固定保留时间。** 计时器不产生业务状态，这是本仓库反复确认过的一条。
- **把 Notch 点击当成已读。** 它是本应用自己的"已确认"，覆盖不了用户直接在桌面端阅读的情况；而且点击这条交互按 CC-012 是要拿去做导航的（唤起宿主），一个交互不能同时是两件事。

  （**终态行的右键移除不是这一条。** 它不声称用户已读，也不进入本 ADR 判定的任何一半——判定只从两个产品自己的证据里取源，右键一次都不喂给它。它是用户直接说「这一行我不要了」，而这句话不需要证据，只需要他们说了。它用的也是另一个手势：左键仍然只做导航，一个交互仍然只是一件事。）
- **用 `lastActivityAt > lastFocusedAt` 作为未读集合。** 见上：它把左右两半都交给桌面端，而左半本应用自己有更好的。
- **~~在 Turn 结束的那一刻就撤掉屏幕上那一行。~~** 同上，**已被接受**：第三条在结束后约 2 秒（`terminalReadSettlingInterval`，本来是给桌面端约 583 ms 持久化延迟留的余量）撤掉它。「那一刻两种用户完全同形」这个判断没有变，变的是拿它得出的结论——同形意味着分辨不了，产品于是选了两种错里的一种，而不是无限期保留。
- **读 `main.log` 里的 `setFocusedSession`。** 它比 `lastFocusedAt` 只少不多（只在切换会话时出现），换来的是一个更脆的依赖——日志级别、行文本和轮转都不是契约。
- **把「另一个常规应用从 Claude Desktop 手里拿走前台」算作读过。** 它能覆盖「读完就切去别的应用」，但代价是一次被别的应用抢焦点——用户不在座位上时也会发生——就足以撤掉一行没人读过的答案。第三条现在覆盖了这种用法里更早的那一刻。
- **用一次按键或滚动当作已读证据（`CGEventSource.secondsSinceLastEventType`）。** 这一版**实现过并且上线过**（`c1052bb`），第三条把它换掉了，原样记在这里：规则是「该 Turn 结束之后，用户往 Claude Desktop 里敲了键或滚了页，且它屏幕上的就是这个会话」，鼠标移动不算（移动投递给指针下面的东西，多屏下可以完全在另一块屏幕上），点击不算（本应用自己的浮层能在前台不变的情况下吃掉一次）。它比第三条安全——走开的人产生不了手势——但**答不了用户提的那个问题**：坐着看完、什么都不做的人，行不会走。另外实测中发现它有一处说不清的地方：解锁屏幕要输密码，而 `secondsSinceLastEventType` 是全机器的，分不出那几下敲的是 loginwindow 还是 Claude Desktop。

## 代价

- ~~**只覆盖一半的用户。** 纯终端用户什么都得不到。这是本决定最大的取舍，而它是诚实的取舍：另一半根本不存在可观察的真值。~~ **2026-08-19 第二次修订取消了这一条。** 最后半句是错的，而且错在一个具体的地方：不存在可观察真值的是「哪个 tab 在用户眼前」，不是「用户在不在这个会话的终端跟前」——后者内核一直按设备记着。现在纯终端用户拿到的退出路径比 Desktop 用户的更严：全部由手势驱动，没有一条像第三条那样只看状态。**真正剩下的未覆盖**是问不出终端的会话：`-p` 且输出被管道接走的，以及 Claude Desktop 托管却连 Desktop 记录也读不到的。
- **终端那一半有一条会提前移除的路径。** 某个应用自己跳到前台时，屏幕上那个界面会收到一次 `ESC [ O`，读起来和用户主动切走一样。它要求那一刻答案确实在屏幕上，因此比第三条窄，但它确实能撤掉一行没人读过的答案。
- **终端那一半不覆盖「读完之后一动不动」。** 这与第三条要救的是同一种用户，而终端这边选择不救——理由（终端上任何后续动作都会撤掉那一行）写在该节里。产品因此在两半上对同一种用户给了不同答案，这是清醒的不一致：哪一半有按会话的手势可用，就在哪一半用它。
- **第二个私有只读 schema 依赖**，风险等级与 Codex 未读适配器相同；外加一个未公开的 bundle identifier（`com.anthropic.claudefordesktop`，只用于在公开的激活通知里认出这个应用）。两者都登记在 [`non-public-codex-integration-features.md`](../non-public-codex-integration-features.md)。
- **把窗口留在前台然后走开的用户，会丢掉那一次通知。** 屏幕暗掉或锁上之前的那段时间里，第三条分不出他们和坐着看的人，会把行撤掉。这是本决定被明确选中的代价（见第三条），也是与「读完就走的人不用再等」这件事换来的。
- **窗口在前台但不在人眼前的三种状态没有覆盖**：另一块显示器、另一个 Space、最小化而应用仍活动。要回答它们得读窗口几何，而那条禁令不动。
- **三处会提前移除的路径**，其余每一处失败都朝保留的方向倒：
  - 第三条本身，见上。
  - 用户关掉了那个会话的窗口（记录里它仍然是"最后被显示的"），随后因为别的事把 Claude Desktop 切到前台——那一行会被当作已读移除。它要求关窗之后会话进程还活着（否则那一行早就因为会话消失而没了），因此实际很难碰到；而且被移除的是一个用户不久前还开着的会话。
  - 机器从睡眠唤醒时，Claude Desktop 会给**屏幕上那个**会话重新盖一次 `lastFocusedAt`（实测 2026-08-19 09:29:00 唤醒、09:29:09 盖章）。醒来时那个答案就在屏幕上，所以这一条离谱得有限；但它确实是第一条在没有人的情况下也会成立的一种方式。
